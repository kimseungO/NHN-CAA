## 1. Instance

**정의**: 가상의 CPU, 메모리, 기본 디스크로 구성된 **가상 서버**. 고객이 필요한 애플리케이션을 설치하여 End-User에게 서비스 제공

**핵심 특징**
- 콘솔에서 원하는 사양의 타입을 선택하여 **몇 분 내에 쉽게 생성**
- 사용 용도에 맞는 다양한 **인스턴스 타입(Flavor)** 제공
- **인스턴스 타입 변경**을 통해 vCPU·메모리 사양 변경 가능
- **여러 가용성 영역**을 사용하여 고가용성 아키텍처 구성 가능
- **Security Groups**로 송수신 네트워크 트래픽 제어
- **사용한 만큼만 과금 (시간당 비용)**, 인스턴스 유형별로 요금 상이
- **Monitoring 서비스**를 통해 CPU, 네트워크, 메모리, 디스크 등 상태 확인

> ⚠️ 기출 8번 함정: 상태 확인은 **Cloud Monitoring**(구 System Monitoring)이지 "Service Monitoring"이 아님

## 2. Instance Flavor (타입) ⭐암기

**명명 규칙**: `r2.c4m16` = **타입(r2)** + **스펙(c4m16 = vCPU 4 / Memory 16GB)**

| 분류 | 타입 | CPU:메모리 비율 | 특징 | 추천 용도 |
|---|---|---|---|---|
| **Standard** | **t2** | **1:1** | 경량의 컴퓨팅 리소스가 필요한 경우 | 소규모 웹 서비스 |
| **Standard** | **m2** | **1:2** | CPU·메모리를 균형 있게 할당한 범용 기본 인스턴스 | 중/대규모 웹서비스 |
| **Compute Optimized** | **c2** | **1:1** | CPU 사용에 최적화 (컴퓨팅 집약적 워크로드) | 소/중규모 게임 서비스 |
| **Memory Optimized** | **r2** | **1:4** | CPU 대비 메모리 비율을 높여 대용량 데이터 처리 | 데이터베이스, 소/중규모 게임 |
| **Performance Optimized** | **x1** | **1:4, 1:8** | **64GB 이상**의 고메모리로 높은 성능 수행 | 대규모 게임, 고성능 DB |
| **GPU** | **g2, g4** | **-** | 고성능 컴퓨팅, 딥러닝 트레이닝·추론, 머신러닝, 데이터 분석 | AI 트레이닝·추론, HPC, ML |

> 💡 헷갈림 주의: **t2와 c2 모두 1:1**이다. 차이는 "경량(t2)" vs "CPU 최적화(c2)"

## 3. 지원 OS와 스토리지 요건 ⭐숫자 암기

**공용 이미지 및 루트 블록 스토리지 최소 용량**

| 운영체제 | 루트 블록 스토리지 | 메모리 |
|---|---|---|
| **Linux** (Ubuntu, Debian, Rocky) | **20GB 이상** | **1GB 이상** |
| **Windows** | **50GB 이상** | **2GB 이상** |

- ※ 소프트웨어가 설치된 인스턴스(DB 인스턴스, GPU 인스턴스 등)는 유형에 따라 **최소 요구 사양이 다름**
- **Windows는 OS 라이선스 비용 때문에 추가 비용 발생** ⭐

**추가 블록 스토리지**

| 타입 | 지원 크기 |
|---|---|
| **HDD, SSD, Encrypted HDD, Encrypted SSD** | **1 ~ 2000GB** |

**인스턴스 타입 변경** ⭐출제

| 대상 타입 | 변경 가능 범위 |
|---|---|
| **t2, m2, c2, r2, x1** | t2, m2, c2, r2, x1 타입으로 변경 가능 |

- ⭐ **인스턴스를 중지한 후에만 타입 변경 가능** (실행 중 변경 불가)
- ⭐ 변경 표에 **GPU(g2, g4)는 포함되지 않음**
- 스케일업이 필요한 경우 타입 변경, 추가 볼륨이 필요한 경우 **Block Storage 서비스** 이용

## 4. Instance 생성 절차 ⭐순서 배열형 출제

**필수 요건 (앞 6단계)**
1. **이미지 선택**
2. **블록 스토리지 설정**(루트 블록 스토리지)
3. **가용성 영역 선택**
4. **인스턴스 타입 선택**
5. **키 페어 선택**
6. **네트워크 설정**

**선택 항목 (필수 아님)**
- **플로팅 IP 설정**, **보안 그룹 설정**
- **추가 블록 스토리지** / **사용자 스크립트** / **삭제 보호**

> ⚠️ 함정: **플로팅 IP와 보안 그룹은 필수 요건이 아니다.** 다이어그램상 "필수 요건" 괄호는 네트워크 설정까지만 포함

**추가 설정 3종 상세**

| 항목 | 내용 |
|---|---|
| **추가 블록 스토리지** | 인스턴스 생성 시 추가 연결. 연결 후 **초기 작업(파티션·포맷·마운트) 필요**. 타입 **HDD/SSD**, 크기 **1GB~2000GB** |
| **사용자 스크립트** | 인스턴스 생성 후 **초기 부팅 시 자동 실행**. 접근하지 않아도 원하는 상태로 구성 가능. **Linux/Windows OS 모두 지원** |
| **삭제 보호** | 활성화 시 실수로 삭제되지 않도록 보호. **비활성화할 때까지 해당 인스턴스 삭제 불가** |

## 5. 사용자 스크립트 ⭐

- 인스턴스 **구동 후 최초 1회** 수행 (첫 번째 부팅 완료 후, 네트워크 설정 등 초기화 과정이 끝난 뒤 실행)
- **root(Linux) / Administrator(Windows) 사용자 권한**으로 실행
- 실행 주체 = 공식 이미지에 내장된 **cloud-init(Linux)**, **Cloudbase-init(Windows)**
- 콘솔에서 로그 확인 가능

**OS별 로그 위치** ⭐암기
| OS | 경로 |
|---|---|
| Linux | **`/var/log/cloud-init-output.log`** |
| Windows | **`C:\Program Files\Cloudbase Solutions\Cloudbase-Init\log\cloudbase-init`** |

- ⭐ **인터넷 액세스가 필요한 스크립트를 프라이빗 서브넷 인스턴스에서 실행하려면 NAT Gateway 구성이 필요**

## 6. Image (Compute)

**정의**: 운영체제와 애플리케이션을 담고 있는 **가상 디스크**, 인스턴스의 **기본 디스크**로 사용

| 종류 | 내용 |
|---|---|
| **퍼블릭 이미지**<br>(=공용 이미지) | NHN Cloud에서 제공하는 이미지. **Debian, Ubuntu, Rocky, Windows** 제공 |
| **사용자 이미지** | 퍼블릭 이미지를 토대로 사용자가 수정한 이미지. 새로운 애플리케이션 설치, 각종 운영체제 설정 변경 가능. **실행 중에도 이미지 생성이 가능하지만 데이터 정합성을 위해 중지 후 생성 권고** ⭐ |
| **공유 이미지** | 사용자 이미지를 **다른 프로젝트에 공유**하거나 **다른 리전으로 복제** 가능. **동일한 소유자의 프로젝트 사이에서만 공유 가능** ⭐ |

**활용 방법**
- NHN Cloud 제공 이미지 선택 / 생성된 인스턴스로부터 새 이미지 생성 후 선택
- 이미지를 기반으로 **Instance Template**을 생성하여 빠르게 인스턴스 증설
- **Image Builder** 서비스로 요구사항에 맞는 개인 이미지 생성

**⭐⭐ Image 생성 시 주의(단골 함정)**
- **두 개 이상의 블록 스토리지를 사용하는 인스턴스**는 **`/etc/fstab` 파일에서 기본 디스크를 제외한 블록 스토리지 설정을 주석 처리한 후 이미지를 생성**해야 부팅 시 오류를 방지할 수 있음

## 7. Image 복제 · 공유 ⭐개념 구분

| 구분 | 의미 | 사용 예 |
|---|---|---|
| **복제(Copy)** | 이미지를 **다른 리전**으로 복사 | 판교에서 만든 이미지를 평촌에서도 동일하게 사용 |
| **공유(Share)** | **다른 프로젝트**에서 동일 이미지를 사용하도록 공유 | 권한을 가진 다른 프로젝트에서 사용 |

- 기본적으로 개인 이미지는 **동일한 프로젝트, 동일한 리전에서만 사용 가능**
- 이미지 공유는 공유를 시도하는 계정이 **기본 인프라 서비스에 대한 권한**이 있어야 하며, **기본 인프라 서비스가 활성화되어 있는 프로젝트로만** 공유 가능
- ※ **복제한 이미지도 공유 가능**

## 8. Instance Template

- 자주 사용하는 인스턴스 **구성 정보를 미리 정의**하여 빠르게 인스턴스를 준비하는 서비스
- 정의 가능한 값: **인스턴스 이름, 이미지, 가용성 영역, 인스턴스 타입, 블록 스토리지, 키 페어, 네트워크, 플로팅 IP 사용 여부, 보안 그룹, 추가 블록 스토리지, 사용자 스크립트**

**두 가지 용도(Case)**
- **Case 1**: 미리 정의한 템플릿으로 **동일한 사양의 인스턴스를 생성**할 때
- **Case 2**: **Auto Scale의 스케일링 그룹**을 만들 때

- ⭐⭐ **Instance Template은 생성 후 수정이 불가능하다.** 구성 값을 수정하려면 **새 Instance Template을 생성**해야 함

## 9. Image Builder

- 공용 이미지 또는 개인 이미지를 **기반으로** 사용자의 요구 사항에 맞는 **개인 이미지를 생성**하는 서비스
- 구성 흐름: **(Applications + User Script) + Image Template + Base Image → 이미지 빌드 → 개인 이미지**
- **이미지 템플릿** = 이미지를 생성하기 위한 정보를 기록해둔 문서(애플리케이션 설치 구성 요소, 사용자 스크립트, OS 정보 등을 기입)
- 이미지 템플릿을 선택하고 **이미지 빌드 시 베이스 이미지를 선택** → 빌드 완료 시 개인 이미지 생성
- 생성된 이미지는 **Image 서비스에서 관리**

**지원 애플리케이션** ⭐
PostgreSQL / MySQL / MariaDB / CUBRID / Apache Kafka / Redis / JEUS, WebtoB / Apache Tomcat / Node.js / Slurm / NHN Kubernetes Services(NKS) Worker Node / Deep Learning Framework

- ⭐ **[참고] 현재는 Linux OS와 셸(shell) 스크립트 형태의 사용자 스크립트만 지원**
- 활용: 인스턴스로부터 직접 이미지 생성을 **자동화**하고 싶을 때, 애플리케이션이 미리 설치된 개인 이미지가 필요할 때, **Auto Scale 스케일링 그룹처럼 다수 인스턴스로 구성된 클러스터 구축** 시

## 10. Key Pair (키 페어) ⭐⭐OS별 차이 최다 출제

인스턴스 생성 후 접속에는 **PEM Key**가 필요하며 **OS마다 인증 방법이 다름**

| 구분 | **Linux** | **Windows** |
|---|---|---|
| 인증 방식 | 다운로드한 **PEM 키로 SSH 접근할 때마다 인증** | 랜덤 생성된 **Administrator의 비밀번호를 키 페어로 암호화** → PEM 키로 **복호화한 암호로 인증** |
| 키 저장 위치 | 퍼블릭 키가 **`~/.ssh/authorized_keys`**에 저장 | 개인 키는 **서버로 전송되지 않음**(브라우저에서 비밀번호 복호화에만 사용) |
| 키 교체 | 유실 등 부득이한 상황 시 **교체 가능** | ⭐ **키 페어 교체 불가능** |
| 기타 | OS별 유저명 상이 | 콘솔에서 **.rdp 파일 다운로드** 제공 |

- ⭐ **키 페어는 생성 직후에만 다운로드 가능** → 키 페어 관리 정책 수립 필요
- **Windows 기본 사용자 ID는 `Administrator`**

**OS별 SSH 사용자명** ⭐암기 (`사용자명@인스턴스IP`)

| OS | 사용자명 |
|---|---|
| CentOS | **centos** |
| Ubuntu | **ubuntu** |
| Debian | **debian** |
| Rocky | **rocky** |

**키 페어 생성·관리 3가지 방식**
1. **인스턴스 생성 시 키 페어 파일 생성** — 인스턴스 정보 > 키 페어 생성 → 키 페어 다운로드
2. **콘솔에서 키 페어 파일 생성** — `Compute > Key Pair > 키 페어 생성`
3. **도구를 통한 키 페어 파일 생성** — `ssh-keygen -t rsa -f my_key.pem`로 private/public key 생성 → `cat my_key.pem.pub`로 조회 → 콘솔 `Compute > Key Pair > 키 페어 가져오기`로 **Import**

- ※ 인스턴스의 키 페어 변경은 **인스턴스 > 기본 정보 탭 > 키 페어 > [변경]**을 통해 가능

## 11. Bastion Host (베스천 호스트)

- 보안이 중요한 네트워크 환경에서 **내부 네트워크와 외부 네트워크 간의 안전한 연결을 제공하는 중계 서버**
- 내부 인스턴스에 접근하기 위한 **진입점** 역할, ⭐ **ssh(22) 포트만 허용**하고 사용자 접근 이력·명령어 사용 이력을 수집

**주요 용도 4가지**
- **보안 액세스 제공**: 안전한 SSH 또는 RDP 접속으로 내부 자원 접근
- **네트워크 격리**: 인터넷과 내부 네트워크 사이에 위치하여 직접적인 접근 제한
- **감사 및 모니터링**: 접속 로그 기록 → 누가 언제 어떤 자원에 접근했는지 추적
- **단일 진입점 제공**: 여러 서버에 직접 접근하는 대신 중앙에서 보안 정책 관리

| 구분 | 인스턴스 직접 생성 | **NHN Bastion 이용** |
|---|---|---|
| 구성 | 베스천 호스트용 인스턴스를 사용자가 직접 생성 | 콘솔에서 손쉽게 베스천 생성 |
| 이력 관리 | **ssh log, last, auditd** 등을 이용한 **수동** 이력 관리 | 콘솔에서 사용자 세션 관리, 접속 이력, 명령어 이력 관리 |

> 직접 생성 방식은 인스턴스 관리·로그 설정 및 저장 관리·보안 정책 관리에 **많은 불편**이 따름

## 12. NHN Bastion (완전관리형)

NHN Cloud의 인스턴스에 안전하게 접근할 수 있도록 제공하는 **서버 접근 제어 서비스**

**주요 기능**
- 인스턴스에 대한 **브라우저 기반 SSH 접근** (⭐ **RDP는 추후 제공 예정**)
- 사용자 관리 및 **명령어 통제**
- ⭐ 인스턴스 접속 및 명령어 사용 이력을 **최대 6개월** 제공 / **Object Storage로 백업** 제공
- ⭐ **SSH 키, 패스워드, 임시 SSH 키** 등 **세 가지** 인증 방식
- **생성·삭제되는 인스턴스를 자동으로 연결 대상으로 반영**
- **실시간 모니터링 및 세션 차단** 기능

## 13. Instance의 Life Cycle ⭐⭐최다 출제

**상태 전이**
```
Instance Launch → Scheduling → Running(실행중)
Running --stop--> Stopped(중지) --start--> Running
Running --terminate--> Terminated(종료) --start--> Scheduling(다시 배치)
Terminated / Stopped --delete--> Deleted(삭제)
Running --Restart(재시작)--> Running
```

| 상태 | 의미 |
|---|---|
| **Scheduling** | 사용자가 설정한 값에 따라 인스턴스가 배치될 **적절한 호스트를 선정하는 과정** |
| **Running(실행중)** | 정상 동작 중 |
| **Stopped(중지)** | 사용을 멈춘 상태, **호스트 자원을 점유한 상태** |
| **Terminated(종료)** | 사용을 멈춘 상태, **호스트 자원을 점유하지 않은 상태**, 최소한의 자원만 점유 |
| **Deleted(삭제)** | **되돌릴 수 없는 상태**로 자원을 회수한 상태 |

**상태별 자원 및 과금** ⭐⭐표 통째로 암기

| 구분 | **중지(Stopped)** | **종료(Terminated)** | **삭제(Deleted)** |
|---|---|---|---|
| **호스트 컴퓨터**(하이퍼바이저 자원) | 유지 | **삭제** | 삭제 |
| **루트 블록 스토리지** | 유지 | **유지** | 삭제 |
| **추가 블록 스토리지** | 유지 | 유지 | **선택 삭제** |
| **(플로팅) IP** | 유지 | 유지 | **선택 삭제** |
| **인스턴스 과금** | **할인 (90일간 90%)**<br>**GPU 인스턴스 제외** | **스토리지, 플로팅 IP 비용만 청구** | **없음** |

**중지 vs 종료 판단 기준** ⭐
| 비교 | 중지(Stop) | 종료(Terminate) |
|---|---|---|
| 자원 점유 | 점유함 | 점유하지 않음 |
| 재시작 시 부팅 시간 | **짧다** | **길다** (호스트 선정 과정 포함) |
| 인스턴스 비용 | **90일간 90% 할인**, 그 이후 정상 요금 | **과금되지 않음** |
| 연결 리소스 비용 | — | 플로팅 IP, 로드 밸런서, 블록 스토리지 등은 **정상적으로(100%) 청구** |
| 권장 | **일시적이거나 단기간** 적용 시 | 장기 미사용 시 |

- **삭제**는 자원이 완전히 회수되므로 **복구 불가** → 삭제 전 **필요 데이터 백업 권장**

## 16. Load Balancer (로드 밸런서)

**정의**: 인스턴스 하나로 처리하기 힘든 부하를 **여러 대의 인스턴스로 분산**하여 처리량을 늘리는 서비스. 트래픽의 **단일 접점** 역할

**핵심 특징** ⭐
- 인스턴스뿐 아니라 **스케일링 그룹(Auto Scale)을 대상으로 할 수 있음**
- **멤버 상태 확인 기능** 제공 → 상태 이상 인스턴스에는 더 이상 트래픽을 보내지 않음
- 지원 프로토콜: **TCP / HTTP / HTTPS / TERMINATED_HTTPS**
- 세 가지 분배 방식: **Round Robin / Least Connection / Source IP**
- 로드 밸런서로 유입되는 트래픽을 제어하는 **IP 접근 제어** 기능 제공

**연결 세션 제한** ⭐⭐숫자 암기
| 구분 | 최대 연결 세션 |
|---|---|
| **일반 로드 밸런서** | **60,000개** |
| **전용 로드 밸런서** | **480,000개** |
- 서비스 품질(QoS) 보장을 위해 **리스너별로** 동시 유지 가능한 연결 수를 제한
- 초과 요청은 로드 밸런서 내부 **큐에 누적**되어 앞선 요청 완료 후 처리 → 큐가 가득 차거나 타임아웃 시 요청이 **강제 중단**될 수 있음

## 17. Load Balancer – 모드 (L4 / L7) ⭐

| 구분 | **L4 라우팅** | **L7 라우팅** |
|---|---|---|
| 분산 기준 | **IP 및 포트 기반** 부하 분산 | **L7 데이터 기반** 부하 분산 |
| 지원 프로토콜 | **TCP, HTTP, HTTPS** | **HTTP, TERMINATED_HTTPS** |
| 계층 | 4계층 | 7계층 |

- ⭐ **L4 라우팅 모드로 로드 밸런서를 생성하고 나중에 L7 규칙을 추가할 수 있다**
- **L7 정책은 리스너의 프로토콜이 HTTP / TERMINATED_HTTPS인 경우에만 정상 동작**

**L7 규칙에 따른 액션 3종과 적용 순서** ⭐순서 출제
| 액션 | 설명 |
|---|---|
| **차단** | L7 규칙에 매칭될 경우 차단. ⭐ **Forbidden(403)** 응답 반환 |
| **URL로 전달** | 설정된 URL로 리다이렉션. HTTP 헤더의 **Location** 사용 |
| **멤버 그룹으로 전달** | 매칭 시 설정된 멤버 그룹으로 패킷 라우팅 |

- ⭐ **규칙 적용 순서 = 차단 → URL로 전달 → 멤버 그룹으로 전달**
- 우선순위: 입력한 값 기반으로 작업 유형 내 우선순위 결정, **중복된 값 입력 시 새로운 규칙이 우선**

**L7 규칙 조건** ⭐
- ⭐ **L7 규칙당 조건은 최대 10개까지 생성 가능**

| 조건 유형 | 검사 대상 | 비고 |
|---|---|---|
| **경로** | URL 경로의 값 | |
| **헤더** | HTTP 헤더에 포함된 필드 | **헤더 필드 이름(key) 추가 입력 필요** |
| **파일 타입** | URL 경로의 끝 값 | 확장자 매칭에 유용 |
| **쿠키** | HTTP 요청 헤더의 쿠키 필드 | **쿠키의 키(key) 추가 입력 필요** |
| **호스트명** | HTTP 요청 헤더의 호스트 필드 | |

**비교 방식 5종** ⭐암기
| 비교 방식 | 참(True) 조건 |
|---|---|
| **CONTAINS** | 조건 유형의 문자열이 입력값을 **포함** |
| **EQUAL_TO** | 조건 유형의 문자열이 입력값과 **일치** |
| **STARTS_WITH** | 입력값으로 **시작** |
| **ENDS_WITH** | 입력값으로 **끝남** |
| **REGEX** | 입력한 **정규식 문법**에 부합 |

## 18. Load Balancer – 리스너

- 로드 밸런서로 유입되어 처리될 트래픽을 **규칙으로 정의**. 리스너별로 **수신 포트와 프로토콜**을 정의
- **단일 리스너 구성**: 일반적으로 단일 서비스 프로토콜/포트, L7 규칙에 대해 바인딩
- **다중 리스너 구성**: 다중 서비스 프로토콜/포트, L7 규칙에 대해 바인딩 (예: HTTP 80 리스너 + HTTPS 443 리스너)
- 하나의 로드 밸런서에 **여러 개의 리스너 등록 가능**
- ⭐⭐ **단, 하나의 로드 밸런서에서 동일한 수신 포트를 가지는 리스너를 중복 생성할 수 없다**

## 19. Load Balancer – 분배 방식 3종 ⭐⭐

| 방식 | 동작 | 적합한 상황 |
|---|---|---|
| **Round Robin**(순차 선택) | 트래픽을 전달할 인스턴스를 **순차적으로** 선택. 가장 기본적·대중적 | 모든 멤버가 같은 요청에 동일한 응답을 하는 경우 |
| **Least Connection**(최소 연결 우선 선택) | 현재 **TCP 연결 수가 가장 적은** 인스턴스 선택 | 요청에 따른 처리 부하 변동이 심할 때, 특정 인스턴스 부하 집중 방지 |
| **Source IP**(원본 IP 기준 선택) | 요청자의 **원본 IP를 해싱**하여 인스턴스 선택 → **동일 IP는 항상 같은 인스턴스로** | 한 사용자의 요청을 매번 동일 인스턴스에서 처리해야 할 때 |

> ⚠️ Ch.2의 **GSLB 라우팅 규칙(FAILOVER/RANDOM/GEOLOCATION)**과 혼동 금지. 로드 밸런서 분배 방식은 **Round Robin / Least Connection / Source IP** 3가지

## 20. Load Balancer – 지원 프로토콜 ⭐

| 프로토콜 | 계층 | 특징 |
|---|---|---|
| **TCP** | 4계층 | TCP 트래픽의 로드밸런싱. 애플리케이션에 대한 **높은 성능** |
| **HTTP** | 7계층 | **평문 통신** |
| **HTTPS** | 7계층 | ⭐ **멤버(인스턴스)에서 암/복호화 수행** |
| **TERMINATED_HTTPS** | 7계층 | ⭐ **로드 밸런서에서 암/복호화 수행** |

**TERMINATED_HTTPS 상세** ⭐출제 포인트
- HTTPS 트래픽을 수신하여 **멤버 인스턴스에게는 HTTP 트래픽으로 전달**
- 최종 사용자 ↔ 로드 밸런서 구간은 **HTTPS로 높은 보안성 확보**, 서버에는 HTTP로 넘겨 **복호화에 드는 CPU 부하 절감**
- **인증서와 개인 키를 로드 밸런서에 등록**해야 함
- ⭐ **등록하는 개인 키는 반드시 비밀번호가 제거되어 있어야 올바르게 동작**
- ⭐ **로드 밸런서 이후는 신뢰할 수 있는 네트워크 구간이어야 함**

## 21. Load Balancer – 상태 확인(Health Check) ⭐

- 등록된 멤버가 정상 동작하는지 **주기적으로 확인**, 정상 응답이 오지 않으면 **비정상 인스턴스로 간주하여 부하 분산 대상에서 제외**
- ⭐ **상태 확인 프로토콜: TCP / HTTP / HTTPS** (TERMINATED_HTTPS 아님)
- ⭐ **상태 확인 설정은 리스너별로 정의되며, 리스너 생성 시 결정**

**설정 항목** ⭐
| 항목 | 내용 |
|---|---|
| 상태 확인 프로토콜 | TCP/HTTP/HTTPS 중 하나 |
| 상태 확인 포트 | 상태 확인할 멤버 인스턴스의 포트 |
| **HTTP 메서드** | ⭐ **현재는 GET만 지원**. 프로토콜이 HTTP/HTTPS일 때만 활성화 |
| **HTTP 상태 코드** | 정상 응답으로 간주할 상태 코드. HTTP/HTTPS일 때만 활성화 |
| URL | 상태 확인을 시도할 멤버 인스턴스의 경로. HTTP/HTTPS일 때만 활성화 |
| **상태 확인 주기** | ⭐ **단위는 초**. 지정된 주기마다 상태 확인 시도 |
| **최대 응답 대기 시간** | ⭐ **단위는 초**. 초과하면 **실패로 간주** |
| **최대 재시도 횟수** | 반복 시도할 최대 횟수. ⭐ **2 이상인 경우 정상 응답이 한 번 오지 않아도 바로 실패로 간주하지 않음**. 재시도 횟수만큼 반복 실패 시 부하 분산 대상에서 제외 |
| 호스트 헤더 | 상태 확인 시 호스트 헤더 필드값. HTTP/HTTPS일 때만 활성화 |

**멤버 상태 4종** ⭐암기
| 상태 | 의미 |
|---|---|
| **ACTIVE** | 멤버 연결 완료, 정상 동작 중 |
| **INACTIVE** | 멤버의 **헬스 체크가 수행되지 않는** 상태 |
| **ONLINE** | 멤버가 **비활성화되어 있는** 상태 |
| **OFFLINE** | **멤버 연결 실패** |

## 22. Load Balancer – 세션 지속성(Session Persistence) ⭐⭐

- 클라이언트의 요청을 처리한 서버가 계속 해당 클라이언트의 요청을 처리하게 하는 설정
- ⭐ **Round Robin 또는 Least Connection 분배 방식을 선택했을 때 사용 가능**
- ⭐ 분배 방식을 **Source IP로 선택한 경우 그 자체로 세션 지속성이 제공**됨

| 방식 | 지원 프로토콜 | 동작 |
|---|---|---|
| **No Session Persistence** | — | 세션 유지를 하지 않음 |
| **Source IP** (원본 IP에 의한 세션 관리) | **HTTP / HTTPS / TERMINATED_HTTPS / TCP** | 최초 요청 시 선택된 인스턴스와 원본 IP 사이의 **매핑 테이블**을 내부 보관. ⭐ **최대 10,000개의 원본 IP 매핑 저장**. ⭐ **TCP 프로토콜 리스너에서 세션을 유지하려면 이 방식을 사용해야 함** |
| **App Cookie** (응용에 의한 세션 관리) | **HTTP / TERMINATED_HTTPS** | ⭐ **인스턴스(서버) 측에서 Set-Cookie 헤더로 쿠키 설정**. 로드 밸런서가 **쿠키–서버ID 매핑** 관리. ⭐ **매핑이 3시간 동안 사용되지 않으면 자동 삭제** |
| **HTTP Cookie** (로드 밸런서에 의한 세션 관리) | **HTTP / TERMINATED_HTTPS** | ⭐ **로드 밸런서에서 자동으로 쿠키 설정**. 서버 응답에 **`SRV` 쿠키**를 추가하여 전송, SRV 값은 **서버별 고유 아이디** |

## 23. Load Balancer – 그 외 요소

**프록시 모드** ⭐
- 로드 밸런서는 **프록시 모드로 동작** → 멤버에서는 세션의 **원본(Source) IP가 로드 밸런서의 IP로 보임**
- 클라이언트의 IP를 확인하려면:

| 방법 | 적용 프로토콜 |
|---|---|
| **X-Forwarded-For 헤더** 정보 이용 | **HTTP / TERMINATED_HTTPS** |
| **Proxy Protocol** 이용 | **TCP / HTTPS** |

- 프록시 모드이므로 **클라이언트가 요청하는 포트와 서버가 서비스하는 포트를 다르게 설정 가능**

**유효하지 않은 요청 차단**
- HTTP 요청 헤더에 **유효하지 않은 문자가 포함된 경우 차단** (서버 취약점을 노린 해커 공격, 버그 있는 브라우저 대응)
- ⭐ 차단 시 클라이언트에 **400 응답 코드(bad request)** 전송

**로드 밸런서 통계 기능**
- 로드 밸런서가 처리한 **네트워크 플로우** 관련 지표를 차트로 확인
- **로드 밸런서별, 리스너별** 통계 차트 제공
- 기간 분류: **1시간, 24시간, 1주, 1달, 지정 기간**
- **클라이언트 통계량과 인스턴스 통계량은 서로 다른 차트**로 제공
- 인스턴스 통계량은 **멤버 인스턴스별 구분 조회 / 취합 결과만 조회** 선택 가능 (인스턴스별 보기: **ON/OFF**)

## 24. Load Balancer – IP 접근제어 ⭐⭐숫자·규칙 출제

**IP 접근제어 그룹**
- ⭐ **한 프로젝트에 최대 10개의 그룹** 생성 가능
- 그룹 속성: **이름, 메모, 접근제어 타입**
- 접근제어 타입: **'허용(Allow)'** 또는 **'차단(Deny)'** 중 하나
- 그룹을 삭제하면 그룹 내 모든 대상이 삭제되고, 적용되었던 모든 로드 밸런서에서 해당 IP를 제어하지 않음

**접근제어 타입**
| 타입 | 동작 |
|---|---|
| **허용(Allow)** | 그룹에 속한 IP는 **허용**, 그 외 **모든 IP 차단** |
| **차단(Deny)** | 그룹에 속한 IP는 **차단**, 그 외 **모든 IP 허용** |

**IP 접근제어 대상**
- ⭐ **한 프로젝트에 최대 1,000개의 접근제어 대상** 생성 가능
- 속성: **메모, IP 주소**
- 하나의 대상은 **IP 주소 또는 CIDR 형식의 IP 주소 범위**를 가질 수 있음

**적용 규칙** ⭐
- 한 접근제어 그룹은 **여러 로드 밸런서에 적용 가능**
- 한 로드 밸런서에 **여러 접근제어 그룹 적용 가능** — ⭐ **단, 바인딩되는 그룹들의 접근제어 타입이 동일해야 함**
- ⭐ **접근제어 그룹을 적용하지 않은 로드 밸런서는 모든 IP의 접근을 허용**
- IP 접근 제어 기능으로 설정된 **포트 이외의 트래픽은 차단**

**변경 시 동작**
| 동작 | 결과 |
|---|---|
| **로드 밸런서 삭제** | ⭐ **접근제어 바인딩만 삭제. 접근제어 그룹은 삭제되지 않음** |
| **접근제어 그룹 삭제** | 바인딩된 모든 로드 밸런서에 반영 |
| **그룹 내 대상 추가/삭제** | 바인딩된 모든 로드 밸런서에 반영 |

## 27. 자주 나오는 함정 포인트 ⭐⭐

1. **인스턴스 타입 변경은 "중지 후에만" 가능**하며, 변경 가능 타입은 **t2/m2/c2/r2/x1** — **GPU(g2, g4)는 표에 없음**
2. **t2와 c2는 둘 다 1:1**, m2는 1:2, r2는 1:4, x1은 1:4 및 1:8
3. **인스턴스 생성 필수 요건에 플로팅 IP와 보안 그룹은 포함되지 않는다** (선택 사항)
4. **중지(Stopped)는 호스트 자원을 점유**하고, **종료(Terminated)는 점유하지 않는다** → 종료 후 재시작이 부팅 시간이 **더 길다**
5. **중지 시 90일간 90% 할인**이지만 **GPU 인스턴스는 할인 제외**, 90일 이후에는 정상 요금
6. **종료(Terminated) 상태에서도 스토리지·플로팅 IP·로드 밸런서 비용은 100% 청구**된다
7. **종료 시 루트 블록 스토리지는 유지**되고 **호스트 컴퓨터 자원만 삭제**된다 (삭제 시에는 루트 블록 스토리지도 삭제)
8. **삭제 시 추가 블록 스토리지와 플로팅 IP는 "선택 삭제"** — 무조건 삭제 아님 (Ch.2 Floating IP 함정과 동일 맥락)
9. **Instance Template은 생성 후 수정 불가** → 새로 만들어야 함
10. **이미지 공유는 "동일한 소유자의 프로젝트 사이"에서만** 가능. **복제는 리전 간, 공유는 프로젝트 간**
11. **블록 스토리지 2개 이상 인스턴스는 `/etc/fstab`에서 기본 디스크 외 설정을 주석 처리 후 이미지 생성**해야 부팅 오류를 막는다
12. **Image Builder는 현재 Linux OS + 셸 스크립트 사용자 스크립트만 지원**
13. **키 페어는 생성 직후에만 다운로드 가능**. **Linux는 키 교체 가능, Windows는 키 페어 교체 불가**
14. **Windows는 개인 키가 서버로 전송되지 않으며**, 기본 사용자 ID는 **Administrator**
15. **OS별 SSH 사용자명**: CentOS→centos, Ubuntu→ubuntu, Debian→debian, Rocky→rocky (root 아님)
16. **사용자 스크립트는 최초 1회만**, root/Administrator 권한으로 실행. 로그는 **`/var/log/cloud-init-output.log`**
17. **프라이빗 서브넷 인스턴스에서 인터넷이 필요한 사용자 스크립트를 실행하려면 NAT Gateway 필요**
18. **NHN Bastion은 현재 브라우저 기반 SSH만 지원, RDP는 추후 제공 예정**
19. **Cloud Monitoring Agent는 이미지에 기본 포함** → 별도 설치 없이 구동 시 자동 수집. 지표는 **1분 단위, 52주 보관**
20. **하나의 로드 밸런서에 동일한 수신 포트를 가지는 리스너는 중복 생성 불가**
21. **로드 밸런서 분배 방식은 Round Robin / Least Connection / Source IP 3가지** — GSLB의 FAILOVER/RANDOM/GEOLOCATION과 혼동 금지
22. **세션 지속성은 Round Robin·Least Connection일 때만 설정** (Source IP 분배는 자체적으로 지속성 제공)
23. **App Cookie는 서버(인스턴스)가 쿠키를 설정**, **HTTP Cookie는 로드 밸런서가 SRV 쿠키를 자동 설정**
24. **TERMINATED_HTTPS는 로드 밸런서에서 복호화**, **HTTPS는 멤버에서 복호화**
25. **TERMINATED_HTTPS용 개인 키는 비밀번호가 제거되어 있어야** 정상 동작
26. **상태 확인 프로토콜은 TCP/HTTP/HTTPS 3가지** (TERMINATED_HTTPS 없음), **HTTP 메서드는 GET만 지원**
27. **L4로 만든 로드 밸런서에도 L7 규칙을 추가할 수 있다** (L7 정책은 HTTP/TERMINATED_HTTPS 리스너에서만 동작)
28. **L7 규칙 적용 순서는 차단 → URL로 전달 → 멤버 그룹으로 전달**
29. **로드 밸런서는 프록시 모드** → 멤버에는 원본 IP가 LB IP로 보임. 클라이언트 IP 확인은 **X-Forwarded-For(HTTP/TERMINATED_HTTPS)** 또는 **Proxy Protocol(TCP/HTTPS)**
30. **IP 접근제어 그룹을 적용하지 않은 로드 밸런서는 모든 IP를 허용**하고, **한 LB에 여러 그룹을 붙일 때는 타입이 동일해야** 한다
31. **로드 밸런서를 삭제해도 접근제어 그룹은 삭제되지 않는다** (바인딩만 삭제)
32. **Private Station은 Compute/Container/Network/Storage/Database/Security 6개 카테고리만** 제공, Notification 등은 퍼블릭 리전 이용

## 1. Cloud Native란

**정의**: 클라우드 컴퓨팅 환경에서 **현대적 애플리케이션을 구축·배포·관리하는 접근 방식**이며, 클라우드의 이점(**민첩성, 확장성, 유연성, 복원력**)을 최대로 활용할 수 있도록 하는 방식

- 용어는 ⭐ **CNCF(Cloud Native Computing Foundation)** 에서 공식적으로 정의
- 강력한 자동화 + 느슨한 시스템 운영 방식이 결합 → 엔지니어의 최소한의 수고로 방대한 시스템 관리 가능
- 전체 애플리케이션을 손상시키지 않고 **플랫폼에 독립적인 운영·관리·모니터링** 가능

## 2. 클라우드 네이티브로의 여정 (Modernization 4단계) ⭐⭐순서 배열형 출제

```
On Premise --Rehost/Replatform--> Cloud Ready --Replatform/Refactor--> Cloud Friendly --Refactor/Rearchitect--> Cloud Native
◀──────────────────────────── Modernization (클라우드의 이점 극대화) ────────────────────────────▶
```

| 단계 | 마이그레이션 전략 | 특징 |
|---|---|---|
| **① On Premise** | — | **고정된 용량, 확장성이 없는 상태** / 데이터 센터 기반으로 직접 사용자가 시스템을 운영하는 상태 |
| **② Cloud Ready** | **Rehost / Replatform** | On Premise와 **대응되는 클라우드 서비스를 이용** / 거의 그대로의 아키텍처로 마이그레이션한 **한 단계** / **빠른 마이그레이션이 목표** / 일반적으로 **Monolithic 구조** / 클라우드의 이점 중 **일부**를 획득 |
| **③ Cloud Friendly** | **Replatform / Refactor** | 좀 더 클라우드의 이점을 극대화할 수 있도록 **아키텍처를 개선** / **민첩성·탄력성에 집중** / **Auto Scale 적용** / **PaaS, SaaS 도입을 고려** |
| **④ Cloud Native** | **Refactor / Rearchitect** | 클라우드의 이점을 극대화할 수 있는 기술 등을 활용 / **MSA, Container, CI/CD, DevOps** |

> ⭐ 각 단계에 붙는 전략 키워드(Rehost → Replatform → Refactor → Rearchitect)가 오른쪽으로 갈수록 "더 많이 뜯어고치는" 순서다.

## 3. Cloud Native 주요 요소 4가지 ⭐⭐암기

| 요소 | 정의 | 핵심 특징 |
|---|---|---|
| **DevOps** | 개발과 운영 팀 간의 **협업**을 통해 소프트웨어 제품 및 서비스의 더 빠르고 지속적인 제공을 목표로 하는, **소프트웨어 개발과 IT 운영 사이의 문화와 환경** | ⭐ 기술이 아니라 **"문화와 환경"** |
| **MSA**<br>(Microservices Architecture) | 큰 애플리케이션을 **작고 독립적이며 함께 작동하는 서비스들로 분해**하여 설계하는 접근 방식 | **API, MQ 사용** / **독립적인 확장** / **독립적인 기술 선택** |
| **Container** | **OS 수준의 가상화 기술**을 사용하여 하드웨어 수준의 가상화를 사용하는 **VM 대비 경량화된 이미지**를 통해 애플리케이션 실행 환경을 제공하는 기술 | **빠른 실행 및 종료** / 애플리케이션·라이브러리 등 실행에 필요한 **모든 구성 요소를 패키지화** / ⭐ **Immutable(불변)한 이미지** / 뛰어난 확장성 및 이식성 |
| **CI/CD**<br>(Continuous Integration / Continuous Deployment) | 여러 형태로 분리된 애플리케이션 환경에서 **지속적으로 소스를 통합**하여 서비스에 전달·배포할 수 있도록 **자동화한 접근 방식** | **지속적 통합 / 지속적 전달, 배포** / 소프트웨어 개발 및 배포의 **자동화된 접근 방식** / 고품질 소프트웨어를 빠르고 안정적으로 제공 |

- 이 외에도 **서비스 메시, 컨테이너 오케스트레이션** 등의 요소를 활용

## 4. Monolithic Architecture vs MSA ⭐⭐

| 구분 | **Monolithic** | **Microservices** |
|---|---|---|
| 결합도 | **결합도가 높음** | **결합도가 낮음** |
| 장애 영향 | ⭐ **부분의 장애가 전체 서비스의 장애로** 이어짐 | ⭐ 부분의 장애가 전체 서비스의 장애로 **이루어지지 않음** |
| 확장 | 부분의 수요 증가로 **전체적인 확장 필요**, 부분적 리소스 확장이 어려움 | **부분적인 리소스 확장이 가능** |
| 변경/수정 | 서비스 변경이 어렵고 **수정 시 영향도 파악이 힘듦** | 서비스 변경을 보다 빠르게 많이 할 수 있고 **수정 시 영향도 파악이 쉬움** |
| 빌드/배포 | **빌드·배포 시간이 많이 걸림** | **배포를 좀 더 빠르게 자주** |
| 기술 스택 | **하나의 프레임워크, 하나의 언어**, 기술에 종속적 | **애플리케이션에 적합한 기술을 선택** |
| 연동 기술 | — | **API, Service Mesh** 등을 추가로 운영/관리 |

## 5. MSA 장단점 비교표 ⭐⭐표 통째로 암기

| 구분 | **장점 (Advantages)** | **단점 (Challenges)** |
|---|---|---|
| **비즈니스 & 조직** | **민첩한 대응**: 신속한 개발 및 비즈니스 변화에 유연하게 대처 가능 | **조직 구조의 변화**: 도메인 분리 및 팀 간 협업 방식의 근본적 변화 필요 |
| **기술 스택** | **기술 자율성**: 서비스별 최적화된 다양한 기술 스택 및 DB 활용 가능 | **전문성 요구**: 마이크로서비스 환경 운영을 위한 높은 기술적 숙련도 필요 |
| **배포 & 확장** | **독립적 배포/확장**: 서비스별 개별 배포와 효율적인 부하 분산(Scaling) 가능 | **복잡성 증가**: 서비스 개수가 늘어남에 따라 배포 및 테스트 프로세스 복잡 |
| **시스템 운영** | **장애 격리**: 특정 서비스 장애가 전체로 확산되지 않으며 복구가 용이 | **관리 포인트 증가**: 다수의 서비스 모니터링, 보안, 장애 대응의 어려움 |
| **성능 & 데이터** | **유연한 설계**: 아키텍처 구성이 자유롭고 데이터베이스 분산 가능 | **통신 및 트랜잭션**: 서비스 간 통신 오버헤드 발생 및 **분산 트랜잭션 처리의 어려움** |

> **"MSA는 단순히 기술적인 유행이 아니라, 클라우드 네이티브 환경에서 비즈니스 가치를 극대화하기 위한 전략적 선택"**

**MSA의 핵심 이점 4가지**
- **민첩성과 독립성**: 서비스별 독립 개발·배포 → 릴리즈 속도 향상
- **기술 최적화**: 특정 기술 스택에 갇히지 않고 도메인 특성(DB, 언어)에 맞는 도구 선택
- **탄력적 운영**: 전체를 키우는 대신 **트래픽이 몰리는 특정 서비스만 Scale-out**
- **강력한 회복력**: 서비스 간 격리로 **연쇄 장애** 방지, 빠른 복구

**직면하게 될 도전 과제 3가지**
- **운영 복잡도**: 관리 포인트가 수십~수백 개, 서비스 간 통신 오버헤드·네트워크 지연
- **데이터 정합성**: 분산 DB 간 **트랜잭션 처리(ACID 유지)** 는 기술적으로 난해
- **인프라 숙련도**: 배포·테스트·보안 모니터링이 Monolithic보다 훨씬 복잡

**성공적인 MSA 운영을 위한 6대 원칙** ⭐순서·개수 출제 주의
| # | 원칙 | 내용 |
|---|---|---|
| ① | **독립성** | 영향도 최소화를 위한 개별 배포/관리 체계 구축 |
| ② | **단일 책임(SRP)** | 명확한 비즈니스 경계 설정 |
| ③ | **표준 API 통신** | 명시적이고 표준화된 인터페이스 활용 |
| ④ | **자율적 팀 구조** | 팀이 결정권을 갖고 운영까지 책임지는 DevOps 문화 |
| ⑤ | **데이터 분산** | 서비스 간 데이터 의존성 최소화 |
| ⑥ | **분산 트랜잭션 수용** | 모든 것을 하나로 묶기보다, 서비스별 정합성을 관리하는 유연한 사고 |

**선택 기준** — MSA는 '만능 열쇠'가 아니다. ⭐ 비즈니스가 충분히 성장했는지, 도메인 분리가 명확한지, 무엇보다 **독립적인 팀 운영이 가능한 조직 구조를 갖추었는지**를 먼저 자문해야 한다.

## 6. API Gateway

**정의**: 여러 백엔드 엔드포인트 서비스들의 **게이트웨이 역할**을 하여 **API의 엔드포인트를 하나로 통합**하는 서비스

**왜 필요한가**
- API Gateway가 없으면 클라이언트는 각 서비스별 엔드포인트를 알고 접근해야 하며, 트래픽 관리 및 부하 분산 기능을 개별적으로 구현해야 함
- 동적 서비스에 대한 **서비스 디스커버리**(서비스를 구성하는 개별 인스턴스를 찾는 프로세스)와 관리가 어려움

**주요 기능** ⭐
- 제공 **플러그인**으로 백엔드 엔드포인트 서비스의 **변경/배포 없이 기능 추가 가능**
  - **CORS, 요청/응답 헤더 변경·삭제, 요청 쿼리 문자열 파라미터 추가**
  - **IP ACL, 액세스 로그, 요청 유효성 검사, 요청 수 제한** 등
- ⭐ **스테이지(Stage)** 를 이용하면 **서비스·환경별로 API 엔드포인트 도메인을 구성** 가능
  - 예) 결제 서비스, 회원 서비스, 운영 환경, 개발 환경
- **대시보드를 통한 모니터링 제공**
  - **API 인입 요청 수, 평균 응답 시간, HTTP 상태 코드 그룹(2xx, 5xx)별 응답 수** 등
- 단일 진입점을 통해 모든 서비스에 액세스, **서비스 위치 변화에 유연성** 제공
- 연동 대상: **NKS, NCS, AI EasyMaker, 기타 NHN Cloud 서비스, 외부 애플리케이션**

## 7. VM vs Container ⭐⭐최다 출제

| 구분 | **Virtual Machine (VM)** | **Container** |
|---|---|---|
| **가상화 수준** | ⭐ **H/W 수준의 가상화** | ⭐ **OS 수준의 가상화** |
| **가상화 계층** | **Hypervisor** | **Container Engine** |
| **OS** | ⭐ **Guest OS를 포함**, 크기가 큼 | ⭐ **Host OS를 공유**, 경량화 |
| **가상화 단위** | 완전한 운영체제(OS)를 포함한 가상 환경 | **호스트 OS의 커널을 공유**하며 OS 수준에서 가상화 제공 |
| **자원 소비** | 자체 OS·커널·라이브러리를 실행하므로 **상대적으로 많은 자원 소비** | 적은 자원 사용, **여러 컨테이너를 한 대의 호스트에서 실행 가능** |
| **시작 시간** | 부팅이 필요해 **시작 시간이 다소 긺** | ⭐ **빠른 시작과 종료 가능** (필요한 라이브러리 및 의존성만으로 시작) |
| **기타** | 더 많은 격리 및 완전한 운영체제 환경이 필요한 경우 적합 | 모든 종속성을 패키지, **이식성 높음** |

**계층 구조 비교**
```
[VM]        App / Bins·Libs / Guest OS  →  Hypervisor  →  Host OS  →  Infrastructure
[Container] App / Bins·Libs             →  Container Engine  →  Host OS  →  Infrastructure
```
- 컨테이너는 **Image** 형태로 만들어져 **Container Registry**에 저장·배포된다

## 8. Container Orchestration

**대규모 컨테이너 관리 시 발생하는 문제점 7가지** ⭐
| 문제 | 내용 |
|---|---|
| **관리 및 운영 복잡성** | 많은 컨테이너를 관리하려면 오케스트레이션 도구 및 복잡한 설정 필요 |
| **자원 충돌과 경합** | 여러 컨테이너 간 자원(CPU, 메모리) 경합·충돌 발생 |
| **네트워크 병목** | 다수 컨테이너가 동시에 통신할 때 병목 발생 |
| **서비스 디스커버리의 어려움** | 컨테이너가 동적으로 생성·종료될 때 디스커버리와 로드 밸런싱을 실시간 관리하기 어려움 |
| **로그 및 모니터링의 복잡성** | 많은 컨테이너의 로그·모니터링 데이터를 효과적으로 수집·분석하기 어려움 |
| **보안 및 규정 준수** | 각 컨테이너의 보안 설정 및 감사 추적 필요 |
| **컨테이너 이미지 관리** | 이미지 버전 관리와 레지스트리의 효율적 활용 필요 |
| **자원 낭비** | 스케일 다운이나 비활성 기간에서의 자원 관리 중요 |

**Container Orchestration 정의**: 여러 컨테이너의 **배포, 관리, 확장, 네트워킹** 등을 자동화하는 **도구의 집합**. 컨테이너화된 애플리케이션의 복잡성을 관리하는 데 중요한 요소

**제공 기능 6가지** ⭐⭐암기
- **자동화된 배포**
- **확장성**
- **자가 복구**
- **서비스 검색과 로드 밸런싱**
- **롤링 업데이트/롤백**
- **리소스 관리**

**Kubernetes**
- 컨테이너 오케스트레이션 및 관리를 위한 **오픈소스 플랫폼**
- 구조: **Control Plane** (중앙) ↔ **Data Plane** (각 노드 그룹)
- 주요 특징: 컨테이너 오케스트레이션, 마이크로서비스 지원, **자동 확장/축소**, 서비스 디스커버리 및 로드 밸런싱, **롤링 업데이트와 롤백**, 강력한 스케줄링, **자체 복구**, 고가용성 지원

## 9. NHN Kubernetes Service (NKS) ⭐

**정의**: NHN Cloud에서 제공하는 확장성이 뛰어나고 자동화된 **관리형(Managed) Kubernetes 오케스트레이션 서비스**

**주요 기능**
- **NHN Cloud 기반 서비스 연동**: **로드밸런서, NCR, 서비스 게이트웨이, 블록 스토리지** 등
- **클러스터 웹 콘솔 제어 기능 제공**: 클러스터, **노드 그룹**, **오토스케일** 등
- **빠른 Kubernetes 최신 버전 제공 및 무중단 업데이트 기능 제공**
- ⭐ **GPU 노드 구성 가능**

**구성 요소 3가지** ⭐⭐책임 주체 구분이 핵심
| 구성 요소 | 정의 | 관리 주체 |
|---|---|---|
| **클러스터** | 컨테이너화된 애플리케이션을 실행하는 **노드의 집합** | — |
| **컨트롤 플레인** | 클러스터를 관리하며 노드와 상호작용하여 컨테이너화된 애플리케이션 관리 | ⭐ **NHN Cloud에서 관리** |
| **노드** | 사용자의 애플리케이션이 구동되는 **워커 머신** | ⭐ **사용자가 관리** |

**획득 인증 3종** ⭐
| 인증 | 의미 |
|---|---|
| **CNCF Certified Kubernetes** | 쿠버네티스 표준 API를 준수하는 인증 (**상호운용성**) |
| **CNCF KCSP** | 전문적인 **컨설팅과 기술 지원**을 제공할 수 있는 역량 인증 (Kubernetes Certified Service Provider) |
| **OPA K-PaaS 적합성 인증** | K-PaaS 코어 공급, K-PaaS 코어 API 지원 취약점 점검을 통과한 클라우드 플랫폼 서비스 |

**추가 특징**
- Load Balancer를 활용한 서비스 노출, 블록 스토리지를 이용한 **영구 볼륨(Persistent Volume, PV)** 지원
- **kubeconfig 파일**을 지원하여 인터넷이 연결된 환경에서 쉽게 클러스터에 접근
- ⭐ 클러스터 백업이 필요한 경우 **Velero 플러그인**을 사용하여 **오브젝트 스토리지에 백업**

## 10. NKS Cluster 아키텍처 ⭐

```
사용자 → kubectl → [API Server] → Scheduler / Resource Controller / Storage   ← Control Plane
                                    ↓
                          NODE (사용자 Pod → Containers)
                                    ↓
                NHN Cloud 서비스 연계: VPC / Block Storage / Load Balancer / Monitoring
```

**컨트롤 플레인 주요 구성 요소 3가지** ⭐⭐역할 구분 출제
| 구성 요소 | 역할 | 기능 |
|---|---|---|
| **API Server** | 쿠버네티스 클러스터의 모든 상호작용을 위한 **중심 접점** | 사용자의 **kubectl 명령어를 포함한 모든 REST API 요청 처리**, 클러스터의 현재 상태를 검증·설정하며 다른 구성 요소 간의 통신 조정 |
| **Scheduler** | **새로 생성된 파드(Pod)를 실행할 최적의 노드(Node)를 결정** | 각 노드의 리소스 가용성, 제약 조건, 정책 등을 고려하여 파드를 배치할 가장 적합한 노드 선택 |
| **Resource Controller** | 클러스터의 현재 상태를 사용자가 원하는 상태(**Desired State**)로 유지·관리하는 **제어 루프(Control Loop)** | 디플로이먼트, 복제 컨트롤러 등 다양한 내장 컨트롤러 포함. **파드의 복제본 수 유지**, 노드 상태 모니터링 및 복구 조치 |

- 컨트롤 플레인 구성 요소들은 일반적으로 **별도의 머신(가상 머신 혹은 물리 머신)에서 구동**
- ⭐ **고가용성 보장을 위해 한 클러스터에 다수의 컨트롤 플레인 구성 요소를 구성할 수도 있음**
- **노드**는 컨트롤 플레인과 **연결되어야 동작**하며, 컨트롤 플레인의 애플리케이션 구동·정지 명령에 따라 수행. 하나의 클러스터에 **다수의 노드** 존재 가능
- Kubernetes가 제공하는 기능은 **클러스터 단위로 동작하며, 클러스터 단위로 설정**

## 11. NHN Container Service (NCS) ⭐

**정의**: 인스턴스, Kubernetes와 같은 **컨테이너 실행 환경을 구성하지 않아도** 컨테이너를 구동하는 환경을 제공하는 서비스
- ⭐ **빠르고 안전한 서버리스(Serverless) 컨테이너 인스턴스 서비스** — 서버를 관리하지 않고도 컨테이너로 애플리케이션 배포

**주요 기능** ⭐
- **NAS를 볼륨으로 사용 가능**
- **GPU를 사용하는 컨테이너 구성 가능** (CUDA 및 머신 러닝 애플리케이션 실행 시 하나 이상의 GPU 사용 가능)
- 컨테이너에 **로드밸런서 연결, Floating IP와 도메인을 통해 서비스를 외부 노출 가능**
- **롤링 업데이트 배포, 예약 실행/종료**
- ⭐ **컨테이너 이미지 악성 코드 검사**
- **비정상 컨테이너를 자동으로 복구**하여 원하는 수만큼의 컨테이너를 동작
- NHN Cloud VPC에 워크로드를 실행 → 가상 네트워크 내 서브넷에 배포하면 다른 리소스와 안전하게 통신
- 워크로드 실행 시 Load Balancer 사용 여부를 지정하면 **NCS가 자동으로 Load Balancer에 컨테이너를 추가**
- **NHN Cloud Storage와 연결하여 영구 스토리지 사용 가능**

**구성 요소 3가지** ⭐⭐순서·정의 출제
| # | 구성 요소 | 기술하는 내용 |
|---|---|---|
| ① | **템플릿** | 컨테이너 **사양, 이름, 서브넷, 레지스트리, NAS, DNS, 버전 정보, HostAliases** 등을 기술 |
| ② | **워크로드** | **템플릿을 참조**하여 정의. **작업 실행 수, 로드밸런서 사용 여부, Floating IP, 스케줄, Private DNS 사용 여부**를 기술 |
| ③ | **작업(Task)** | **하나 이상의 컨테이너 실행 단위**. 워크로드에서 작업 수 정의. ⭐ **VPC Subnet으로부터 할당받은 IP가 지정** |

> ⭐ 관계: **템플릿 ← (참조) ← 워크로드 → (실행) → 작업(Task)**

## 12. NHN Container Registry (NCR) ⭐

**정의**: 컨테이너 이미지를 쉽고 안전하게 **저장, 관리하고 배포**할 수 있는 **비공개 컨테이너 레지스트리 서비스**

- ⭐ **NKS와 NCS를 모두 지원**

**주요 기능**
- ⭐ **OCI(Open Container Initiative) 규격을 지원** (OCI 호환 아티팩트 저장·관리 가능)
- **HTTPS 암호화, NHN Cloud 인증 및 권한 관리**를 통한 보안성 강화
- ⭐ **NHN Cloud Object Storage 기반**으로 확장성 및 안정성 제공
- 웹 콘솔을 통한 레지스트리 관리(**생성, 삭제, 조회** 등) 가능
- ⭐ **이미지 스캔을 통한 취약성 점검**, **이미지 서명을 통한 무결성 점검** 기능 제공
- ⭐ **리전 간 레지스트리 복제 기능** 제공
- 외부 저장소 및 **CI/CD 도구와 연동** 가능
- 이미지 사용량, 다운로드 횟수, 버전 관리 등에 대한 **통계와 로그** 제공

**구성 요소 4가지** ⭐암기
| 구성 요소 | 의미 |
|---|---|
| **Registry** | 컨테이너 **이미지를 보관 및 관리** |
| **Image** | **실행 가능한 애플리케이션 패키지** |
| **Artifact** | 이미지를 구성하는 **세부 레이어** |
| **Tag** | **이미지 버전 구분용 식별자** |

## 13. NHN Cloud Pipeline (CI/CD) ⭐⭐순서 배열형 출제

**정의**: 소스 코드 빌드부터 컨테이너 이미지 생성, 배포까지 자동화하는 **지속적 통합·배포(CI/CD) 서비스**

**4단계 흐름 — End-to-End 자동화**
| 순서 | 단계 | 역할 | 사용 도구/전략 |
|---|---|---|---|
| **1** | **Source** | **코드 연동 및 관리** | **GitHub, GitLab, Private 저장소** |
| **2** | **Build** | **빌드, 컴파일, 이미지 생성** | **Jenkins 연동, NHN Cloud 빌드 도구, Helm 차트** |
| **3** | **Registry** | **이미지 등록 및 저장** | **NCR(NHN Container Registry), Docker Hub** |
| **4** | **Deployment** | **서비스 환경 배포** | **NKS/NCS 배포, Blue/Green 배포, 자동/수동 승인** |

**주요 기능**
- 사용자가 정의한 **스테이지와 시나리오**를 기반으로 릴리즈 프로세스의 빌드·테스트·배포를 자동화
- 각 스테이지에서는 취합, 빌드, 테스트, 배포 단계를 **병렬로 생성하고 실행** 가능
- ⭐ **자동 트리거링 이벤트**(**Git Push**, 다른 파이프라인으로의 실행 등)를 통해 파이프라인 구동
- **GitHub, Jenkins, Kubernetes 계정** 등을 환경 설정에 등록하여 팀원 간 협업 관리
- 파이프라인 상태를 **실시간 확인**, **이메일이나 문자로 알림** 수신
- ⭐ **승인 관리 기능**을 통해 무분별한 운용을 최소화하고 안전한 운영 지원

## 16. 자주 나오는 함정 포인트 ⭐⭐

1. **Cloud Native 용어의 공식 정의 주체는 CNCF** (Cloud Native Computing Foundation)
2. **Modernization 4단계 순서**: On Premise → **Cloud Ready** → **Cloud Friendly** → **Cloud Native**. Cloud Ready와 Cloud Friendly 순서를 뒤집는 오답 주의
3. **Cloud Ready는 Monolithic 구조가 일반적**이고 클라우드 이점 중 **일부만** 획득. "Auto Scale 적용"은 **Cloud Friendly** 단계
4. **DevOps는 도구가 아니라 "문화와 환경"**
5. **Cloud Native 주요 요소는 DevOps / MSA / Container / CI/CD 4가지**. 서비스 메시와 컨테이너 오케스트레이션은 "이 외의 요소"로 별도 언급
6. **Monolithic은 부분 장애가 전체 장애로 이어지지만, MSA는 그렇지 않다**
7. **MSA의 단점에 "분산 트랜잭션 처리의 어려움"과 "조직 구조의 변화 필요"가 포함**된다 — MSA를 무조건 우월한 것으로 서술하면 오답
8. **MSA 선택 기준은 기술이 아니라 조직** — "독립적인 팀 운영이 가능한 조직 구조를 갖추었는지"
9. **VM은 H/W 수준 가상화 + Guest OS 포함**, **Container는 OS 수준 가상화 + Host OS 공유**. 뒤바꾼 지문 주의
10. **컨테이너 이미지는 Immutable(불변)** 하다
11. **Container Orchestration 제공 기능 6가지**: 자동화된 배포, 확장성, 자가 복구, 서비스 검색과 로드 밸런싱, 롤링 업데이트/롤백, 리소스 관리
12. **NKS는 컨트롤 플레인을 NHN Cloud가 관리하고, 노드는 사용자가 관리**한다 — "노드까지 NHN Cloud가 관리"는 오답
13. **NKS는 GPU 노드 구성이 가능**하다 (Auto Scale 미지원인 GPU 인스턴스 함정과 혼동 주의)
14. **NKS 클러스터 백업은 Velero 플러그인 + 오브젝트 스토리지**
15. **API Server는 kubectl 요청의 중심 접점**, **Scheduler는 파드를 배치할 노드 결정**, **Resource Controller는 Desired State 유지**. 역할을 바꿔 놓는 지문 빈출
16. **고가용성 보장을 위해 한 클러스터에 다수의 컨트롤 플레인 구성 가능**
17. **NCS는 서버리스** — 인스턴스나 Kubernetes 같은 **실행 환경을 구성하지 않아도** 컨테이너 구동
18. **NCS 구성 요소는 템플릿 → 워크로드 → 작업(Task)** 순이며, **워크로드가 템플릿을 참조**한다. 방향을 뒤집으면 오답
19. **로드밸런서 사용 여부·Floating IP·스케줄은 "워크로드"에 기술**, **컨테이너 사양·서브넷·NAS·레지스트리는 "템플릿"에 기술**
20. **NCR은 OCI 규격 지원 + Object Storage 기반 + 리전 간 복제 가능**
21. **NCR 구성 요소는 Registry / Image / Artifact / Tag 4가지** — Artifact는 "이미지를 구성하는 세부 레이어"
22. **Pipeline 4단계 순서**: Source → Build → Registry → Deployment
23. **Pipeline의 Deployment 전략에 Blue/Green 배포와 자동/수동 승인**이 포함된다
24. **소규모 애플리케이션 + 클러스터 관리 부담 회피 → NCS**, **대규모 오케스트레이션 필요 → NKS**
25. **API Gateway의 스테이지(Stage)** 는 서비스·환경별 API 엔드포인트 도메인 구성용이며, 플러그인은 **백엔드 변경/배포 없이** 기능 추가를 가능하게 한다
