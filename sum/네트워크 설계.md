## 1. VPC (Virtual Private Cloud)

**정의**
- 논리적으로 격리된 **가상의 사설 네트워크**에서 NHN Cloud 리소스를 운영하는 기능
- 각각의 VPC는 **완전히 독립된 서브넷과 라우팅**을 구성 → 기본적으로 서로 **격리(망 분리)**
- Instance 등 다수 서비스의 리소스는 VPC로 만들어진 네트워크 환경이 **선행 필수**

**핵심 특징**
- 목적에 따라 여러 개 생성 가능 (개발/테스트/운영, 애플리케이션별, 조직별)
- 트래픽 제어 수단: **Subnet(영역 분할) / Routing(경로 제어) / Network ACL·Security Groups(흐름 제한)**
- Private IP 범위는 **CIDR 표기법**으로, **RFC1918**에 정의된 범위로 기술

**비용** ⭐
- **1개의 VPC**에 대해 Subnet + Routing 포함 **무료**
- **1개 초과분부터 시간당 비용 과금**
- 네트워크 **트래픽 비용은 VPC와 무관하게 별도 과금**

**쿼터**: 프로젝트당 **3개** (조정 가능)

## 2. Subnet

**정의**: VPC IP 주소 범위 내에서 용도에 맞게 네트워크 공간을 **세분화**한 IP 주소 영역 (VPC의 하위 단위)

**제약사항** ⭐출제
| 항목 | 내용 |
|---|---|
| IP 범위 | 반드시 **VPC의 Private IP 범위 안에** 포함되어야 함 |
| 중복 | 다른 서브넷과 **겹쳐서는 안 됨** |
| 수정 | 서브넷 IP 주소 범위는 **설정 후 수정 불가** |
| 최소 크기 | **/28** |
| 라우팅 | 생성 시 VPC의 **기본 라우팅 테이블에 자동으로 연결** |
| 쿼터 | **VPC당 10개** |

**퍼블릭 vs 프라이빗**
- 서브넷은 기본적으로 **프라이빗 상태**(인터넷 접근 불가능한 상태)
- **퍼블릭 서브넷** = Internet Gateway + 라우팅 테이블 설정을 통해 인터넷에서 접근 가능하게 만든 서브넷
- **프라이빗 서브넷** = 인터넷을 통한 접속이 제한됨. 필요 시 추가 라우팅 테이블 설정 가능

**서브넷 설계 — 예약 IP** ⭐숫자 암기
- 서브넷마다 **4~5개의 IP가 예약**됨. `10.0.1.0/24`의 경우:

| IP | 용도 |
|---|---|
| 10.0.1.0 | 자체 네트워크 주소 |
| 10.0.1.255 | Broadcast 주소 |
| 10.0.1.1 | 라우터에 연결되는 **Gateway IP** |
| 10.0.1.2 | **DHCP Server IP** |
| 10.0.1.3 | **인터넷 게이트웨이 (옵션)** ← 5번째, 옵션이라 "4~5개" |

- `/24`는 호스트 할당 가능 IP가 이론상 **254개**지만, 실제로는 위 예약분 + 시스템 환경에서 고정/예약되는 IP가 있어 **충분히 큰 범위로 설계 권장**
- 일반적으로 **프라이빗 서브넷을 크게** 설계 → 퍼블릭에는 최소한의 리소스(웹서버, External LB, NAT GW)만 배치
- 인스턴스 생성 시 Private IP는 서브넷 범위에서 **Random(임의) 할당**. **고정 IP가 필요하면 Network Interface를 수동 생성**

## 3. Network Interface

**정의**: 가상 네트워크 카드로써 VPC의 **논리적 네트워크 요소**

**포함할 수 있는 속성**
- VPC·서브넷 내에 있는 Private IP / Floating IP / 하나 이상의 Security Groups / 연결된 장치(인스턴스, Gateway 등) / 이름

**기타**
- **가상 IP(VIP)**: 이중화, IP 선점 등을 위한 가상 IP
- **보안**: 스푸핑 방지, 보안 그룹 설정
- **소스/대상 확인**: 인스턴스가 수신하는 트래픽의 소스 또는 대상인지 확인

**자동 생성 vs 수동 생성** ⭐
- 인스턴스 생성 시 **자동 생성**되는 Network Interface와의 차이:
  - Private IP를 **지정하여 생성**할 수 있음
  - 인스턴스와 함께 자동 생성되는 Network Interface는 **인스턴스 삭제 시 같이 삭제**됨 (수동 생성분은 유지)
- 다른 서비스의 리소스 생성 시에도 같이 생성됨: Instance, Load Balancer, Internet Gateway, Service Gateway, NAT Gateway, Transit Hub의 Attachment, Network Firewall
- 서브넷 생성 시에도 **예약된 IP 중 일부가 같이 생성**됨

---

## 4. Internet Gateway

- VPC의 리소스를 **인터넷에 연결**할 수 있게 해주는 서비스
- 생성한 뒤에 **라우팅 테이블 설정이 필요** (콘솔에서 라우팅 테이블과 Internet Gateway의 연결 버튼 클릭으로 간단히 설정)
- 기본적으로 인터넷 액세스가 차단된 **서브넷 안의 리소스들도 인터넷 액세스가 가능**해짐
- **Internet Gateway 자체의 비용은 무료** (트래픽에 대한 비용은 발생) ⭐
- 쿼터: 프로젝트당 **3개**

## 5. Routing & CIDR

**CIDR (Classless Inter-Domain Routing)**
- 기존 **클래스 기반** IP 주소 할당 방식보다 더 효율적으로 사용할 수 있는 IP 주소 할당 방식
- IPv4는 8bit씩 4개의 옥텟, 총 **32bit**
- `/24` = 앞 24bit는 고정, 뒤 8bit가 범위 → `192.168.0.0` ~ `192.168.0.255`
- `/32` = 전체 32bit 고정 → **하나의 IP만** 지정
- **`0.0.0.0/0` = Anywhere(모든 주소)**. 인터넷 망으로 나가는 트래픽의 목적지 범위 표기 시 사용 ⭐
- **링크 로컬 주소**: 자동으로 IP 주소를 할당받을 수 없을 때 **일시적으로** 사용되는 IP 주소

**RFC1918 사설 IP 대역** ⭐숫자 암기
| 구분 | IP 주소 영역 | 사용 가능한 주소 개수 |
|---|---|---|
| 24bit block | **10.0.0.0/8** | 16,777,216 |
| 20bit block | **172.16.0.0/12** | 1,047,576 |
| 16bit block | **192.168.0.0/16** | 65,536 |

**local 라우터**
- VPC를 생성하면 **자동으로 생성되는 암시적 라우터**
- **VPC 내 리소스 간 라우팅**을 담당

**라우팅 테이블**
- 패킷이 출발지에서 목적지로 이동하는 **경로를 결정**하는 데 사용되는 테이블
- Route는 연결된 Subnet에서 발생되는 패킷들의 **목적지 경로 지정**
- **CIDR을 통해** 패킷의 목적지 IP 주소를 찾고, 그에 따른 목적지를 설정 (게이트웨이 타입 + 게이트웨이 이름)
- 기본 라우팅 테이블은 **VPC 생성과 같이 생성**되며 VPC의 모든 Subnet과 **기본 연결**
- 새로 생성된 라우팅 테이블에는 **자신이 속한 VPC의 범위를 목적지 CIDR로 가지고 게이트웨이가 local**인 라우트 규칙이 기본 포함
- 쿼터: 라우팅 테이블 **VPC당 10개**, 라우트 **라우팅 테이블당 10개(최대 100개)**, **정적 라우트 Subnet당 20개(조정 불가)**

## 6. 기본 라우팅 테이블 & 암시적/명시적 연결 ⭐개념 구분

| 구분 | 의미 |
|---|---|
| **암시적 연결** | 서브넷이 별도 설정 없이 **기본 라우팅 테이블에 자동 연결**된 상태. **암시적 연결 = 기본 연결** |
| **명시적 연결** | 새 라우팅 테이블을 생성한 뒤 특정 서브넷을 **직접 연결**한 상태 |

- 특정 라우팅 테이블에 서브넷이 **명시적으로 연결되면 더 이상 기본 라우팅 테이블의 규칙을 따르지 않음** ⭐
- **새롭게 만들어지는 서브넷은 기본 라우팅 테이블에 암시적으로 연결되므로 주의 필요**
- 프라이빗 서브넷을 퍼블릭 서브넷과 라우팅을 분리하려면 → **새 라우팅 테이블 생성 후 프라이빗 서브넷에 명시적 연결**

## 7. Floating IP

- 인터넷에서 인스턴스에 직접 액세스하기 위해 필요한, **고정된 공인 IP**를 할당하여 리소스와 **1:1 연결**
- 인스턴스 **또는 로드밸런서**와 같은 리소스에 연결하여 사용
- 특정 리소스에 연결된 Floating IP의 연결을 **해제한 후 다른 리소스에 연결 가능**
- ⭐ **인스턴스 삭제 시 Floating IP 삭제는 "선택 사항"** (무조건 함께 삭제되지 않음 → 기출 4번 함정)
- ⭐ **생성과 동시에 연결 여부와 관계없이 시간당 비용 발생** (놀려도 과금)
- 인터넷 게이트웨이가 연결된 네트워크 환경에서 사용 가능
- 콘솔의 **Network Interface 메뉴에서도** 연결 가능
- 쿼터: 프로젝트당 **50개**

## 8. Security Groups (보안 그룹)

- **인스턴스의 송수신 트래픽을 제어**하여 인스턴스를 보호하는 서비스
- IP 프로토콜, 포트, 원격 소스를 이용하여 보안 규칙 설정
- **Network Interface에 바인딩** ⭐

**동작 방식** ⭐핵심
| 항목 | 내용 |
|---|---|
| 기본 규칙 | 모든 **송신(outbound) 트래픽의 허용 규칙**이 기본 설정되어 있음 |
| 수신(inbound) | 기본이 **All Deny** 상태 → **허용 규칙을 추가 설정**하는 방법으로 구성 |
| 상태 | **상태 저장(Stateful)** → 한번 연결된 세션은 **반대 방향의 규칙이 없어도 허용** |
| 원격 소스 | **CIDR로 IP 범위를 지정**하거나 **다른 보안 그룹을 지정** 가능 |
| 비용 | **별도 비용 없음** (단, 네트워크 트래픽 요금은 별도 부과) |

- 다른 보안 그룹을 지정하면 → 해당 보안 그룹을 할당받은 리소스로부터 수신되는 트래픽을 허용하는 규칙을 만들 수 있음

---

## 9. Network ACL

- **VPC 네트워크로 유입되는 패킷을 네트워크 단위로 제어**하는 서비스
- Security Groups와 더불어 **추가적인 트래픽 제어**를 가능하게 함
- **생성 후 VPC와 바인딩**하여 설정 (생성 시가 아님) ⭐
- 출발지·목적지의 IP 프로토콜, 포트, CIDR 등을 이용하여 규칙 설정

**Security Groups와의 결정적 차이** ⭐⭐
| 비교 항목 | Security Groups | Network ACL |
|---|---|---|
| 적용 단위 | 인스턴스(Network Interface) | **네트워크(VPC)** |
| 상태 | **Stateful(상태 저장)** | **Stateless(상태 비저장)** |
| 규칙 | **허용(Allow)만** 설정 | **허용/차단(Allow/Deny) 모두** 설정 |
| 방향 | 응답 트래픽 자동 허용 | 송/수신 **양방향 모두 명시적 규칙 필요** |
| 우선순위 | 없음(모든 규칙 종합) | **순서 번호(priority)에 따라 적용, 번호가 작을수록 우선** |
| 비용 | 무료 | **무료** |

**쿼터** ⭐숫자 암기
- **프로젝트당 최대 10개 ACL**
- **ACL당 최대 100개 Rule**

**Rule 관리 방법**
| 방식 | 설명 |
|---|---|
| **Whitelist** | 기본적으로 **모든 트래픽을 차단** → 허용이 필요한 트래픽만 허용 규칙으로 등록. **Inbound/Outbound 규칙을 동시에 등록**해야 함 |
| **Blacklist** | 기본적으로 **모든 트래픽을 허용** → 차단이 필요한 트래픽만 차단 규칙으로 등록 |

**ACL 생성 시 기본 규칙** ⭐
- 생성 시 **순서 번호 101번에 모두 허용 규칙**, **순서 번호 32765에 모두 차단 규칙**이 기본 적용
- 기본(default) 상태 = 모두 허용 = **블랙리스트 방식**
- **ACL의 마지막 Rule(32765)은 정책상 모두 차단이며 삭제할 수 없음**
- **순서 번호 101번~32765번 사이의 값을 사용해 원하는 Rule을 추가 가능**
- **1~100번은 내부 시스템용으로 예약**되어 있음 ⭐
- 순서를 수정할 수 없으므로 삭제 후 재생성 → **10~100 사이의 순서 번호로 간격을 두고 설정**하는 것이 좋음
- 화이트리스트로 바꾸려면 → 순서 번호 **32764에 모두 허용 규칙을 추가**하고, 앞쪽 순서 번호로 허용 규칙을 관리

**NHN Cloud 인터넷 포트 차단 정책(inbound)** — 침입 차단 시스템, 모두 **네트워크 ACL 차단 적용 / 외부에서 접속 불가**
| 클라우드 | 리전 | 서비스명 | 차단 포트 |
|---|---|---|---|
| 민간 | 한국(판교/평촌), 일본(도쿄) | 시스템 터미널 포트 | **TCP/23** |
| 공공 | 한국(판교/평촌) | 시스템 터미널 포트 | **TCP/22, 23, 3389** |
| 공공 | 한국(판교/평촌) | DBMS 포트 | TCP,UDP/**1433(MS-SQL), 1521(Oracle), 3306(MySQL)** |
| 공공 | 한국(판교/평촌) | Netbios 관련 포트 | TCP,UDP/**135, 137, 138, 139, 445** |
| 공공 | 한국(판교/평촌) | 기타 | **TCP/21(FTP), TCP/5900(VNC)** |

## 10. Default Network

- 기본 인프라 서비스를 활성화하면 **각 리전마다 기본적으로 생성**되는 VPC 네트워크 환경
- 네트워크 환경을 필요로 하는 서비스를 **별도의 네트워크 구성 없이 바로 사용** 가능

| 구성 요소 | 내용 |
|---|---|
| VPC | 이름 **Default Network**, Private IP Range **192.168.0.0/16** |
| 서브넷 | 이름 **Default Network**, Private IP Range **192.168.0.0/24** |
| 라우팅 | 기본 라우팅 테이블 + **Internet Gateway 연결된 상태** |
| Security Groups | 이름 **default** — 규칙: **자기 자신을 원격 소스로 하는 임의(모든) 수신 트래픽 허용** |

- **기능 검증용(테스트)으로 사용하는 것을 권장** ⭐

## 11. NAT Gateway

- **프라이빗 서브넷에 위치한 인스턴스들이 Outbound 인터넷 액세스**를 가능하게 하는 서비스
- 프라이빗 서브넷의 인스턴스들은 외부 인터넷 액세스는 가능하나 **인터넷에서 해당 인스턴스에 액세스할 수 없음** (단방향)
- **퍼블릭 서브넷에 위치**해야 하며 **Floating IP 1개를 연결한 후 라우팅 테이블을 설정** ⭐
- 라우팅 규칙: 목적지 CIDR에 **`0.0.0.0/0`**(Anywhere) 입력 + 게이트웨이 타입/이름을 NAT Gateway로 설정
- **시간당 비용 발생** ⭐
- 쿼터: 프로젝트당 **3개**
- 용도 예: 패키지·소프트웨어 업데이트, 외부 구성 요소와의 상호작용

---

## 12. Service Gateway

- VPC에서 **인터넷을 경유하지 않고** VPC 외부의 NHN Cloud 서비스를 이용할 수 있게 해주는 서비스
- 생성 시 **선택된 서비스와 자동으로 할당된 IP가 1:1 연결 관계로 생성**
- ⭐ **Service Gateway의 비용은 무료**
- 쿼터: 프로젝트당 **10개**

**지원 서비스** ⭐암기
- Server Security Check / **Object Storage** / **CloudTrail** / IaaS API Identity / **NHN Container Registry(NCR)** / API Gateway / Log & Crash Search 등

> 💡 기출 7번 정답 유형: "인터넷 연결 없이 프라이빗 서브넷에서 Object Storage에 파일 저장" → **Service Gateway** (NAT Gateway 아님)

## 13. 다중 VPC 설계

- VPC는 독립된 네트워크 환경 → **한 프로젝트 내에 격리된 네트워크 구성이 필요하면 다중 VPC** 구성
- 격리 기준: **환경별**(개발/테스트/운영), **애플리케이션·워크로드별**, 공용 서비스
- VPC는 기본적으로 **서로 통신이 불가능한 상태**로 생성 → 필요 시 **Peering을 통해 상호 통신**
- **기본적으로 프로젝트마다 VPC는 3개까지 생성 가능**, 필요 시 쿼터 조정 신청

---

## 14. Peering Gateway

- **격리된 VPC 간의 연결**을 통해 네트워크 통신을 가능하게 하는 서비스
- 생성 후 **라우팅 테이블 설정 필요** (상대 VPC를 향하는 트래픽의 경로 지정 — 상대 VPC 대역의 목적지 CIDR, 게이트웨이 타입/이름)
- ⭐ **VPC 간의 Private IP 범위가 겹치면 안 됨**
- ⭐ **하나의 Peering마다 1:1로만** VPC 간 상호 연결
- **다른 리전**에 있는 VPC와의 피어링(**리전 피어링**)과 **다른 프로젝트**에 있는 VPC 간 연결(**프로젝트 피어링**) 지원
- ⭐ **Peering Gateway 비용은 무료** (네트워크 트래픽 비용은 별도 청구)
- 쿼터: 리전 피어링 프로젝트당 10개 / 프로젝트 피어링 프로젝트당 10개

**연결 복잡도 공식** ⭐숫자 암기
- **VPC N개를 모두 상호 연결 시 연결 수 = N(N-1)/2**

| VPC 개수 | 1 | 2 | 3 | 4 | 5 | N |
|---|---|---|---|---|---|---|
| 연결 수 | 0 | 1 | 3 | **6** | **10** | **N(N-1)/2** |

- A, B, C 3개 피어링 시: A-B, A-C를 했다고 해서 **B-C가 자동 연결되지 않음** (전이적 피어링 미지원) ⭐
- 복잡도 증가 방지 → **꼭 필요한 VPC 간에만 연결** 권장

---

## 15. Transit Hub

- **중앙 허브 역할**을 하는 **단일 게이트웨이**를 통해 여러 개의 VPC를 **중앙 집중식으로 연결**
- 복잡하게 연결된 피어링 관계를 제거하고 **중앙 집중식으로 네트워크를 간소화**
- **라우터 역할을 수행하며 VPC 간 통신 경로를 관리**할 수 있음

**주요 개념**
| 용어 | 설명 |
|---|---|
| Transit Hub | 중앙 집중식 연결을 관리하는 **최상위 리소스** |
| **Attachment(연결)** | Transit Hub와 연결되는 리소스. **현재는 VPC만 제공** ⭐ |
| Transit Hub 라우팅 테이블 | 라우팅 연결 - Attachment와의 연결 / 라우팅 전파 - 연결된 리소스의 CIDR 값을 얻어와 자동으로 라우팅 룰 생성 / 라우팅 룰 - 목적지 CIDR과 패킷의 전달할 연결을 지정하는 방식으로 정적 라우팅 설정 |

**주요 기능**
- 여러 개의 VPC를 연결
- 연결된 VPC 간 **라우팅 설정** 제공
- 연결된 VPC 간 **멀티캐스트 통신** 제공 (멀티캐스트 그룹을 생성하고 트래픽의 수신자를 설정)
- 조직 내의 다른 프로젝트의 **트랜짓 허브를 공유**받을 수 있음 (대상 프로젝트의 태그 ID 입력 → 다른 프로젝트의 VPC와도 중앙 집중식 연결 가능)
- **리전별 지원이 상이하므로 사전 확인 후 적용 권장** ⭐

## 16. Flow Log

- 사용자의 **네트워크 인터페이스로 들어오고 나가는 패킷을 분석하여 통계를 제공**
- 네트워크 인터페이스로 오가는 **패킷들의 헤더를 검사** → VPC, Subnet, 네트워크 인터페이스 단위로 생성
- **5-tuple을 기준으로 집계**: **출발지 IP/Port, 목적지 IP/Port, 프로토콜** ⭐
- 사용자가 설정한 **수집 간격(분 단위)** 마다 **Object Storage에 파일이 생성**되며, 이 파일로 통계 확인
- 통계를 확인하여 **Security Groups의 올바른 설정 여부, 외부 침입 시도 등**을 확인
- 수집 간격을 짧게 설정할 경우 **실제로는 다른 연결이지만 같은 5-tuple로 수집될 수 있음** → 상황에 맞는 **적절한 수집 간격 설정 필요** ⭐

## 17. Traffic Mirroring

- 인스턴스 네트워크 패킷을 **캡처하여 콘텐츠 보안, 위협 분석, 트러블 슈팅** 등에 활용

| 구성 요소 | 설명 |
|---|---|
| **미러 세션** | 미러 소스와 대상 소스를 **미러 세션 단위로 연결**. 필터 그룹을 지정해야 트래픽 미러링 가능 |
| **미러 소스** | 네트워크 패킷을 모니터링할 네트워크 인터페이스. **인스턴스의 네트워크 인터페이스만 지원** |
| **미러 대상** | 미러 소스에서 복사한 네트워크 패킷을 전달받는 네트워크 인터페이스. **미러 대상 포트로 지정된 네트워크 인터페이스는 통신이 불가**. 필요 시 통신용 네트워크 인터페이스 추가 필요 ⭐ |
| **미러 방향** | 미러링 할 패킷의 방향을 **인바운드, 아웃바운드**로 설정 |
| **미러 필터** | 필터를 통해 원하는 특정 네트워크 패킷만 미러링. **프로토콜, 소스 및 대상 포트의 범위, 소스 및 대상 CIDR 블록**을 지정 |

- 서비스 대상: 네트워크의 트래픽을 캡처하여 원하는 **감지 도구로 라우팅**하려는 경우 / 테스트 및 문제 해결을 위해 애플리케이션 트래픽 미러링이 필요한 경우

## 18. Colocation Gateway

- NHN Cloud와 **온프레미스 환경의 네트워크**를 **하이브리드로 연결**
- 하이브리드 서비스를 이용하는 경우 **NHN Cloud Zone**이 제공됨
- **NHN Cloud Zone**: 고객의 네트워크 환경과 연결된 리소스
- Colocation Gateway를 생성하여 VPC와 NHN Cloud Zone을 연결
- 지원 리전: **한국(판교), 한국(평촌)** ⭐ (점차 다른 리전도 제공 예정)
- ⭐ **Colocation Gateway 비용은 무료**

**주의사항**
- Colocation Gateway 생성 시 사전 등록된 VPC만 온프레미스 네트워크로 연결할 수 있음
- 온프레미스 네트워크와 통신을 원하는 VPC는 Colocation Gateway 생성 전에 반드시 NHN Cloud 고객 센터에 문의 필요
- ⭐ **NHN Cloud 리전 간의 통신은 불가능**하지만, 같은 NHN Cloud Zone에 연결된 다른 VPC와의 통신은 가능

## 19. Direct Connect

- 온프레미스 환경과 클라우드 서비스 간의 **전용 회선**을 통해 빠르고 일관된 성능으로 데이터를 전송
- 인터넷을 경유하지 않으므로 **보안상 더 안전**

**사양** ⭐숫자 암기
| 지원 항목 | 사양 |
|---|---|
| 리전 | **한국(판교), 한국(평촌)** |
| 대역폭 | **10Mbps ~ 10Gbps** |
| 회선 타입 | **이더넷(Ethernet) 방식** |
| 통신 방식 | **L2(Vlan), L3(BGP, Static, IPsec)** |
| 연결 방식 1 | **전용 연결** — 회선 사업자를 통한 전용 회선 연결 방식. **KT, LG U+, SK브로드밴드, 드림라인, 세종텔레콤** 중 선택 (NHN Cloud에서 회선 계약 및 개통 진행) |
| 연결 방식 2 | **호스팅 연결** — N/W 파트너를 통한 클라우드 플랫폼 연결 방식. **KINX 클라우드 허브 / LG U+ 클라우드 멀티커넥트 / 드림라인 클라우드 익스체인지 플랫폼** |

- **전용 연결**은 NHN Cloud 위치 내 Direct Connect 네트워크 포트 및 사용자의 네트워크 포트 간 **물리적 연결**
- **호스팅 연결**은 Direct Connect 제공 파트너의 네트워크 환경을 통해 프로비저닝하여 연결되는 **논리적(VLAN) 연결**
- L2, L3 기반 VLAN, BGP 등 다양한 통신 프로토콜 지원

## 20. VPN Gateway (Site-to-Site VPN)

- VPC와 고객의 온프레미스 네트워크 사이에 **암호화된 네트워크 연결**을 제공. **IPsec 암호화 지원**

**주요 기능** ⭐숫자 암기
| 항목 | 값 |
|---|---|
| 대역폭 (outbound 기준 보장) | **20M, 50M, 100M, 1G** 중 선택 |
| 암호화 알고리즘 | **AES, DES, 3DES** 중 선택 |
| 무결성 알고리즘 | **MD5, SHA1, SHA256** 중 선택 |
| Network ACL | **적용 가능** ⭐ |

**제한 사항** ⭐⭐출제 포인트
- VPN 연결에는 **IPv6 트래픽이 지원되지 않음. IPv4만 지원**
- VPC를 온프레미스 네트워크에 연결하는 경우 **서로 네트워크 주소가 겹치지 않는 대역** 사용
- **VPC 단위로 VPN Gateway를 생성**하며 대역폭을 정함. **하나의 VPN Gateway에 속한 VPN 연결은 모두 같은 대역폭을 사용**
  - 예) 최초 VPN 연결을 20Mbps로 생성했다면 해당 VPC에서 이후 추가 생성하는 VPN 연결은 모두 20Mbps. 다른 대역폭을 쓰려면 **다른 VPC에서 최초 VPN 연결 생성 시 지정**
- **VPN Gateway는 각 VPC마다 한 개씩만** 생성 가능
- **각 VPN Gateway당 최대 연결은 10개**
- **VPN과 연결된 VPC에서는 피어링을 사용해 다른 네트워크에 접근하거나, 기타 Gateway를 통해 다른 네트워크 혹은 서비스에 접근하는 것을 지원하지 않음** ⭐
- 쿼터: VPN 게이트웨이 프로젝트당 **3개(조정 불가)**, VPN 게이트웨이(S2S) 연결 프로젝트당 **30개(조정 불가)**

## 21. DNS Plus

- 전 세계 사용자들이 안정적이고 빠르게 접속할 수 있는 **DNS(Domain Name System)** 서비스
- **별도의 DNS 서버를 설치하지 않고 웹 콘솔에서 바로 DNS 작업 가능**
- **대규모 DNS 질의를 받을 수 있도록 설계**
- **DNS를 대상으로 하는 DDoS 공격 완화** (서비스 중단을 목적으로 대량의 트래픽을 대상 서버 또는 공격 대상에게 발생시키는 공격)
- ⭐ **도메인은 판매하고 있지 않음** (등록 대행 서비스가 아님)

### GSLB (Global Server Load Balancing)
- **DNS 기반으로 엔드포인트에 안정적으로 트래픽을 로드밸런싱**해주는 서비스
- **HTTP / HTTPS / TCP** 프로토콜로 엔드포인트의 **헬스 체크** 기능을 지원
- 현재와 다른 리전 또는 다른 로케이션에 서비스를 구성하여 **DR(Disaster Recovery)** 형태의 서비스 구성에 용이

**라우팅 규칙 — 3가지뿐** ⭐⭐최다 출제
| 라우팅 규칙 | 설명 |
|---|---|
| **FAILOVER** | GSLB 도메인에 연결된 Pool의 **우선순위로 라우팅**. 엔드포인트 헬스체크 기능을 이용하여 Failover 라우팅 |
| **RANDOM** | GSLB 도메인에 연결된 Pool 중 **사용 가능한 Pool을 무작위**로 라우팅 |
| **GEOLOCATION** | **설정된 지역**의 트래픽을 해당 연결된 Pool로 라우팅 |

> ⚠️ **ROUND ROBIN(순차 전달)은 NHN Cloud GSLB의 라우팅 규칙이 아님** — 기출 6번 정답

- GEOLOCATION 지원 지역: Western/Eastern North America, Western/Eastern Europe, Northern/Southern South America, Oceania, Middle East, Northern/Southern Africa, India, Southeast Asia, Northeast Asia

### Private DNS
- 별도의 DNS 솔루션이나 서버 없이 웹 콘솔 설정으로 **VPC 내의 인스턴스에서 접근 가능한 DNS** 서비스
- 개인이나 회사 소유의 **내부 네트워크 내에서** 도메인 네임 시스템을 자체적으로 관리·운영
- **공공 DNS 서비스와 달리 내부 네트워크에서만 사용**되며 **외부에서는 접근 불가**

| 특징 | 내용 |
|---|---|
| 생성 | VPC별로 독립된 DNS를 구성할 수 있음 |
| 연결 | **하나의 Zone(도메인 영역)에 한 개 이상의 VPC 연결** |
| 요청 범위 | **Zone 외부에서 요청하는 경우 응답을 받을 수 없음** |
| 외부 도메인 | VPC 내의 인스턴스는 **외부 등록기관을 통해 등록된 도메인에 대한 요청에도 응답을 받을 수 있음** |
| Private DNS 사용 시 | **VPC에는 프라이빗 IP 도메인 정보로 접근 가능** |
| hosts 파일 | **Service Gateway 연계 시 운영체제 hosts 파일 변경 불필요** ⭐ |

- 장점: 내부 네트워크에서 사용되기 때문에 **외부로부터의 DNS 공격을 방지**할 수 있고, 외부 DNS 서버를 거치지 않고 내부에서 직접 처리하므로 **DNS 요청에 대한 응답 시간이 빠름**
- 활용: 기업 인트라넷(그룹웨어, 파일 서버 등), 개발/테스트 환경에서 특정 도메인 사용, 마이크로서비스 아키텍처에서 서비스 간 도메인 식별

## 22. VPC 설계 고려사항 ⭐설계형 문제 근거

- 단일 VPC, 다중 VPC, 다중 프로젝트 고려
- **프로젝트 생성 전 VPC 네트워크 설계 고려** (나중에 네트워크 변경 = 리소스 변경 → 문제 발생)
- **VPC 및 관련 서비스 쿼터 확인** (VPC 3개, 인터넷 게이트웨이, 서브넷, 라우팅 테이블 등)
- **VPC 네트워크 토폴로지를 단순하게**
- 식별할 수 있는 이름 사용: 회사명, 비즈니스, 애플리케이션 코드, 리전 등
- 애플리케이션 유형이 같을 경우 **큰 IP 주소 범위를 사용하여 적은 수의 서브넷** 사용
- ⭐ **퍼블릭보다는 프라이빗의 범위를 더 크게 잡는 것이 유리**, **최소한의 리소스만 퍼블릭에 위치** (웹서버, External LB, NAT GW)
- 하이브리드 환경 고려: **Colocation Gateway, Site to Site VPN** 등
- **외부 통신이 필요한 서비스만 인터넷 게이트웨이 연결**
- **Hub - Spoke 구조에서는 Transit Hub나 Network Firewall 사용 고려**

## 26. 자주 나오는 함정 포인트 ⭐⭐

1. **Floating IP는 인스턴스 삭제 시 "선택 사항"** — 무조건 함께 삭제되지 **않음** (기출 4번)
2. **Floating IP는 연결하지 않아도 생성 즉시 과금** — "연결 여부와 관계없이"
3. **GSLB 라우팅 규칙은 FAILOVER / RANDOM / GEOLOCATION 3가지뿐** — **ROUND ROBIN 없음** (기출 6번)
4. **프라이빗 서브넷 → Object Storage 인터넷 없이 접근 = Service Gateway** (NAT Gateway 아님, NAT는 인터넷 아웃바운드용) (기출 7번)
5. **Security Groups = Stateful / Network ACL = Stateless** — ACL은 인/아웃 양방향 규칙을 모두 써야 함
6. **Security Groups는 허용(Allow) 규칙만, Network ACL은 허용+차단 모두**
7. **Network ACL은 순서 번호가 작을수록 우선**, 1~100은 예약, 101 허용 / 32765 차단이 기본, **32765는 삭제 불가**
8. **Network ACL은 생성 후 VPC와 바인딩** (Security Groups는 Network Interface에 바인딩)
9. **서브넷 IP 범위는 생성 후 수정 불가**, 최소 크기 **/28**
10. **서브넷당 4~5개 IP 예약** (.0 네트워크, .255 브로드캐스트, .1 게이트웨이, .2 DHCP, .3 인터넷 게이트웨이(옵션))
11. **Peering은 1:1만, 전이적 연결 안 됨** → N개 완전 연결 시 **N(N-1)/2**
12. **Peering은 Private IP 범위가 겹치면 불가**
13. **VPN Gateway는 VPC당 1개**, 게이트웨이당 **연결 10개**, **IPv6 미지원**
14. **VPN 연결된 VPC에서는 Peering·기타 Gateway를 통한 다른 네트워크 접근 미지원**
15. **명시적 연결이 생기면 기본 라우팅 테이블 규칙을 더 이상 따르지 않음**. **새 서브넷은 항상 기본 라우팅 테이블에 암시적 연결**
16. **Internet Gateway는 무료**지만 **NAT Gateway는 유료** — 헷갈리기 쉬움
17. **NAT Gateway는 퍼블릭 서브넷에 위치 + Floating IP 1개 필요**
18. **Transit Hub의 Attachment는 현재 VPC만 지원**, **리전별 지원 상이**
19. **Flow Log는 5-tuple 기준, Object Storage에 파일로 저장** — 수집 간격이 짧으면 다른 연결이 같은 5-tuple로 집계될 수 있음
20. **Traffic Mirroring의 미러 대상 포트로 지정된 네트워크 인터페이스는 통신 불가** → 별도 통신용 인터페이스 필요
21. **Colocation Gateway는 NHN Cloud 리전 간 통신 불가** / 한국(판교·평촌)만 지원 / 사전 등록 VPC만 연결
22. **Direct Connect는 한국(판교·평촌)만, 10Mbps~10Gbps**
23. **DNS Plus는 도메인을 판매하지 않음**
24. **Default Network는 192.168.0.0/16(VPC) + 192.168.0.0/24(Subnet)**, 테스트·기능 검증용 권장
25. **`0.0.0.0/0` = Anywhere**, `/32` = 단일 IP
26. **공공 클라우드는 22, 23, 3389 차단 / 민간 클라우드는 23만 차단** (시스템 터미널 포트)
