# PART A. Enhance the Architecture (Ch5)

## 1. 3-Tier 아키텍처

| 계층 | 다른 이름 | 역할 | 대표 소프트웨어 |
|---|---|---|---|
| **Presentation Layer** | Web Tier, Front-End, **프레젠테이션 티어** | 사용자와 직접 상호작용, UI·정적 컨텐츠 제공. 웹 브라우저에서 실행되는 클라이언트 측 코드(HTML/CSS/JavaScript) 포함 | **Apache HTTP Server, Nginx** |
| **Business Logic Layer** | WAS Tier, Back-End, **애플리케이션 티어** | 비즈니스 로직 수행. 클라이언트 요청을 실제 처리하고 데이터를 **CRUD**(생성·조회·업데이트·삭제)하는 코드 포함. 동적 컨텐츠 제공 | **Apache Tomcat Server, WildFly** |
| **Data Layer** | Database Tier | 로직 처리 결과로 생성·수정·삭제되는 데이터를 관리 | RDBMS 등 |

## 2. Tier 통합 vs 분리 ⭐출제

| 구분 | WEB/APP **통합** | WEB/APP **분리** |
|---|---|---|
| 장점 1 | **단순성** — 개발이 단순해지고 네트워크 설정이 단순화 | **확장성** — 각 티어를 독립적으로 확장 |
| 장점 2 | **성능 향상** — 네트워크 지연, 데이터 전송에 따른 **오버헤드 감소** | **보안** — 웹 티어만 노출, App Server는 내부 네트워크에서만 접근 가능하도록 설정 |
| 장점 3 | **유지보수 용이** — 보다 적은 관리 대상 | **독립성** — 독립적으로 유지 보수, 빠른 개선 |
| 배치 | WEB/APP이 하나의 Subnet(Public Network) | WEB=Web Subnet(Public), APP=App Subnet(Private), DB=DB Subnet(Private) |

- 통합이 무조건 나쁜 게 아니다 → **애플리케이션 규모가 커지고 사용자 수가 늘어나고 기능이 복잡해질 때** 분리를 검토
- 성능(오버헤드)만 보면 **통합이 유리**, 확장성·보안만 보면 **분리가 유리** → 트레이드오프

## 3. 결합도(Coupling) ⭐개념 비교

| 구분 | 밀접한 결합 (Tight Coupling) | 느슨한 결합 (Loose Coupling) |
|---|---|---|
| 의존성 | 모듈 간 의존성이 **높은** 상태 | 모듈 간 의존성이 **낮은** 상태 |
| 변경 영향 | 한 모듈이 변경되면 다른 모듈도 **변경해야 할 가능성 높음** | 한 모듈이 변경돼도 다른 모듈에 미치는 **영향이 최소화** |
| 결과 | 유지보수 어려움, 테스트 어려움, **확장성 떨어짐** | 독립적 개발·테스트 가능. **유연성과 확장성 증가** |
| 대응 아키텍처 | **Synchronous(동기식)** | **Asynchronous(비동기식)** |
| 장애 전파 | 한 모듈에 장애 발생 시 **전체에 영향** | 지연이 발생해도 **전체에 영향 없음** |

- **결합**의 정의: 애플리케이션의 각 구성 요소가 서로에 대한 종속성을 측정하는 것
- ⚠️ **밀접한 결합과 느슨한 결합은 상대적 개념** — 절대적 이분법이 아니다
- **느슨한 결합의 3가지 방향** ⭐암기
  1. **Load Balancing**을 이용한 아키텍처
  2. **메시지 대기열(Queue)**을 이용한 아키텍처 = 비동기식 아키텍처
  3. **마이크로서비스** 아키텍처

## 4. 클라우드에서의 컴퓨팅 리소스

- On-Premise 서버: 초기 준비에 **비용과 시간** 필요 / 문제 해결에도 **긴 시간** 소요
- 클라우드 인스턴스 3대 특성: **짧은 시간 안에 구동 / 재사용 가능(다른 VPC로) / 필요할 때마다 증설·축소 가능**
- 핵심 문장: "인스턴스는 유연하고 신속하게 준비될 수 있도록 관리가 필요합니다."

## 5. 스케일 개념 ⭐출제

| 구분 | 방식 | 설명 | 예시 |
|---|---|---|---|
| **Scale Up/Down** | **수직 확장(Vertical Scaling)** | 인스턴스 자체의 사양 변경 | 1vCPU/2GB → **3vCPU/6GB** |
| **Scale Out/In** | **수평 확장(Horizontal Scaling)** | 인스턴스 개수를 늘리거나 줄임 | 1vCPU/2GB 1대 → **1vCPU/2GB 3대** |

> ⚠️ **Auto Scale은 새로운 인스턴스를 추가·삭제하는 확장/축소 방식(Scale Out/In)을 사용한다.** Scale Up/Down이 아니다. — 대표 함정

## 6. Auto Scale

**정의** — 인스턴스의 부하를 지속적으로 모니터링하여 필요한 경우 인스턴스를 추가로 생성하거나 삭제. **스케일링 그룹을 생성하여 동작**하게 함.

**구성 요소 (예시값)**

| 항목 | 예시 |
|---|---|
| Instance Template | 스케일링 그룹이 사용할 인스턴스 템플릿(원본) |
| 최소 인스턴스 | 1 |
| 최대 인스턴스 | 3 |
| 구동 인스턴스 | 1 |
| 증설 정책 / 감축 정책 | 예: **CPU 사용률이 50% 이상 5분 동안 지속 시** |
| 판단 기준 | **스케일링 그룹 내 인스턴스의 평균값**을 체크 |

> ⭐ **축소 시 가장 오래된(가장 먼저 만들어진) 인스턴스부터 삭제된다.** — 최신 인스턴스부터가 아니다. 대표 함정

**Auto Scale의 비용 효과** — On-prem은 확장성이 없어 피크 기준으로 고정 용량을 잡아야 하고, 그 차이만큼이 **낭비되는 용량(클라우드에서의 비용)**. Auto Scale은 사용량 곡선을 따라가므로 낭비 영역이 줄어든다.

## 7. Auto Scale에 적합한 세션 관리 ⭐핵심 출제

| 구분 | Stateful Architecture | Stateless Architecture |
|---|---|---|
| 세션 저장 위치 | **서버(인스턴스) 내부**에 이전 요청 및 사용자 상태 정보 저장·활용 | **서버 내에 저장하지 않음**. 세션 정보를 서버 외부(**DB, Cache**)에 별도 저장 |
| 조회 | 서버 로컬 | 요청 시 **외부 저장소에서 실시간 조회** |
| 세션 분산 기법 | ① **세션 복제(Replication)**: 서버 간 세션 정보를 실시간 공유·복사<br>② **세션 지속성(Persistence)**: 특정 사용자를 **항상 동일한 서버로 라우팅** | 불필요 |
| Auto Scaling 한계/장점 | **한계** — 인스턴스 증감 시 **동기화 부하** 발생 및 **초기 구동 지연**. 기존 세션 유지로 인해 **신규 인스턴스로의 트래픽 분산 제약** | **장점** — ① **서버 독립성**: 모든 서버가 동일한 세션 정보에 접근 가능 ② **확장 용이성(Scalability)**: 인스턴스 확장 및 Auto Scaling에 최적화 |

> Stateless는 인스턴스가 추가로 확장되는 데 **추가적인 작업이 필요 없고**, 원래 인스턴스의 상태 그대로 변경 없이 구동하면 되므로 Auto Scale에 유리하다.

## 8. Auto Scale에서 인스턴스 준비 — 이미지 vs 사용자 스크립트 ⭐

인스턴스 구성요소를 아래에서 위로: **OS → 네트워크 → 패키지 → 유틸리티 → 런타임 → 라이브러리 → 프레임워크 → 웹서버 → 코드 배포 → 모니터링**
어느 지점까지를 **Image**로 굽고, 어디부터를 **User Script**로 처리할지가 설계 포인트.

| 구분 | Image | User Script |
|---|---|---|
| 시점 | 인스턴스 **생성 시간**에 포함 | 인스턴스 **생성 이후** 실행 |
| 소요 시간 성격 | **고정된 시간(정적)** | **유동적인 시간(동적)** |
| 장점 | 준비되는 데 보다 **적은 시간 소요** | 시간 소요가 크지만 사용자가 **제어 가능**. 변경사항 발생해도 스크립트를 그대로 유지하거나 변경하여 관리 가능 |
| 단점 | **유연성이 낮음**. 변경사항 발생 때마다 **새로운 이미지 생성 → 관리 포인트 증가** | 수행되는 데 시간이 걸림 → 원하는 상태 도달까지 **추가적인 시간 소모** |
| 방향성 | Image 비중↑ = **안정성 증가, 관리포인트 증가** | User Script 비중↑ = **유연성 증가** |

> ⭐ **이미지의 비율이 증가할수록 Auto Scale에 일반적으로 유리하다.** 단, **두 요소 사이의 균형을 고려**해야 한다.
> 총 소요 시간 = 인스턴스 생성 시간(고정) + 사용자 스크립트 수행 시간(유동)

## 9. Auto Scale에서의 스케일링 정책 (4원칙) ⭐

| 원칙 | 이유 |
|---|---|
| **확장은 미리, 축소는 천천히** | 인스턴스 확장은 시간이 걸리나 인스턴스 축소는 **즉각적**이기 때문 |
| **재사용 대기 시간을 이용** | 급격한 확장·축소(플래핑) 방지 |
| **모니터링 지표는 여러 개 사용** | CPU 32%/Memory 98%, Memory 43%/CPU 99% 처럼 **한 가지 지표만으로는 인스턴스 상태 파악이 어려움** → **2개 이상의 지표** 사용 |
| **예상되는 이벤트에는 예약 스케일링 사용** | 동적 스케일링으로는 이벤트로 인한 **급격한 수요 증가를 대비하기 어려움** (예: 10시 이벤트) |

## 10. 비용을 고려한 Auto Scale ⭐숫자 출제

| 인스턴스 타입 | 단가 | 10시간 비용 계산 | 한달 예상 비용 |
|---|---|---|---|
| **m2.c8m16** (적은 수의 큰 인스턴스) | **399원/시간** | 399 × 14 = **5,586원** | **397,872원** |
| **m2.c2m4** (많은 수의 작은 인스턴스) | **93원/시간** | 93 × 35 = **3,255원** | **234,360원** |
| **절감** | — | — | **163,512원 (약 41% 절감)** |

**인스턴스 사이즈 선정 3원칙**
1. **비용만** 고려한다면 인스턴스의 사이즈를 **작게** 가져가는 것이 유리
2. 다만 **인스턴스 준비 시간이 길어진다면** 오히려 **서비스 가용성 측면에서 불리**
3. 인스턴스 수 증가로 **오버헤드 되는 자원 사용량**과 **최소 자원 크기**를 고려하여 사이즈 선정

## 11. Auto Scale 고려사항 (총정리) ⭐암기

1. 애플리케이션을 **Stateless**로 구성하여 확장에 용이하도록
2. 빠른 기동을 위해 구성 컴포넌트 중 **이미지로 구성되는 비중을 높이되 유연성도 함께 고려**
3. 안정적인 서비스 운영을 위해 스케일링 정책을 **미리 확장하고 나중에 축소**하도록 고려 (축소 시 **가장 먼저 만들어진 인스턴스 먼저 삭제**)
4. **2개 이상의 지표**를 사용하여 스케일링
5. 필요하다면 동적 스케일링이 아니라 **예약된 스케일링** 사용
6. 인스턴스 비용과 **오버헤드 비용**을 고려하여 적절한 인스턴스 사이즈 선정

## 13. 클라우드에서의 캐시 전략

- 캐시 도입은 **투자 비용 대비 높은 효과**를 기대할 수 있는 전략
- 캐시는 **이전 티어의 요청 부담을 완화**하여 원본 서버의 부하와 리소스 사용량을 줄임
- 캐시 비용은 추가되지만, **응답 시간 개선을 통해 전체 비용 효율성을 높일 수 있음**

| 위치 | 캐시 | 원본 | 비용 관계 |
|---|---|---|---|
| Client ← **CDN 캐시** ← Server | CDN($$) | Server($$$) | 캐시가 원본보다 저렴 |
| App Server ← **인메모리 캐시** ← Database | Cache($$) | Database($$$) | 캐시가 원본보다 저렴 |

## 14. CDN

전 세계에 분산되어 있는 캐시 서버를 사용하여 사용자에게 빠르게 컨텐츠 제공.

- 사용자에게 **가장 인접한 캐시 서버**를 통해 컨텐츠 전송
- 전 세계에 있는 캐시 서버를 이용하여 **해외 사용자도** 컨텐츠를 빠르게 전송 가능
- **원본**으로 **Object Storage, Instance, 또는 직접 입력한 위치**로 설정 가능 ⭐
- 네트워크 전송량, 컨텐츠 배포 통계 등을 확인 가능
- 이용자 접근을 **허용 또는 제한** 가능
- ⭐ **과금: 이용한 네트워크 전송량에 대해서만 과금**

| **자동 백업** | **매일 백업 스케줄 4회까지 예약 지원**. 백업 **내보내기** 기능으로 **오브젝트 스토리지**로 데이터 전송 가능 |
| **수동 백업** | 특정 시점의 캐시 데이터를 **영구히 저장**. **명시적으로 삭제하지 않는 한 캐시가 삭제되어도 함께 삭제되지 않음** ⭐ |
| 기타 | 성능 모니터링 제공 |

## 16. Caching Strategy — Loading (읽기 전략) ⭐

| 구분 | Eager Loading | Cache-Aside (Lazy Loading) |
|---|---|---|
| 개념 | 데이터를 **미리 캐시에 로드**하여 요청 즉시 사용할 수 있게 하는 전략 | 데이터가 **필요할 때만** 캐시에 로드. 애플리케이션이 데이터를 요청할 때 캐시에 없으면 **DB에서 가져와 캐시에 저장** |
| 장점 | 데이터 요청 시 **빠른 응답 시간** 제공 | 불필요한 데이터를 캐시에 저장하지 않아 **자원을 효율적으로 사용** |
| 단점 | 사용되지 않는 데이터까지 미리 로드하므로 **자원 낭비** 가능 | **캐시 미스 발생 시 지연**이 발생할 수 있음 |

## 17. Caching Strategy — Write (쓰기 전략) ⭐

| 구분 | Write Through | Write Around |
|---|---|---|
| 개념 | DB에 데이터를 쓸 때마다 **캐시에도 즉시** 데이터를 추가하거나 업데이트 | 모든 데이터는 **DB에 저장**되고 **읽은 데이터만 캐시에 저장** |
| 장점 | 캐시에 있는 데이터가 **항상 최신 상태** | **쓰기 지연이 없음**. 데이터가 **곧바로 읽힐 가능성이 낮은 경우** 유용 |
| 단점 | 사용되지 않는 데이터까지 캐시에 로딩되므로 **자원 낭비** 가능 | **처음 읽을 때 지연** 발생 |

> 함정 정리: "자원 낭비"는 **Eager Loading**과 **Write Through**의 단점. "지연 발생"은 **Cache-Aside**(캐시 미스 시)와 **Write Around**(첫 읽기 시)의 단점.

# PART B. Infrastructure as Code (Ch10)

## 19. IaC 개념

**코드로 서버, 네트워크, 가상 머신 등의 IT 인프라를 자동화하여 구성하고 관리하는 방법.** 소프트웨어 개발처럼 인프라도 **하나의 소스 코드로 취급**하여 관리.

**IaC 적용 영역** — 서버 구성 → 네트워크 설정 → 스토리지 관리 → 소프트웨어 업데이트 → 백업·복구 → 환경 복제 → 모니터링·로깅 → 변경 관리

**IaC 핵심 이점 5가지** ⭐암기: **자동화 / 효율성 / 재사용 / 버전 관리 / 오류감소**

## 20. IaC Tools 분류 ⭐출제

| 범주 | 도구 | 목적 |
|---|---|---|
| **구성 관리** | **Ansible, Puppet, Chef, SaltStack** | 소프트웨어 설치 및 운영 시스템 설정과 같은 **서버의 구성을 관리** |
| **프로비저닝** | **Terraform, AWS CloudFormation, Azure Bicep, Azure Resource Manager** | 클라우드 환경에서 **리소스의 프로비저닝과 관리를 자동화** |

> 함정: Ansible/Chef를 프로비저닝 도구로, Terraform을 구성 관리 도구로 바꿔 놓는 문제 주의.

## 21. Terraform

**HashiCorp이 개발한 오픈 소스 IaC 도구.** 인프라 리소스의 생성, 변경 및 관리를 자동화. **선언적 코드**를 사용하여 인프라를 구축하고, 이를 **버전 관리 시스템에 저장**하여 협업과 변경 관리를 용이하게 함.

**Terraform 특징 6가지** ⭐: **선언적 코드 / 상태 관리 / 코드로 인프라 관리 / Plan & Apply 분리 / 모듈화 / 멀티 클라우드 호환성**

## 22. Terraform 동작 방식 — 3단계 ⭐순서 출제

| 순서 | 단계 | 설명 | 산출물 |
|---|---|---|---|
| 1 | **Write** | 인프라에 대한 구성을 정의하는 테라폼 파일을 생성하고 **관리할 리소스의 속성과 설정을 명시** | Terraform Configuration, Terraform State File |
| 2 | **Plan** | **현재 관리 중인 인프라와 작성한 코드 간의 차이를 출력**하여, 실제 적용 전에 변경사항을 검토할 수 있는 기회를 제공 | 변경 계획 |
| 3 | **Apply** | plan 단계에서 검토한 변경사항을 **실제 인프라에 적용** | 인프라 프로비저닝 + state file 업데이트 |

## 23. HCL (HashiCorp Configuration Language)

- HashiCorp이 개발한 **구성 언어**
- **JSON과 유사하지만 더 직관적이고 간결**
- **Key-Value 형식의 속성 정의**와 **블록 구조**를 통해 인프라 구성을 명확하게 표현

## 24. Terraform 주요 구성 요소 ⭐

| 요소 | 정의 | 예시 코드 |
|---|---|---|
| **provider** | Terraform이 클라우드나 외부 서비스를 관리하기 위해 사용하는 **플러그인**. 인증 정보와 서비스별 설정을 정의해 NHN Cloud, AWS, Azure, Kubernetes, GitHub 등과 연동 | `provider "nhncloud" { user_name, tenant_id, password, auth_url, region = "KR1" }` |
| **resource** | Terraform에서 관리하는 **인프라의 기본 단위**. 가상 머신, 네트워크, 데이터베이스 등을 정의. 각 리소스는 **Provider를 통해 생성·관리·삭제** | `resource "nhncloud_networking_vpc_v2" "vpc01" { name, cidrv4 = "10.0.0.0/16" }` |
| **variable** | **파라미터화**를 통해 Terraform 코드의 **재사용성과 유연성**을 높임. 사용자 입력, **기본값(default)** 또는 환경 변수를 통해 값을 정의 | `variable "password" { sensitive = true }` → default 없으면 **항상 입력 필요** |
| **data sources** | **이미 생성된 인프라 리소스**나 Terraform 코드로 만들어진 리소스의 **데이터를 가져오는 데 사용** | `data "nhncloud_networking_vpc_v2" "vpc" { name = "Default Network" }` |
| **output** | Terraform **모듈의 출력값**을 정의. IP 주소나 리소스 ID 같은 정보를 출력하거나 **다른 모듈에서 참조**할 수 있게 함 | `output "vpc_id" { value = module.vpc.vpc_id }` |

- `terraform { required_version = ">= 1.0.0" ... }` 블록으로 버전 및 required_providers 명시

## 25. Terraform 코드 작성 기본 단계 ⭐순서 출제

**Provider 설정 → 리소스 정의 → 변수 정의 → 데이터 소스 정의 → 출력 정의 → 모듈 사용**

| 단계 | 목적 |
|---|---|
| Provider 설정 | 클라우드 서비스 공급자 지정 |
| 리소스 정의 | 인프라 구성 요소를 정의 |
| 변수 정의 | 사용자로부터 값을 받거나, 기본값을 사용 |
| 데이터 소스 정의 | **이미 생성된 리소스 정보를 조회** |
| 출력 정의 | 생성된 인프라의 정보 출력 |
| 모듈 사용 | **반복적으로 사용될 수 있는 구성을 모듈로 정의** |

## 26. NHN Cloud Terraform 지원 범위 — Resources ⭐

Terraform resources를 통해 리소스를 **생성, 수정, 삭제**할 수 있다.

| 분류 | 지원 Resources |
|---|---|
| **Compute** | `nhncloud_compute_instance_v2`, `nhncloud_compute_volume_attach_v2`, `nhncloud_compute_keypair_v2` |
| **Network** | `nhncloud_lb_loadbalancer_v2`, `nhncloud_lb_listener_v2`, `nhncloud_lb_pool_v2`, `nhncloud_lb_member_v2`, `nhncloud_lb_monitor_v2`, `nhncloud_networking_floatingip_v2`, `nhncloud_networking_floatingip_associate_v2`, `nhncloud_networking_port_v2`, `nhncloud_networking_vpc_v2`, `nhncloud_networking_vpcsubnet_v2`, `nhncloud_networking_routingtable_v2`, `nhncloud_networking_secgroup_v2`, `nhncloud_networking_secgroup_rule_v2` |
| **Block Storage** | `nhncloud_blockstorage_volume_v2` |
| **Object Storage** | `nhncloud_objectstorage_container_v1`, `nhncloud_objectstorage_object_v1` |
| **Key manager** | `nhncloud_keymanager_secret_v1`, `nhncloud_keymanager_container_v1` |

> ⭐ **버전 접미사 함정**: Object Storage와 Key manager는 **`_v1`**, 나머지(Compute·Network·Block Storage)는 **`_v2`**.
> ⭐ **RDS, EasyCache, CDN, NAT Gateway, Service Gateway 등은 지원 Resources 목록에 없다.**

## 27. NHN Cloud Terraform 지원 범위 — Data Sources ⭐

- tf 파일 작성에 필요한 **인스턴스 타입 ID, 이미지 ID** 등은 **콘솔에서 확인**하거나, Terraform이 제공하는 **data sources**를 이용하여 가져올 수 있다.
- ⭐ **Data sources는 tf 파일 안에 작성하며 정보는 수정할 수 없고 오직 참조만 가능하다.**
- ⭐ **NHN Cloud는 주기적으로 이미지를 업데이트하므로 이미지 이름이 변경될 수 있다.**

| 분류 | 지원 Data Sources | 용도 |
|---|---|---|
| **Compute** | `nhncloud_compute_flavor_v2`, `nhncloud_compute_keypair_v2` | **인스턴스 타입, 키페어 조회** |
| **Network** | `nhncloud_networking_vpc_v2`, `nhncloud_networking_vpcsubnet_v2`, `nhncloud_networking_routingtable_v2`, `nhncloud_networking_secgroup_v2` | 네트워크 리소스 조회 |
| **Block Storage** | `nhncloud_blockstorage_volume_v2`, `nhncloud_blockstorage_snapshot_v2` | 블록 스토리지 리소스 조회 |
| **Image** | `nhncloud_images_image_v2` | **공용 이미지 또는 개인 이미지 조회** |
| **Key manager** | `nhncloud_keymanager_secret_v1`, `nhncloud_keymanager_container_v1` | 사용자 시크릿 리소스 조회 |

> ⭐ **Resources에는 있으나 Data Sources에는 없는 것**: LB 계열(`nhncloud_lb_*`), Floating IP, Port, Object Storage, secgroup_rule, compute_instance
> ⭐ **Data Sources에만 있는 것**: `nhncloud_compute_flavor_v2`(인스턴스 타입), `nhncloud_images_image_v2`(이미지), `nhncloud_blockstorage_snapshot_v2`(스냅숏)

## 35. 자주 나오는 함정 포인트 ⭐⭐

1. **Auto Scale = Scale Out/In(수평)** — Scale Up/Down(수직)이 아니다. Auto Scale은 인스턴스 사양을 바꾸는 게 아니라 **새 인스턴스를 추가·삭제**한다.
2. **축소 시 가장 먼저 만들어진(오래된) 인스턴스부터 삭제** — "최근 인스턴스부터"는 오답.
3. **"확장은 미리, 축소는 천천히"** — 확장은 시간이 걸리지만 **축소는 즉각적**이기 때문. 반대로 서술한 보기 주의.
4. **모니터링 지표는 2개 이상** — CPU 단일 지표만으로는 상태 파악이 어렵다.
5. **예상되는 이벤트에는 동적 스케일링이 아니라 예약(예정) 스케일링**.
6. **Stateful의 세션 지속성(Persistence)은 Auto Scaling에 불리** — 기존 세션 유지로 **신규 인스턴스로의 트래픽 분산이 제약**된다. "Persistence를 쓰면 Auto Scale에 유리하다"는 오답.
7. **Image 비중↑ = 안정성↑ + 관리포인트↑ / User Script 비중↑ = 유연성↑**. 이미지 비중이 높을수록 Auto Scale에 유리하지만 **균형**이 필요.
8. **Tier 통합의 장점은 단순성·성능·유지보수 용이**, **분리의 장점은 확장성·보안·독립성**. 서로 바꿔 놓는 함정이 잦다. (성능=통합 쪽, 확장성=분리 쪽)
9. **밀접한 결합과 느슨한 결합은 상대적 개념** — 절대적 기준이 아니다.
10. **비용만 고려하면 작은 인스턴스가 유리하지만, 준비 시간이 길면 가용성 측면에서 불리**하다. "작은 인스턴스가 무조건 유리"는 오답.
11. **캐시 전략 단점 매칭**: 자원 낭비 = Eager Loading / Write Through, 지연 = Cache-Aside(캐시 미스) / Write Around(첫 읽기).
12. **Write Around는 쓰기 지연이 없다** — 캐시를 거치지 않고 DB에 직접 쓰기 때문. Write Through와 반대.
13. **CDN 과금은 이용한 네트워크 전송량에 대해서만** 발생. 캐시 서버 대수나 저장 용량 기준이 아니다.
14. **CDN 원본은 Object Storage, Instance, 직접 입력한 위치** 모두 가능.
15. **EasyCache는 Valkey 기반**(Redis 기반이라 하면 오답). 자동 백업은 **매일 4회까지 예약**.
16. **EasyCache 수동 백업은 캐시가 삭제되어도 함께 삭제되지 않는다** — 명시적 삭제 필요.
17. **IaC 도구 분류**: Ansible/Puppet/Chef/SaltStack = **구성 관리**, Terraform/CloudFormation/Bicep/ARM = **프로비저닝**.
18. **Terraform 3단계는 Write → Plan → Apply**. Plan은 **차이(diff)를 출력**할 뿐 실제 적용하지 않는다.
19. **Terraform 코드 작성 순서**: Provider → 리소스 → 변수 → 데이터 소스 → 출력 → 모듈.
20. **Data sources는 참조만 가능하고 수정할 수 없다**. 또한 **NHN Cloud가 주기적으로 이미지를 업데이트하므로 이미지 이름이 변경될 수 있다**.
21. **NHN Cloud Terraform 버전 접미사**: Object Storage·Key manager = **`_v1`**, Compute·Network·Block Storage = **`_v2`**.
22. **인스턴스 타입(flavor)과 이미지 조회는 Data Sources에만 존재** — Resources에는 없다. 반대로 **LB·Floating IP·Object Storage는 Resources에만** 있고 Data Sources에는 없다.
23. **보안 계층 순서**: 물리적 보안 → 보안 정책(계정·권한) → 네트워크 → 컴퓨팅 → 애플리케이션 → 데이터. 순서 뒤바꾸기 출제 주의.
24. **안정성 = 단순함 유지** — "기능이 많고 복잡한 아키텍처가 안정적"은 오답. 복잡한 아키텍처는 오히려 신뢰성과 성능이 떨어진다.
25. **백업은 필수이며, 복원력이 뛰어난 시스템도 재해 대비가 필요**하다. "고가용성 구성했으면 백업 불필요"는 오답.
26. **비용 최적화에서 Auto-Scale의 요지는 유휴 자원 배치 지양** — 이벤트 대비 미리 큰 자원을 깔아두는 것은 비용 최적화에 반한다.
27. **성능 최적화의 설계 키워드**: 읽기/쓰기 분리, 정적/동적 분리, 프론트엔드 캐싱(CDN) + 백엔드 캐싱(EasyCache).
28. **웹 페이지 로드 2초 지연 → 이탈률 103% 증가 / 모바일 3초 이상 → 53% 이탈 / 100ms 증가 → 매출 1% 감소** (숫자 그대로 출제 가능).
29. **Lab 구성에서 Private was subnet = 10.1.3.0/24, Private db subnet = 10.1.2.0/24** — 번호 순서가 직관과 반대이므로 주의.
30. **Service Gateway는 인터넷 없이 Object Storage에 접근**하기 위한 것이고, 이것이 Lab에서 Private was subnet에 배치된다.
