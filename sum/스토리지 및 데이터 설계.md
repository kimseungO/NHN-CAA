## 0. 스토리지 3종 선택 기준 ⭐설계형 출제

| 요구사항 | 선택 서비스 |
|---|---|
| 인스턴스에 루트 스토리지 **외 추가 디스크**가 필요 | **Block Storage** |
| **여러 인스턴스에서 공유** 스토리지를 사용해야 함 | **NAS** |
| **많은 데이터**를 저장 / **인터넷을 통해 콘텐츠 제공** | **Object Storage** |

- 인스턴스의 기본 로컬 디스크(루트 디스크)도 **Block Storage 서비스를 통해 제공**된다.
- "공유"라는 단어가 나오면 NAS, "정적 콘텐츠·웹 배포·무제한 용량"이면 Object Storage.

## 1. Block Storage

**정의** — 인스턴스에 연결해서 사용하는 **블록 레벨** 스토리지

**타입 및 용량** ⭐숫자
| 항목 | 값 |
|---|---|
| 타입 | HDD, SSD, **Encrypted HDD, Encrypted SSD** |
| 용량 | **1GB ~ 2,000GB** |
| 암호화 요건 | **Secure Key Manager(SKM) 대칭 키** 필요 |

**용량 변경**
- 인스턴스에 **연결된 상태에서도 증설 가능** (루트 블록 스토리지 포함)
- **축소는 불가** ⭐함정

**연결 / 분리**
- 인스턴스를 **삭제해도 블록 스토리지 데이터는 보관** 가능
- 연결 해제 후 다른 인스턴스에 연결 가능 — 단 **동일 가용성 영역 내에서만** ⭐함정
- 사용하려면 연결 후 **파티션 생성 → 포맷 → 마운트** 순서로 초기 설정 필요

**스냅숏**
- 특정 시점 상태 저장·복구, 복구 시 **블록 스토리지 타입 변경 가능**
- 스냅숏 생성/복원에는 **원본 블록 스토리지가 반드시 필요** (동일 가용성 영역)
- **스냅숏 복제는 동일 리전 내 다른 가용성 영역**으로 가능
- **구동 중인 인스턴스**에 연결된 볼륨의 스냅숏은 **파일 시스템 무결성을 보장하지 않음** ⭐함정
- 스냅숏 복구 시 다른 가용성 영역의 인스턴스에 연결 가능. 단 **루트 블록 스토리지는 신규 인스턴스를 생성**하는 형태로 복구

**복제 / 이동**
- 복제 범위: **동일 조직 내** 다른 프로젝트 / 다른 리전 / 다른 가용성 영역 → 모두 가능
- 복제 시 **타입 변경 가능**: HDD ↔ SSD, Encrypted HDD ↔ Encrypted SSD (**암호화군과 비암호화군 사이는 불가**)
- 동일 조직의 다른 프로젝트로 **이동** 가능. 단 **스냅숏이 존재하면 이동 불가** ⭐함정

## 2. NAS

**정의** — 하나 이상의 인스턴스에 **동시에 연결**하여 사용하는 **공유 스토리지**

| 항목 | 값 |
|---|---|
| 프로토콜 | **NFS, CIFS** — **CIFS만 ID·비밀번호 설정 필요** ⭐함정 |
| 용량 | **300GB ~ 10,000GB** |
| 용량 변경 | 사용 중에도 **확장 및 축소 모두 가능** (Block Storage와 대조) |
| 접근 제어 | **ACL**로 허용 IP·IP 대역 지정, **다중 서브넷 연결 가능** |
| 스냅숏 | **자동·수동** 생성, 스냅숏으로 원하는 시점 복원 |
| 암호화 | **SKM 대칭 키 저장소를 먼저 생성**해야 설정 가능 |
| 복제 | **동일 조직 내 모든 프로젝트 / 리전 간** 복제 가능 |
| 모니터링 | 스토리지 용량, 사용률, **IOPS, Latency** |

- 스냅숏 저장은 **NAS 자체의 저장 공간을 소모**하므로 불필요하면 사용하지 않을 수 있다.

## 3. Object Storage

**정의** — 다양한 유형의 데이터를 원하는 만큼 저장하고 필요할 때 가져오는 **객체 스토리지**

**구조**
- 저장소 공간 = **컨테이너** (컴퓨팅의 컨테이너와 구분하기 위해 **OBS 컨테이너**라고도 함)
- 컨테이너 생성 시 **용량을 미리 지정하지 않음** → 탄력적 확장, 사용한 만큼 과금
- **오브젝트 = 데이터 + 메타데이터 + 고유한 주소**
- 데이터를 서로 다른 하드웨어에 **3개의 복제본**으로 분산·중복 저장 → 안정성 보장 ⭐숫자

**용량 제약** ⭐숫자
- **5GB를 초과하는 오브젝트는 5GB 이하의 세그먼트로 분할하여 업로드**해야 한다.

**스토리지 클래스**
| 클래스 | 용도 |
|---|---|
| **Standard** | 자주 접근하는 일반적 용도 |
| **Economy** | 드물게 접근, 주로 아카이브 장기 보관 |

**Economy Container 요금·제약** ⭐숫자 암기
- 10GB당 **0.2원/시간** (Standard는 **0.4원/시간**)
- 액세스 요청 1,000건당 **0.7원 ~ 13원** (PUT/COPY/POST/PATCH가 13원, 그 외 0.7원)
- **오브젝트 최소 보관 기간 30일** — 30일 이전 삭제해도 **잔여 보관 기간 요금이 부과됨**
- **판교 리전에서만 제공** ⭐함정

**접근 제어 / API**
- 오브젝트마다 **접근 URL 생성**, 인터넷을 통해 접근 가능
- 컨테이너를 **프라이빗**으로 설정하면 인터넷 접근을 막고 **ACL**로 특정 사용자만 허용
- **HTTP 기반 REST API** 제공

**부가 기능**
- 수명 주기 관리 / 버전 관리 / **객체 잠금** / 암호화(SKM 대칭 키 필요)
- **동일 조직 내 모든 프로젝트·리전 간 복제** 가능
- **정적 웹사이트** 구성 (웹서버 없이 제공)
- **WORM (Write-Once-Read-Many)** — 객체 잠금 주기를 설정하면 WORM 모델로 저장

### 3-1. 버전 관리 & 수명 주기 ⭐고빈도 출제

| 기능 | 동작 |
|---|---|
| **오브젝트 버전 관리** | 업데이트·삭제 시 **이전 버전이 지정된(아카이브용) 컨테이너에 보관**되며 **유닉스 타임스탬프**로 저장 |
| **오브젝트 수명 주기** | 수명 주기가 지난 오브젝트를 **삭제하거나 지정된 컨테이너로 이동** |
| **아카이브 오브젝트 수명 주기** | 수명 주기가 지난 **아카이브 컨테이너의 오브젝트를 자동 삭제** |

- 유닉스 타임스탬프 = **1970년 1월 1일 00:00:00 UTC**부터 경과한 시간을 **초 단위 정수**로 나타낸 값
- **수명 주기는 설정 이후에 업로드한 오브젝트에만 적용된다** ⭐대표 함정 (기존 오브젝트에 소급 적용 X)
- 이전 버전에 수명 주기를 설정하면 수명 주기를 초과한 **이전 버전은 자동 삭제**

**장애 시나리오 2가지** ⭐설계형 출제
1. **아카이브용 컨테이너를 원본보다 먼저 삭제**하면 → 원본 컨테이너의 오브젝트를 업데이트·삭제할 때 **오류 발생**
   - 해결: 아카이브용 컨테이너를 **새로 생성**하거나 원본의 **버전 관리 정책을 해제**
2. 암호화 컨테이너를 아카이브용으로 지정한 뒤 그 **대칭 키를 SKM에서 삭제**하면 → 원본 컨테이너의 오브젝트 **업로드·삭제가 실패**

### 3-2. Object Storage + Service Gateway 연계 ⭐설계형 출제

프라이빗 서브넷에서 인터넷을 경유하지 않고 Object Storage를 **API로** 사용하려면:

**필요한 Service Gateway 2종** ⭐
1. **Object Storage – Service Gateway**
2. **IaaS API Identity – Service Gateway**

**절차**
1. 인증 토큰 발급 — 인증 토큰 발급 API 엔드포인트 + **테넌트 ID / API 사용자 ID**(콘솔 확인) + **API 비밀번호**(콘솔에서 설정)
2. 발급받은 **인증 토큰**으로 Object Storage API 호출 — Object Storage API 엔드포인트 + **스토리지 계정**(콘솔 확인) + 인증 토큰
3. 두 서비스 게이트웨이의 **사설 IP를 인스턴스의 `/etc/hosts` 파일에 등록** ⭐세부 함정

## 4. Data Transporter

**정의** — 고객 데이터를 외부 클라우드로 이전하거나, 외부 클라우드·온프레미스 데이터를 NHN Cloud로 안전하게 이전

| 이전 방향 | 지원 방식 |
|---|---|
| NHN Cloud → 온프레미스 | **네트워크 방식** |
| 온프레미스 → NHN Cloud | **이동식 저장 장치 방식** |

- 이동식 저장 장치 **1대당 최대 100TB**, 여러 대 신청 가능 ⭐숫자
- NHN Cloud 엔지니어의 기술 지원 가능 — **별도 비용 발생**

**네트워크 방식 절차** ⭐순서형 출제
서비스 이용 신청 → 신청 내용 접수 → **고객 환경에 맞는 네트워크 연결 방식 결정** → **VPN 구성** → 제공된 VPN 네트워크로 데이터 이전 → 이전 완료 확인 및 **VPN 해제**

**이동식 저장 장치 방식 절차** ⭐순서형 출제
서비스 이용 신청 → 신청 내용 접수(전달 방법 = 직접 방문 또는 배송 협의) → 고객에게 장치 전달 → 고객이 장치 수령 → **고객 데이터 복사** → NHN Cloud로 장치 전달 → **입고 및 검수** → 업로드 서버 연결 후 NHN Cloud 스토리지로 이전 → 이전 완료 확인 → **이동식 저장 장치 초기화**

- 신청 시 기재 항목: 이전 대상 프로젝트 / 이전 담당자 성함·연락처 / 기술 지원 서비스 요청 여부

## 5. Storage Gateway

**정의** — 인스턴스 또는 **온프레미스 장비**에서 NHN Cloud 스토리지를 **파일 수준으로 마운트**하여 사용하는 서비스

- 별도의 **파일 시스템 구성이나 API 호출이 필요 없음** ⭐(Object Storage를 API로 쓰는 것과 대비)
- 연결 방법: VPC 네트워크에 **Floating IP** 연결 / **IPSec VPN** / **Direct Connect**
- **이중화 구성**으로 장애 발생 시에도 서비스 중단 없이 사용 → 가용성 보장
- 스토리지의 **서버 측 암호화** 기능으로 데이터 안정성 보장
- 제공 범위: **한국(판교) 리전**, 연결 대상은 **Object Storage**, 프로토콜은 **NFS v3 / v4 (Linux)** ⭐

## 6. 데이터베이스 구성 3가지 방법 ⭐핵심 비교

책임 분담 계층 (아래로 갈수록 NHN Cloud가 더 많이 담당)

| 구성 방법 | NHN Cloud가 담당하는 범위 | 고객 접근 계층 |
|---|---|---|
| **Instance에 구성** | 하드웨어·네트워크·인스턴스/서버 구성·**OS 설치**까지 | OS + DB 전부 고객 |
| **DB Instance로 구성** | 위 + **패키지 설치·DB 엔진 설치**까지 | **OS User 접근 가능** (OS 수준 제어 가능) |
| **RDS로 구성** | 위 + **DB 구성·파라미터 세팅·백업 복구 솔루션·고가용성 구성**까지 | **DB User로만 접근** (OS 계층 접근 **불가**) ⭐함정 |

### 6-1. DB Instance vs RDS

| 구분 | DB Instance | RDS |
|---|---|---|
| 설치 형태 | **DBMS가 포함된 이미지**로 Instance 생성 | **설정 값을 입력**하여 DB 인스턴스 생성 |
| 특징 | 단순 DB 설치용, **사용자가 직접 관리** | 고가용성·백업·업데이트 자동화, **별도 설치 없이 상태 모니터링** |
| 지원 DB 엔진 | **MS-SQL, MySQL, PostgreSQL, CUBRID, MariaDB, Tibero, Redis** (7종) | **MySQL, MariaDB, MS-SQL, PostgreSQL** (4종) |
| 제어 영역 | **OS 수준부터** 제어 가능 | **DB 수준부터** + 콘솔에서 DB 관리 제어 |

- RDS는 **2개의 가용성 영역**을 이용해 DB 이중화 및 Failover 구성 가능
- RDS에서 DB User 생성, 스키마(데이터베이스) 생성은 **콘솔을 통해** 수행

### 6-2. RDS DB 엔진별 기능 비교 ⭐표 암기 (MS-SQL 예외가 핵심)

| 항목 | MySQL | MariaDB | PostgreSQL | MS-SQL |
|---|---|---|---|---|
| 제공 리전 | 한국(판교), **한국(평촌), 일본(도쿄)** | 한국(판교) | 한국(판교) | 한국(판교) |
| 고가용성 | 제공 | 제공 | 제공 | 제공 |
| 읽기 복제본 | 일본(도쿄), **교차 리전(판교-평촌)**, 마스터당 **5대** | 한국(판교), 마스터당 5대 | 한국(판교), 마스터당 5대 | **미 제공** ⭐ |
| 데이터 스토리지 | HDD·SSD **20GB~2TB**, **자동·수동** 확장 | 20GB~2TB, **자동·수동** 확장 | 20GB~2TB, **수동 확장(재시작)** | 20GB~2TB, **수동 확장(재시작)** |
| 백업 | 자동·수동 + **교차 리전 백업본 복제(판교·평촌)** | 자동·수동 | 자동·수동 | 자동·수동 |
| OBS 백업·복원 | 제공(동일 리전) | 제공(동일 리전) | 제공(동일 리전) | 제공(동일 리전) |
| 복원 | 백업시점(스냅숏) 복원 + 로그를 이용한 특정 시점 복원 | 동일 | 동일 | 동일 |
| 콘솔 사용자 관리 | 제공 | 제공 | 제공 | **미 제공** ⭐ |

- **교차 리전 읽기 복제본 / 교차 리전 백업본 복제 = RDS for MySQL 전용** ⭐대표 함정
- DB 인스턴스 **타입 변경 시 수 분 동안 DB 인스턴스가 중지 후 시작**된다.

## 7. RDS의 고가용성 (※ MySQL, MariaDB 기준)

**구성**
- **마스터 + 예비 마스터(Candidate Master)** 로 구성, **서로 다른 가용성 영역**에 생성
- 예비 마스터는 **평소에 사용할 수 없다** (읽기 용도로도 사용 불가) ⭐함정
- 고가용성 구성 시 **백업은 예비 마스터에서 수행** → 마스터에 부하를 주지 않음

**장애 감지 & 자동 장애 조치** ⭐숫자
- 예비 마스터가 **Ping 간격**으로 마스터 상태를 체크
- **4회 연속 상태 체크 실패 시** 장애 조치 수행
- Ping 간격이 **짧을수록 민감**, **길수록 둔감** → 서비스 부하에 맞게 설정
- **스플릿 브레인 방지**: 장애 마스터에 할당된 **모든 사용자 보안 그룹의 연결을 해제**해 외부 접속 차단
- 접속용 **내부 도메인의 A record**가 예비 마스터로 변경 → **응용 프로그램 변경 불필요** ⭐
- 장애 조치 후: 기존 마스터 → **장애 조치된 마스터**, 예비 마스터 → **마스터**로 승격

**장애 조치 후 백업/복원 영향** ⭐함정
- 승격된 마스터는 장애 조치된 마스터의 **모든 자동 백업을 승계**
- 그러나 마스터가 변경되면 **바이너리 로그가 모두 삭제** → **기존 백업을 이용한 시점 복원은 지원되지 않음**
- 승격된 마스터에서 **신규 백업이 수행된 시각부터** 시점 복원 가능

**장애 조치된 마스터의 상태**
- **자동 백업이 수행되지 않음**
- **복구 / 재구축 / 분리 / 삭제를 제외한 모든 기능 수행 불가**

| 조치 | 조건 / 동작 |
|---|---|
| **복구** | **데이터 정합성이 깨지지 않았고 바이너리 로그가 유실되지 않은 경우**만 가능. 기존 DB 그대로 승격 마스터와 복제 관계 재설정 |
| **재구축** | 복구 실패 시 사용. 장애 조치된 마스터의 **DB를 모두 제거**하고 승격된 마스터의 DB를 토대로 재구축. 필요한 백업 파일이 없으면 백업이 수행되며 **성능 저하 발생 가능** |

## 8. RDS 백업 & 복원

### 자동 백업
- **백업 보관 기간을 1일 이상으로 설정하면 자동 백업 활성화** ⭐숫자
- 지정된 시간에 백업 수행
- **백업 보관 기간 최대 730일** ⭐숫자
- DB 인스턴스 삭제 시 **선택적으로 삭제** 가능
- 데이터 일관성을 위한 **테이블 잠금 사용 기능** 제공

### 수동 백업
- 특정 시점의 데이터베이스를 **영구 저장**
- 백업을 삭제하지 않는 한 **DB 인스턴스가 삭제되어도 함께 삭제되지 않음** ⭐자동 백업과 대조
- 백업 이름은 **리전별로 고유**해야 함

### 자동 백업 복제 리전
- **재해 복구(DR)** 목적. 원본 리전의 자동 백업 파일을 대상 리전으로 동일 복제
- 백그라운드에서 **일정 주기마다** 진행
- **리전 간 복제 트래픽 비용 + 대상 리전 백업 스토리지 비용**이 추가 청구
- **RDS for MySQL에서만 제공** ⭐함정

### 백업 내보내기
- 내부 백업 스토리지의 백업 파일을 **사용자 Object Storage로 내보내기** 가능
- 수동/자동 백업 파일 모두 가능, 백업 수행과 동시에 내보내기도 가능
- 내보내는 동안 **원본 DB 인스턴스의 네트워크 성능 하락 발생 가능**

### 복원 ⭐핵심 제약
- 복원 시 **항상 새로운 DB 인스턴스가 생성**되며 **기존 DB 인스턴스에는 복원할 수 없다** ⭐대표 함정
- 원본과 **동일한 DB 엔진 버전으로만** 복원 가능
- RDS for MySQL에서 생성한 백업 외에 **외부 MySQL의 백업으로도 복원 가능**

| 복원 방식 | 필요한 것 | 특징 |
|---|---|---|
| **스냅숏 복원** | **백업 파일만** | 백업을 수행한 **원본 DB 인스턴스가 필요 없음**. 백업 수행 시점으로 복원 |
| **시점 복원** | 백업 파일 + **바이너리 로그** | 특정 시점 또는 바이너리 로그의 **특정 포지션**으로 복원 |

**시점 복원이 불가능한 경우** ⭐출제
1. 용량 확보를 위해 원본 DB 인스턴스의 **바이너리 로그를 삭제**한 경우
2. **보관 기간에 따라 MySQL이 자동 삭제**한 경우
3. **고가용성 DB 인스턴스의 장애 조치**로 바이너리 로그가 삭제된 경우
4. 기타 이유로 바이너리 로그가 손상·삭제된 경우

- 바이너리 로그는 **원본 DB 인스턴스의 스토리지**에 저장되므로, 보관 기간이 길수록 스토리지를 더 사용하고 짧을수록 원하는 시점으로 복원이 어려워진다.

## 9. 대규모 데이터베이스 설계 ⭐설계형 출제

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **Scale-Up** (고성능 DB) | 단일 서버의 CPU·메모리·스토리지 업그레이드 | 애플리케이션 변경 없이 성능 향상, 관리 용이, **데이터 일관성·일관된 응답 시간** | 물리적 한계, 고가용성 미구성 시 **SPOF** |
| **Scale-Out – 리플리케이션** (읽기 복제본) | 동일 데이터를 여러 DB 인스턴스에 복제 → **읽기 부하 분산** | 읽기 성능 향상 | **insert·update·`select for update` 구문은 Primary DB를 사용해야 정합성 유지** ⭐ |
| **Scale-Out – 샤딩** | 데이터를 여러 DB에 분산 저장, 각 샤드는 전체의 일부만 보유 | 이론적으로 무한 확장, 높은 가용성 | **샤딩 키·전략 선택 필요**, 트랜잭션 복잡성 증가, 네트워크 오버헤드 |

- 실제로는 **Scale-Up으로 기본 성능을 올리고 Scale-Out으로 확장성·가용성을 보완**하는 혼합 방식이 흔함

### 9-1. SQL vs NoSQL

| 항목 | SQL(관계형) | NoSQL(비관계형) |
|---|---|---|
| 데이터 모델 | 구조화된 데이터 모델 | 유연한 모델(**Key-Value, Document, Graph**) |
| 스키마 | **미리 정의된 스키마** | 스키마가 없거나 유연 |
| 확장성 | **수직 확장(Scale-up)** | **수평 확장(Scale-out)** |
| 트랜잭션 | **ACID 지원** | 미지원 또는 제한적 지원 |
| 질의 언어 | SQL | 다양한 질의 방법 |
| 작업 유형 | 복잡한 질의 처리 | 빠른 읽기·쓰기, 단순 질의 |
| 주요 용도 | 범용 애플리케이션 | **비정형 데이터, 분산 시스템, 실시간 데이터 처리** |

- ACID = **원자성(Atomicity), 일관성(Consistency), 고립성(Isolation), 영속성(Durability)**

### 9-2. RDS for MySQL 고가용성 참조 아키텍처
- Private Subnet 내 RDS for MySQL: **AZ(A) Master ↔ AZ(B) Candidate Master**(HA), Read Replica
- 백업은 **Object Storage로 복제** → 백업 가용성 향상
- **교차 리전 읽기 복제본을 쓰려면 리전 피어링(Peering Gateway)이 필수** ⭐

## 11. 자주 나오는 함정 포인트

1. **Block Storage는 증설만 가능, 축소 불가** / **NAS는 확장·축소 모두 가능**
2. Block Storage 연결 해제 후 재연결은 **동일 가용성 영역만** — "바로 다른 가용성 영역의 인스턴스에 연결 가능"은 오답
3. **스냅숏이 존재하는 Block Storage는 다른 프로젝트로 이동 불가**
4. Block Storage 타입 변경은 **HDD↔SSD**, **Encrypted HDD↔Encrypted SSD** 내에서만
5. NAS 프로토콜 중 **ID·비밀번호가 필요한 것은 CIFS뿐** — "NFS와 CIFS 둘 다 인증 정보 필요"는 오답
6. **Object Storage 수명 주기는 설정 이후 업로드된 오브젝트에만 적용**
7. **Object Storage 복제는 동일 조직 내 다른 리전으로도 가능** — "동일 리전 내에서만"은 오답
8. Economy 클래스는 **최소 보관 30일 + 판교 리전 전용**, 조기 삭제해도 잔여 기간 과금
9. **5GB 초과 오브젝트는 세그먼트 분할 업로드 필수**
10. 암호화(Block Storage / NAS / Object Storage) 는 모두 **SKM 대칭 키 저장소 선행 생성** 필요
11. 프라이빗 서브넷에서 Object Storage API 사용 시 **Service Gateway 2종(Object Storage + IaaS API Identity)** 필요
12. **DB Instance는 OS 접근 가능, RDS는 DB User 접근만 가능**
13. RDS 지원 엔진은 **4종(MySQL/MariaDB/MS-SQL/PostgreSQL)**, DB Instance는 **7종**(+CUBRID, Tibero, Redis)
14. **MS-SQL은 읽기 복제본·콘솔 사용자 관리 미제공**
15. **교차 리전 읽기 복제본·교차 리전 백업본 복제·자동 백업 복제 리전 = MySQL 전용**
16. 고가용성의 **예비 마스터는 평소 사용 불가** (읽기 부하 분산용 아님 → 그건 Read Replica)
17. 장애 조치 판단 기준은 **Ping 4회 연속 실패**
18. **장애 조치가 발생하면 기존 백업 기반 시점 복원 불가** (바이너리 로그 삭제)
19. **복원은 항상 새 DB 인스턴스 생성** — 기존 인스턴스에 덮어쓰기 불가
20. **자동 백업 보관 기간 최대 730일**, 자동 백업 활성화 조건은 **보관 기간 1일 이상**
21. 수동 백업은 DB 인스턴스 삭제 시에도 **남는다**
22. 읽기 복제본 사용 시 **insert/update/select for update는 Primary DB로** 보내야 함
23. Storage Gateway는 **API 호출·파일 시스템 구성 없이** 파일 수준 마운트, **NFS v3/v4**, 판교 리전
24. Data Transporter 이동식 저장 장치는 **대당 최대 100TB**, 마지막 단계는 **장치 초기화**
25. DataFlow 노드는 **Source / Filter / Branch / Sink**, 암호화는 **Cipher 필터**, 파싱은 **Grok 필터**
26. DataQuery는 **Trino** 기반이며 **프로젝트별 클러스터**를 제공
