## 1. NHN Cloud 배포 패턴

### 1-0. 배포 단위의 확장 축

배포 단위는 **가용성 영역 → 리전 → 멀티 리전 → 멀티 클라우드 → 하이브리드** 순으로 점차 확장된다.
배포 패턴 선택은 "리소스를 어디에 둘 것인가"에 그치지 않고 **보안 정책 · 네트워크 구성 · 데이터 복제 방식 · IAM 정책 · 모니터링 표준화**를 함께 결정하는 문제다.

| 패턴 | 장애 대응 범위 | 핵심 목적 | 대표 활용 서비스/기술 |
|---|---|---|---|
| 단일 AZ | 인스턴스 장애 | 단순성 · 비용 효율 | 이미지, 스냅샷, Cloud Scheduler, 백업 |
| 단일 리전 (멀티 AZ) | AZ 장애 | 고가용성 + 낮은 지연 + 데이터 주권 | LB(외부/내부), RDS Active-Standby, Read Replica |
| 멀티 리전 | **리전 전체 장애** | DR · 글로벌 지연 단축 | GSLB(DNS Plus), Region Peering, RDS 교차 리전 읽기 복제본, 스토리지 리전 간 복제 |
| 멀티 클라우드 | CSP 단위 장애 | Lock-in 회피 · Best-of-Breed | Direct Connect, Network Firewall IPSec VPN, VPN Gateway |
| 하이브리드 | 온프레미스 ↔ 클라우드 | 점진적 전환 · 규제 대응 | Private Station, Private Region, Direct Connect, IPSec VPN, VPN Gateway |

### 1-1. 단일 가용성 영역(Single AZ) 배포

WEB / WAS / DB 계층을 **하나의 AZ**에 배치하는 구조.

**사용 사례**
- 개발 및 테스트 환경 (운영과 분리된 개발·QA 목적, 비용 최적화)
- 고가용성이 필수적이지 않은 애플리케이션 (배치 처리, 사내 단위 업무 시스템)
- 상용 애플리케이션 마이그레이션 **초기 단계** (기존 환경 제약으로 단일 인스턴스/단일 AZ만 가능)
- 라이선스 제약 또는 비용 문제 (여러 인스턴스 동시 실행 불가 제품)

**설계 고려 사항 (복구 수단 4종)**
1. **인스턴스 이미지 기반 복구** — 주기적으로 개인 이미지 생성 → 인스턴스 템플릿화하면 생성 속도 추가 단축
2. **블록 스토리지 복제** — 루트/추가 스토리지 정기 복제 → 다른 AZ에서 인스턴스 생성 가능
   - 스토리지 복제는 **데이터 양이 많지 않을수록 효율적**
3. **스냅샷 기반 복구** — 대용량 스토리지는 복제 시간이 길어지므로 스냅샷이 더 유리. 스냅샷은 **블록 단위 저장**이라 빠르게 복구 가능하고 신규 인스턴스 생성에도 활용
4. **백업 서비스** — 복제·스냅샷과는 **별도로** 반드시 수립. DB는 정기 백업·보관 정책 필수이며 단일 AZ에서는 백업이 **최후의 보호 장치**

**⚠ 정합성 권고**: 이미지 생성, 스토리지 복제, 스냅샷 생성 시에는 데이터 정합성을 위해 **인스턴스를 일시 중지한 뒤 작업할 것을 권장**한다.

**운영 자동화**: Cloud Scheduler로 이미지 생성·스냅샷·스토리지 복제를 정기 자동화 → 복구 시간을 예측 가능하게 만든다.

> 정리: 단일 AZ는 단순성·비용이 장점이나 **단일 장애 지점(SPOF)** 이 존재 → 복구 전략·자동화·백업 설계가 안정성의 핵심.

### 1-2. 단일 리전(멀티 AZ) 배포

하나의 리전 안에서 여러 AZ에 워크로드를 분산 배치.

**사용 사례**
- 고가용성이 필요한 애플리케이션 (각 계층에 하나 이상의 인스턴스 존재 → 일부 컴포넌트 실패에도 서비스 지속)
- 지연 시간 최적화 (사용자 요청이 특정 국가/지역에 집중된 경우)
- **리소스 간 짧은 지연 시간이 필요한 내부 연동 시스템** (트래픽이 리전 내부에만 머물러 고대역폭·저지연 구성 가능, 리전 간 전송 비용 미발생)
- **데이터 상주(Data Residency) · 데이터 주권(Data Sovereignty)** 요구사항 준수
  - 예: 금융데이터는 국내 리전 내 저장 필요(금융감독원 규제 준수)

**고려 사항**
- **리전 전체 장애 시 다운타임**은 여전히 발생 → 리전 단위 복제 전략 필요
  - 주요 데이터·구성 요소를 다른 리전으로 복제
  - VPC 리전 피어링을 통한 리전 간 내부 네트워크 통신
  - RDS for MySQL 교차 리전 읽기 복제본 활용 및 장애 시 마스터 승격
  - 블록/오브젝트 스토리지·NAS의 리전 간 복제 기능 활용
  - 해당 국가/서비스의 리전이 **하나뿐이라면** 다른 CSP 리전 또는 오프라인 스토리지 활용도 고려
- 다중 AZ 중복 배포 → 리소스 증가에 따른 비용 부담
- **계층 간 Failover 설계**: 프런트엔드는 **외부 LB**가 영역 간 분산, 백엔드는 **내부 LB**가 라우팅, DB는 **Active-Standby 또는 Read Replica** 구조로 영역 간 복제 유지

> 정리: 단일 리전 배포 = 고가용성 + 낮은 지연 + 데이터 규제 준수. 단, **멀티 AZ 구성 + 리전 간 복제 전략**이 병행돼야 완성된다.

### 1-3. 멀티 리전 배포

**필요 이유**: 단일 리전 아키텍처는 AZ 장애에는 대응 가능하지만 **리전 전체 장애에는 취약**하다.
- 보조(Secondary) 리전에 애플리케이션·데이터·설정을 복제 → 리전 장애 시 **즉시 트래픽 전환(Failover)**
- **DNS Plus GSLB**로 장애 시 트래픽 자동 라우팅
- 보조 리전은 비용 절감을 위해 **축소 구성(reduced footprint)** 으로 운영 가능

**사용 사례**
- 재해 복구(DR) 사이트 — RDS for MySQL 교차 리전 읽기 복제본을 **마스터로 승격** 가능, 블록/Object Storage/NAS 리전 간 복제
- 글로벌 사용자 대상 낮은 지연 시간 — DNS Plus GSLB의 **geolocation 기반 라우팅** (예: 국가별 리전에 배포된 글로벌 게임 서비스)
- 법적·규제 요건 준수 (데이터 주권·상주 규제가 지역별로 있는 경우 리전별 분리 운영)
- 서비스 연속성 — Active-Active 또는 Active-Passive 패턴으로 점검·배포 중에도 무중단
- 타 리전 데이터 백업·장기 보관(소산)

**고려 사항**
- **복제 방식 선택** (핵심 비교)

  | 방식 | 일관성 | 성능/지연 |
  |---|---|---|
  | 동기 복제 | 높은 일관성 | 상대적으로 **큰 지연** |
  | 비동기 복제 | 일관성 지연 가능 | **성능 우수** |

- **RDS 교차 리전 읽기 복제본은 보조 리전에서 읽기 전용**이며, **쓰기 작업은 리전 피어링을 이용해 주 리전의 마스터 DB에 수행**한다. ← 자주 나오는 함정
- 트래픽 라우팅: DNS Plus GSLB + **헬스 체크 기반 장애 감지 후 자동 Failover**
- DR 전략: **RTO(복구 시간 목표)** · **RPO(복구 시점 목표)** 에 따라 DR 레벨 정의, 정기적 복제·백업·**DR 테스트 계획 수립 필수**
- 비용: 리소스 중복 + 데이터 전송 비용 발생 → 보조 리전 축소 구성
- 운영 복잡성: 리전 수 증가 → IaC 기반 자동화, **중앙 집중식 모니터링·로그 수집 플랫폼**, 리전별로 동작 가능한 CI/CD 파이프라인 필요

### 1-4. 멀티 클라우드 배포

**사용 사례**
- **공급자 종속성(Lock-in) 회피** — IaC 기반으로 인프라를 독립적으로 구성해 클라우드 간 전환 비용 절감
- 고가용성 및 재해 복구(HA/DR) — 동일 애플리케이션 이중화, 데이터 복제·동기화로 Failover 지원
- **서비스별 최적 클라우드 활용(Best-of-Breed)** — 예: 머신러닝/AI 워크로드는 NHN Cloud GPU 인스턴스, 데이터 웨어하우스는 타 클라우드

**설계 고려사항**
- 운영 복잡성 증가 — 콘솔 UI·API·서비스 명칭/구조가 달라 통합 운영 체계 필요, **IaC(Terraform 등) 표준화**, 멀티 클라우드 모니터링 시스템
- **네트워크 연결성 및 보안** — NHN Cloud 연결 옵션 3종
  1. **Direct Connect (Hosted Connection)**
  2. **Network Firewall IPSec VPN**
  3. **VPN Gateway (Site-to-Site)**
- 데이터 일관성 및 통합 — 서로 다른 스토리지/DB 플랫폼 간 동기화 난이도 높음 → 복제 방식(동기/비동기), **CDC(Change Data Capture)**, 메시지 큐 기반 이벤트 처리
- 배포 및 CI/CD — GitHub Actions, Jenkins, ArgoCD 등 다중 클라우드 지원 툴로 파이프라인 통합
- 비용 관리 — **CSP별 Billing API 연동** 또는 3rd Party 멀티 클라우드 비용 모니터링 도구 도입

### 1-5. 하이브리드 배포

**사용 사례**
- 점진적인 클라우드 전환(Migration Strategy) — 예: ERP/레거시는 온프레미스 유지, 웹/모바일부터 클라우드로 이전
- 온프레미스 애플리케이션에 클라우드 기능 활용 — 단기 트래픽 급증 시 클라우드로 **확장(버스트)** (예: 수강신청, 대규모 이벤트)
- 규제 기반 데이터 처리 — 민감 데이터는 온프레미스, 분석·처리 계층은 클라우드 (예: 의료 데이터는 병원 IDC 저장, 빅데이터 분석은 클라우드)
- 비즈니스 연속성·DR 구성 (양방향 모두 가능)
- 최적 기술 조합(Best-of-Breed)

**고려 사항**
- 통합 네트워크 설계 — Direct Connect(Hosted Connection)는 **파트너 네트워크 플랫폼을 통해 온프레미스·타사 클라우드와 전용 회선을 동시에 연결 가능**
- 데이터 통합 및 일관성 — CDC, 메시지 큐 기반 동기화, 공통 포맷 설계
- 운영 자동화 및 관찰성 — 여러 환경에 로그/모니터링이 분산되므로 **중앙 집중식 관리 체계 필수**
- 비용 및 라이선스 — 소프트웨어 라이선스가 클라우드·온프레미스에서 **동일하게 적용되는지 확인** 필요
- 애플리케이션 이식성(Portability) — 쿠버네티스/컨테이너 기반 아키텍처로 환경 간 이식성 확보
- **NHN Cloud Private Station**: 고객이 원하는 IDC 환경에 NHN Cloud 기반 프라이빗/하이브리드 클라우드를 구축하는 서비스
- **NHN Cloud Private Region**: 대규모 고객을 위한 전용 프라이빗 클라우드 환경, Compute/Network/Storage 등 주요 IaaS를 고객 전용으로 제공

### 1-6. ★ NHN Cloud 프라이빗 클라우드 서비스 비교 (암기 표)

| 구분 | **Private Deck**<br>소규모 가상화 플랫폼 | **Private Station**<br>중대형 프라이빗 클라우드 | **Private Region**<br>고가용성 프라이빗 클라우드 |
|---|---|---|---|
| 핵심 특징 | 클라우드 관리 플랫폼(**CMP**) 제공 → 이기종 클라우드 플랫폼 통합 관리 | NHN Cloud 환경을 로컬에 구현, **전문 엔지니어가 운영 지원하는 관리형 서비스** | **멀티 AZ 기반** 고가용성 + 대규모 자원 확장 → 엔터프라이즈급 비즈니스 연속성 |
| 제공 형태 | **독립 구축형**<br>온프레미스 DC에 사전 정의된 형태로 제공 | **연동 구축형**<br>온프레미스 DC에 랙 형태 제공, **상위 리전과 연동** | **프라이빗 클라우드 구축형**<br>전용 프라이빗 클라우드 서비스 형태 |
| 규모* | **240 ~ 960 VM**<br>(2 Rack Gold 기준) | **600 ~ 3,000 VM**<br>(최대 **3개 Rack**) | **1,000 ~ 10,000 VM 이상** |
| 가용성(AZ) | **1개** | **1개** | **2개** |
| 네트워크 | **VLAN 기반** | **VxLAN 기반(멀티 테넌트)** ← Station·Region 공통 | |
| 관리 주체 | **고객 직접 관리** 가능 | **NHN Cloud 전담 엔지니어를 통한 운영 서비스 제공** ← Station·Region 공통 | |
| 구축 기간 | **1개월 이내** | **2개월** | **5개월** |
| 이용 방식 | **구매 / 구독** | 구독 | 구독 |

\* VM은 **4 core, 8 GB Memory** 기준. 최대 제공 용량 이상 구성 시 별도 협의 필요.

**아키텍처 가치 요약**
- Private Deck: 하드웨어·네트워크 장비·클라우드 플랫폼이 통합된 **'올인원 패키지'**, 복잡한 설계 없이 즉시 배포 가능한 독립 구축형, **1개월 이내 최단기 구축**
- Private Station: 퍼블릭 리전의 인프라 기술력을 고객 데이터 센터로 확장하는 **연동 구축형**. 퍼블릭과 **동일한 인터페이스와 API 유지** + Managed Service로 관리 부담 최소화
- Private Region: 물리적으로 분리된 **2개 이상의 가용 영역(Multi-AZ)** 을 갖춘 전용 프라이빗 리전. 무중단 비즈니스 연속성(DR) 확보

**기술적 차이점**
- 네트워크: **L2/VLAN(Private Deck)** = 소규모 최적, 구성 단순·초기 진입 장벽 낮음 / **오버레이 VxLAN(Station·Region)** = 대규모 트래픽·유연한 확장, 멀티 테넌트 환경의 네트워크 격리
- HA: **Single AZ(Deck/Station)** — 단일 가용 영역이나 **내부 컴포넌트 이중화**로 안정성 확보 / **Multi-AZ(Region)** — Rack 및 전원 공급원까지 완전히 분리한 2개 이상 AZ, **Active-Active** 가능
- 운영 주체: **Self-Managed(Deck)** vs **NHN Cloud Managed(Station·Region)** — 인프라 하부 레이어부터 플랫폼까지 NHN Cloud 전문 인력이 운영, 고수준 SLA 유지

**사이징 기준**
- Private Deck: 2 Rack 기준 최대 약 **960 VM**, **1:1 ~ 4:1 오버커밋** 가변 적용 가능
- Private Station: 최대 **3,000 VM** 수준 확장, 연동된 상위 리전 자원을 유연하게 활용
- Private Region: 최소 **1,000 VM**에서 시작, **만 단위(10,000+) 이상** 무제한급 확장

**아키텍처 선택 결정 트리**
1. 가장 빠른 시일 내에 독립된 프라이빗 인프라가 필요한가? → **YES: Private Deck** (HCI 기반 빠른 도입·자율 운영)
2. 클라우드 운영 전문성이 부족하며, 퍼블릭 클라우드와 동일한 환경이 필요한가? → **YES: Private Station**
3. 금융권 핵심 계정계나 공공 대규모 서비스처럼 **무중단 가용성(Multi-AZ)이 필수**인가? → **YES: Private Region**

> Note: 위 기준은 고객의 실제 DC 환경, 네트워크 회선 품질, 하드웨어 수급 상황에 따라 조정될 수 있어 설계 전 전문가와의 기술 협의가 수반돼야 한다.

## 2. 리소스 계층 구조

### 2-1. 3계층 구조

**조직(Organization) → 프로젝트(Project) → 리소스(Resource)**

| 레벨 | 단위 | 역할 |
|---|---|---|
| **Level 1** | 조직(Organization) | NHN Cloud 서비스를 사용하기 위한 **최상위 단위**. 회사/부서 등 비즈니스 단위로 구성. **IAM 공통 보안 정책 설정**, **비용 청구의 단위** |
| **Level 2** | 프로젝트(Project) | 특정 서비스·애플리케이션을 위한 **자원 관리 단위**. 프로젝트별 사용자 역할·권한 설정으로 접근 제어. 비용·리소스 사용량을 프로젝트 단위로 추적 |
| **Level 3** | 리소스(Resource) | 프로젝트 내에서 생성되는 실제 클라우드 자원(컴퓨팅 인스턴스, 스토리지, 네트워크 구성 요소). 리소스별 접근 권한·정책 제어, **태그 및 그룹**으로 다양한 관점에서 분류 |

**Level 1 조직의 세부 기능**
- 전사 공통 보안·IAM 정책 정의 (예: 비밀번호 정책, MFA 의무화, 공통 태그 표준)
- 비용 청구 단위 — 여러 프로젝트의 비용을 통합해 전사 관점 관리
- 거버넌스 기준 수립 — 리소스 네이밍 정책, IAM 역할 표준, 보안 정책

**Level 2 프로젝트의 세부 기능**
- 프로젝트별 사용자 역할과 권한 분리 (서비스 운영팀/개발팀/보안팀)
- 비용·사용량을 프로젝트 기준으로 집계 → 팀·환경(dev/stg/prod) 기준 비용 책임 구조 확립
- 서비스 경계 구분 — dev/stg/prod 분리로 **사고 범위 최소화**

**Level 3 리소스의 세부 기능**
- 예: 컴퓨팅 인스턴스, 스토리지, 네트워크 구성 요소(SG, Routing, LB 등)
- 태그/리소스 그룹: 팀·환경·비용센터 관점 분류 → 모니터링·비용 청구·자동화 정책의 **핵심 기준**

### 2-2. 운영 시 주의 사항 및 모범 사례 (안티패턴 3종)

| 안티패턴 | 문제 | 대응 |
|---|---|---|
| **dev/stg/prod를 하나의 프로젝트에 혼재** | 권한·네트워크 보안·비용이 섞여 사고 가능성 증가 | 환경별 프로젝트 분리, 또는 최소한 보안 경계·VPC 단위 분리 적용 |
| **태그 미사용 또는 불완전한 태깅** | 비용 분석·자산 식별·운영 자동화 어려움 | 생성 템플릿/CI·CD 파이프라인에서 **필수 태그를 의무화** |
| **권한을 사용자에게 직접 부여** | IAM 정책 관리가 복잡해지고 회수 누락으로 보안 리스크 | **역할 그룹(Role Group) 기반 표준화** + 정기적 권한 리뷰 |

### 2-3. 리소스 계층 구조 예시 — 분리 모델 2종

| 구분 | **환경별 분리 (dev/stg/prod)** | **부서/팀별 분리 (team1, team2, QA)** |
|---|---|---|
| 사용 조직 | 단일 서비스를 이용하는 회사/조직 | 다양한 팀이 NHN Cloud를 병행 사용하는 조직 |
| 특징 | 개발/운영 환경 분리로 격리 및 **운영 안정성** 확보 | **팀 간 리소스 충돌 방지**, 역할 기반 접근 제어 가능 |
| 장점 | IAM으로 **환경별 접근 권한** 관리 용이, 비용 분리 가능 | **부서/팀 단위 비용 관리**, 거버넌스 정책 적용 간소화 |
| 프로젝트 예 | service-dev / service-stg / service-prod | dev team 1 / dev team 2 / QA team |

**① 환경별 분리 — 의도**: 개발–검증–운영을 강하게 격리하여 배포 실수, 보안 사고, 데이터 오염 방지
- IAM 기준: 운영(prod)은 원칙적으로 **최소 권한(Reader/Operator 중심)**, **변경 권한(Admin)은 승인 절차를 거친 소수 인원에게만**
- 비용·거버넌스: 태그 규칙(예: `env=prod/stg/dev`)으로 비용·로그·정책 적용 용이
- 릴리스 플로우: **dev → stg → prod 승격 기준**을 프로젝트 단위로 강제
- 네트워크·보안 경계: **prod는 별도 VPC·보안 정책**, stg/dev와 라우팅 최소화
- 적합한 경우: 단일/소수 서비스 운영, 릴리스 안정성(품질)이 최우선, 규제 준수가 중요한 산업(금융/공공)
- ⚠ 주의: 공통 리소스(logging, Bastion, CI/CD)가 환경마다 중복될 수 있어 별도 **"공통 인프라 프로젝트"** 를 두는 것이 효율적

**② 부서/팀별 분리 — 의도**: 팀의 자율성과 빠른 개발 속도 보장 + 팀 간 리소스 충돌 방지
- IAM 기준: 팀별 역할 그룹(RBAC)을 표준으로 정의 (예: TeamA:Admin, TeamA:Operator), 사용자에게 직접 권한 부여 금지
- 비용·거버넌스: 팀 단위 예산 관리 및 사용량 측정(**차지백/쇼백**) 용이, 쿼터·태그 정책으로 팀별 리소스 규모 제어
- 표준화 관리: 네트워크·보안·모니터링·이미지 기준을 팀마다 제각각 만들지 않도록 **"베이스라인 템플릿"** 또는 서비스 카탈로그 제공
- 적합한 경우: 여러 개발팀 병렬 개발, 조직 확장 속도가 빠른 스타트업/플랫폼 조직, 팀 단위 책임·예산 분리 필요
- ⚠ 주의: 팀별 보안 정책이 달라지는 문제 방지를 위해 네이밍 규칙, 보안 그룹 규칙, 이미지/패치 기준 등 **"가드레일 정책"** 필수

**③ 선택 가이드**
- 릴리스 품질·규제 우선 → **환경별 분리** 중심
- 조직 확장·책임/비용 분리 우선 → **팀별 분리** 중심
- **혼합 구성(현실적으로 가장 많이 사용)**
  - 서비스 단위 프로젝트 + 환경 접미사 (예: `pay-prod` / `pay-stg` / `pay-dev`)
  - 팀 단위 프로젝트 + 환경 라벨 혼합
  - 공통 인프라(로그/보안/Bastion/CI) 전용 프로젝트 별도 운영

**④ 운영 팁**
- RBAC 표준화: 역할 그룹 중심, **직접 부여는 예외·기간 제한 방식**으로 관리
- 네트워크 경계 설계: prod는 별도 방화벽·피어링 정책, 교차 접근 최소화
- 감사·비용 체계: 태그 규칙 + 프로젝트 기준 리포트
- **분기마다 정기 리뷰** — 프로젝트 구성·권한·태그·공통 인프라 중복 여부 점검

### 2-4. 명명 규칙(Naming Rule)

**표준 구조**

```
[조직/부서]-[환경]-[서비스명]-[리소스유형]-[리전]-[고유식별자]
```

**예시**
- `fin-prod-payment-vm-kr1-001`
- `hr-dev-api-db-kr1-a01`

| 구성 요소 | 설명 | 예 |
|---|---|---|
| 조직/부서 | 리소스를 사용하는 조직 또는 팀명 | fin, hr, rnd |
| 환경(Environment) | 배포 환경 구분 | dev, test, prod |
| 서비스명 | 리소스가 속한 서비스/시스템 이름 | payment, api, erp |
| 리소스 유형 | 리소스 종류 구분 | vm, db, lb, vpc |
| 지역/리전 | 리소스가 배치된 NHN Cloud 리전 코드 | kr1, jp1 |
| 고유 식별자 | 동일 서비스 내 리소스 구분용 순번/문자 조합 | 001, a01, 01 |

**명명 규칙이 중요한 이유 (4가지)**
1. **식별 용이성** — 이름만으로 조직·환경·서비스·리전·유형 파악 → 장애 대응/자산 파악 신속
2. **운영 자동화 효율성** — 스크립트 자동화나 IaC 구성에서 **이름 패턴을 조건으로 활용**
3. **팀/조직 간 협업 품질 향상** — 혼동 감소, 신규 팀원 온보딩 용이
4. **보안 및 규정 준수** — 프로젝트·환경·부서가 명확히 드러나 **RBAC/IAM 정책 적용이 용이**

> 정리: 명명 규칙은 **식별성·일관성·보안성·자동화 효율성**을 동시에 확보하는 핵심 도구이며, 템플릿(IaC)·CI/CD·운영 가이드 등 전사 프로세스에 반영될 때 효과가 가장 크다.

## 3. 계정 및 권한 (IAM)

### 3-1. 계정·권한 구조의 흐름

| 단계 | 수행 작업 |
|---|---|
| **조직** | IAM 콘솔 도메인 생성, IAM 계정 생성, 조직 관리 역할 부여 |
| **프로젝트** | 조직에서 생성한 IAM 계정 **추가(초대)**, 프로젝트 관리 역할 및 프로젝트 하위 **서비스별 역할** 부여 |
| **서비스** | 서비스별 역할을 부여받은 사용자가 서비스 이용, 서비스에서 제공하는 역할 정책 사용 |

**서비스 단위 권한(세분화된 RBAC) 예시**
- Object Storage: **READ(읽기 전용)** / **READ·WRITE(읽기·쓰기)**
- Compute: 인스턴스 조회 권한만 허용 / 생성·삭제·제어 권한 분리 가능
- NHN Bastion: 인스턴스 접속은 IAM 정책과 Bastion 사용자 권한을 기반으로 통제. **특정 사용자에게 특정 인스턴스 접속 권한만** 부여하여 최소 권한 원칙 준수

**⚠ 초기 권한 설계가 미흡할 때의 3대 문제**
1. 사용자 권한 과다 부여 → 보안 취약점
2. 권한 회수 누락 → 운영 통제 어려움
3. 프로젝트 간 경계 붕괴 → 사고 전파 위험

---

### 3-2. ★ NHN Cloud 계정 vs IAM 계정 (암기 표)

| 구분 | **NHN Cloud 계정** | **IAM 계정** |
|---|---|---|
| 개요 | NHN Cloud 포털에 **최초 가입한 기본 관리자 계정**. 조직을 생성하며 **조직 OWNER 권한을 자동 보유** | 조직 관리자가 생성한 **하위 사용자 계정**. 조직 또는 프로젝트 단위로 접근 권한 부여 |
| 계정 유형 | 이메일 기반 **단일 사용자 계정** | **하위 서비스 운영 계정** |
| 권한 수준 | 조직 및 프로젝트 생성 **관리 권한** | 역할(Role)·역할 그룹(Role Group)을 통해 **제한된 권한** |
| 주요 역할 | 조직 OWNER, 조직 관리, IAM 관리, **결제 관리** | 프로젝트 관리자, 서비스 운영자, 읽기 전용 사용자 등 |
| **변경 가능 여부** | **조직 OWNER 삭제 불가**, 권한 위임은 가능 | **계정 잠금, 삭제, 역할 변경 가능** |
| 2차 인증 | 이메일, 휴대폰, OTP | 이메일, 휴대폰, OTP |
| **콘솔 접근** | **NHN Cloud 콘솔** | **IAM 콘솔** |

**왜 분리해야 하는가**
- 보안 관점: NHN Cloud 계정은 조직 전체를 통제할 수 있는 강력한 권한 → 일반 운영 작업에 사용하면 사고 범위가 매우 커짐. IAM 계정에 **최소 권한(Least Privilege)** 적용
- 운영 효율성 관점: 서비스별·프로젝트별 역할 분리로 팀별 자원 관리·배포·접근 체계화. **자동화·CI/CD·운영 스크립트에는 IAM 시스템 계정을 사용하는 것이 안정적**
- **책임 분리(SoD: Segregation of Duties)**
  - NHN Cloud 계정: 관리·결제·정책·조직 운영
  - IAM 계정: 리소스 생성·운영·모니터링

**초기 설계 시 반드시 고려할 사항**
- NHN Cloud 기본 계정은 **로그인 보안 강화(MFA 필수)** 및 **소수 관리자만 사용**이 원칙
- 프로젝트/서비스 운영은 **반드시 IAM 계정 사용**, NHN Cloud 계정은 **결제·조직 관리·정책 수립에만** 사용
- 신규 조직 구성 시 기본 베이스라인
  - `org-admin` 역할 그룹
  - `project-admin`, `service-operator`, `read-only` 역할 그룹
  - **시스템 계정(IAM) 분리** (CI/CD, 자동화 스크립트용)

---

### 3-3. IAM의 3요소

> IAM의 핵심 질문: **"누가(Who) – 어떤 리소스에서(What Resource) – 무엇을 할 수 있는가(What Action)"**

| 요소 | 내용 |
|---|---|
| 누가(Who) | 사용자(User) 또는 계정(Account). 조직의 구성원, 특정 팀 단위 계정, **자동화/CI용 시스템 계정** 포함 |
| 어떤 리소스에서(What Resource) | Compute 인스턴스, Database, Object Storage, Network 구성 요소(VPC, Subnet, Load Balancer 등). **특정 리소스 또는 리소스 그룹**에 대해 접근 범위를 세밀하게 제한 가능 |
| 무엇을 할 수 있는가(What Action) | 읽기(Read), 쓰기(Write), 생성(Create)/삭제(Delete), 관리자(Admin) 수준 제어 |

**★ 동작 구조 (최빈출)**

```
Permission(권한) → Role(역할) → User(사용자)
```

- IAM은 리소스 접근 권한을 **최종 사용자에게 직접 할당하지 않는다.**
- 권한(Permission)은 **역할(Role) 단위로 묶여 있고**, 이 역할이 **인증된 사용자 계정에 할당**된다.
- IAM 정책은 **어떤 역할을 어떤 사용자 계정에 부여할지 정의**하고, 해당 **정책은 리소스에 연결**된다.

**역할 중심 RBAC의 장점**: 사용자 수가 많아져도 일관성·확장성 유지 / 역할별 표준화로 관리 간소화 / 권한 회수·변경이 쉬움

---

### 3-4. IAM Role Binding 두 가지 패턴

| 구분 | **#1 멤버에 역할 직접 부여** | **#2 역할 그룹을 멤버에 부여** |
|---|---|---|
| 방식 | 개별 멤버(NHN Cloud 계정/IAM 계정)에 특정 역할 직접 할당 | 역할 그룹을 만들어 멤버에게 부여 |
| 사용하는 역할 | **사전 정의된 역할** 사용 | **사용자 정의 역할** 사용 |
| 권한 조정 | — | **개별 권한 부여 및 거부 가능** |
| 조합 | — | 역할 그룹 생성 후 멤버에게 **사전 정의 역할 + 사용자 정의 역할** 부여 가능 |
| 예 | obsa@nhn.com / OBS-admin ← Object Storage ADMIN | "데이터베이스 관리자" 그룹 (RDS for MySQL/MariaDB/MS-SQL ADMIN) ← dba@nhn.com / DB-admin |

**#1이 유용한 경우**: 구성원이 적은 소규모 팀 / 단일 서비스 관리자 권한이 소수인 조직 / **임시 권한 부여**(PoC, 긴급 장애 대응, 단기 외주 인력 지원)
- 장점: 설정이 단순하고 즉시 반영, 임시 용도에 빠르게 대응
- ⚠ 한계: 멤버 수가 많아질수록 권한 중복·누락 위험 증가, 누가 어떤 권한을 가졌는지 **가시성 저하**, 인사 이동/퇴사 시 권한 회수 비용 증가, 과도한 권한 부여로 이어질 가능성
- 운영 팁: 직접 권한 부여는 **기한(만료일) + 부여 사유를 반드시 기록**. 프로덕션은 "Viewer 기본 + 필요한 권한만 추가" 원칙

**#2가 유용한 경우**: 직무 기반 권한(RBAC) 표준화가 필요한 조직 / 멤버 변동이 잦거나 팀·서비스 수가 많은 경우 / **보안 감사 요구사항(추적성·책임 분리)** 이 존재하는 환경 / 운영·개발·보안 역할이 명확히 구분되는 중대형 조직
- 장점: **일관성·확장성**(신규 직원은 그룹만 할당, 이동·퇴사는 그룹 회수만), **컴플라이언스 대응 용이**(직무→권한 구조가 명확해 감사 추적 용이), **오류 감소**(검증된 권한 묶음 재사용)
- ⚠ 주의: 역할 그룹 **난립 방지를 위한 명명 규칙 필요** (예: `RDS:Admin:Prod`, `OBS:Operator:Stg`, `Compute:Viewer:Dev`), 환경 분리(prod/stg/dev)를 역할 그룹 단위에서 명확히 구분, **분기 단위로 역할 그룹과 멤버 적합성 점검**(입·퇴사 반영, 팀 이동에 따른 권한 재정렬, 불필요한 권한 회수)

> **선택 기준**: 소수 사용자 / 단기 작업 / 제한된 범위 → **Role 직접 부여(#1)** · 다수 사용자 / 여러 서비스 운영 / 장기 운영 조직 / RBAC 표준화 필요 → **Role Group 기반 부여(#2) 권장**
> 공통 원칙: 최소 권한(Least Privilege), 기한/사유 관리, 권한·그룹 정기 점검

---

### 3-5. IAM 정책 ① 권한(Permission)

- 권한 = 리소스에 대해 특정 작업을 수행할 수 있는 **능력**, NHN Cloud 서비스와 기능을 이용하기 위한 **최소(가장 작은) 단위**
- 일반적으로 **사용자에게 직접 부여되지 않고** 역할 또는 역할 그룹을 통해 **간접적으로 부여**
- 권한을 묶어서 역할 또는 역할 그룹을 생성할 수 있음

**★ 권한 명명 규칙 — `[단위].[리소스].[권한]`**

| 작업 | 권한명 | 명명 규칙 |
|---|---|---|
| 조직 대시보드 수정 | `Organization.Dashboard.Update` | **[조직].[리소스].[권한]** |
| 프로젝트 대시보드 조회 | `Project.Dashboard.Get` | **[프로젝트].[리소스].[권한]** |
| 클라우드 모니터링 서비스 대시보드 조회 | `CloudMonitoring.Dashboard.Get` | **[서비스].[기능].[권한]** |

- 단위는 실제 관리 범위(**조직/프로젝트/서비스**)와 연결된다.
- 리소스는 **기능 단위**(대시보드, 인스턴스, 로그 등)를 의미한다.
- 행동(Get, Update, Delete 등)은 사용자가 수행할 수 있는 작업을 의미한다.

**권한과 역할의 관계 예시**
`Project.Payment.Get` 권한 → **Billing Viewer** 역할에 포함 → Billing Viewer 역할이 부여된 사용자만 결제 조회 기능 이용 가능

> IAM 정책 설계의 핵심: **"개별 권한 단위가 아니라 역할 단위로 접근 제어를 설계한다."**

---

### 3-6. IAM 정책 ② 역할(Role)

- 역할 = 리소스에 접근할 수 있는 권한을 **임시로 부여하는 신원(Identity)**
- 역할은 **누가(계정/서비스) 무엇에(리소스) 어떻게 접근**할 수 있는지 정의하는 것
- **하나 이상의 권한과 연관 역할의 집합**으로 구성. 필요한 경우 **다른 역할(Role)을 포함**할 수 있다.
- 사전 제공되는 **기본 역할**을 사용할 수도 있고, 조직 정책에 맞는 **사용자 정의 역할(Custom Role)** 구성 가능

**★ CloudTrail VIEWER 역할 구성 예시**

| 구분 | 내용 |
|---|---|
| 연관 역할 | `ORG_DASHBOARD_VIEWER` → 조직 단위 대시보드 조회 권한을 함께 사용하도록 포함된 역할 |
| 연관 권한 | `CloudTrail:EventLog.List` → CloudTrail 이벤트 로그 목록 조회 |
| 연관 권한 | `CloudTrail:ExternalStorageConfig.Get` → 외부 스토리지 연동 설정 조회 |

- **⚠ 연관 역할은 반드시 포함되는 요소가 아니며**, 서비스 특성이나 조직 요구에 따라 **선택적으로 구성**된다. ← 자주 나오는 함정
- **ADMIN과 같이 많은 연관 역할이 포함되어 있을 경우 특정 역할이나 권한을 "거부(Deny)"할 수 있다.**
- "사전 정의된 역할"과 역할 그룹을 통해 만들어진 "사용자 정의 역할"을 계정에 부여할 수 있다.

**설계 고려점**
- ADMIN처럼 많은 권한을 포함한 역할이 존재하지만, 운영 환경에서는 **최소 권한 원칙 기준으로 필요한 역할만 부여 권장**
- 역할 + 역할 그룹 조합 시 조직 전체 RBAC 적용이 더 간편 (예: 역할 그룹 `CloudTrail:Admin:Prod`)
- 역할 설계를 잘못하면 개별 권한 부여보다 오히려 복잡해질 수 있으므로 **서비스·조직 단위로 표준 역할 카탈로그 유지**

---

### 3-7. IAM 정책 ③ 역할 그룹(Role Group)

- 역할 그룹 = **여러 개의 역할(Role)을 묶어 관리**하거나, 사용자들에게 **공통된 권한 집합을 부여**하기 위해 만든 **논리적 그룹**
- 역할과 **연관 역할/권한, 권한을 조합해서 생성한 묶음 단위**
- 프로젝트에서는 역할 그룹을 생성하여 계정에 부여하며, **조직에서 "프로젝트 공통 역할 그룹"을 만들어 조직 내 전체 프로젝트에서 활용 가능**

**★ DBA 역할 그룹 구성 예시 (DBA Grp)**

| 포함 역할 | 포함 가능한 추가 권한 |
|---|---|
| RDS for MySQL ADMIN | `ObjectStorage:ProductAppKey.Get` |
| RDS for MariaDB ADMIN | → 오브젝트 스토리지 관련 설정 조회 등 부가 작업 |
| RDS for MS-SQL ADMIN | |

**★ 사전 정의 역할 vs 사용자 정의 역할 그룹**
- NHN Cloud가 제공하는 `RDS for MySQL ADMIN` 등 = **사전 정의 역할(Predefined Role)** — 서비스별 표준 권한 세트 제공
- 사용자가 여러 역할을 조합하여 만든 `DBA Grp` = **사용자 정의 역할 그룹(Custom Role Group)** — **업무·직무 기반 RBAC** 적용 가능

**활용 위치**
- **프로젝트 단위**: 프로젝트 내부에서 역할 그룹을 생성해 특정 사용자에게 부여. 서비스·업무 단위로 독립된 권한 구조를 만들 때 유용
- **조직 단위**: 조직 전체에서 공통으로 사용하는 역할 그룹을 만들면 **모든 프로젝트에서 재사용 가능** (예: 모든 팀에서 활용하는 Operator/Viewer 역할 그룹)

---

### 3-8. IAM 정책 ④ 조건(Condition)

- 조건 = 정책이 적용될 **세부 상황을 제한하거나 제어**하는 기능
- 조건은 시스템 내 접근 제어 등 **역할에 부여되는 단위**이며, **역할(Role)과 역할 그룹(Role Group)에 부여 가능**
- **시간, 요일, 날짜, 위치, IP 대역** 등 다양한 기준으로 세밀한 접근 제어 가능
- 권한을 상시 부여하지 않고 **특정 시간·상황에서만 활성화**되도록 하여 보안성을 높임

**★ 교재 예시 (user-dba)**

| 조건 유형 | 대상 역할 | 결과 |
|---|---|---|
| 요일 기반 | RDS for MySQL ADMIN, RDS for MS-SQL ADMIN (DBA Grp) | **화요일(Tuesday)에만** 부여 |
| 시간 기반 | Object Storage Object VIEWER | **매일 12:00~14:00** 사이에만 부여 |

**조건 활용의 장점 3가지**
1. **업무 시간대 제한** — 근무 시간 외에는 변경 권한이 자동 해제, 긴급 상황 외 권한 오남용 원천 차단
2. **네트워크 기반 제한** — 특정 사내망/VPN 연결 환경일 때만 권한 활성화, 외부 접속 시 중요 권한 자동 비활성화
3. **최소 권한 보장 (Just-In-Time Access)** — 필요한 순간에만 필요한 권한을 부여

> 조건은 단순히 "권한을 가진다/안 가진다"가 아니라 **언제(When) / 어디서(Where) / 어떤 조건에서(How)** 권한이 유효한지를 세분화한다.

---

### 3-9. ★★ 조건 상세 — 다중 조건의 교집합 (최빈출 계산 문제)

**시나리오**
- user1은 역할 그룹 **Group A**에 `(Project) ADMIN` 역할이 부여되어 있고, 이 역할 그룹에는 **매주 화요일에만** 역할이 부여되도록 조건이 추가됨
- user1에 **BILLING VIEWER** 역할을 부여하고, **매일 12시~14시에만** 역할이 부여되도록 조건 추가

**조건 적용 결과**

| 역할 | 부여 조건 | 최종 유효 시점 |
|---|---|---|
| (Project) ADMIN | 매주 화요일 | 매주 화요일 |
| BILLING VIEWER | 매일 12~14시 (+ 상위 역할 ADMIN의 조건 상속) | **매주 화요일 12시~14시** |

```
최종 적용 조건 = (화요일) ∩ (12시~14시)
```

- 조건은 **각각 독립적으로 적용**되며, 권한이 동시에 유효하려면 **모든 조건을 충족해야 한다.**
- **BILLING VIEWER의 상위 역할인 ADMIN에 조건이 설정되었으므로, BILLING VIEWER는 ADMIN의 조건을 상속받아 적용된다.** ← 핵심 함정
- 여러 역할을 동시에 가질 경우 **권한은 조건의 교집합으로 제한**된다.

> 설계 포인트: 역할을 많이 부여하는 것보다, **조건을 활용해 권한 사용 범위를 축소하는 것이 보안적으로 더 안전**하다. 멀티 프로젝트 환경에서는 조건을 통해 업무 창구를 제한하는 방식이 효과적이다.

---

### 3-10. ★★ 조직과 프로젝트의 역할 그룹·권한 부여 (최빈출 함정)

> **핵심 명제: "프로젝트 역할은 조직 단위에서 할당 및 상속은 불가합니다. 모든 권한은 프로젝트별로 직접 부여해야 합니다."**

| 구분 | 조직(Organization) | 프로젝트(Project) |
|---|---|---|
| 가능한 것 | **'프로젝트 공통 역할 그룹'을 통해 프로젝트 역할 생성 가능** | 모든 프로젝트에서 '프로젝트 공통 역할 그룹' **사용 가능** |
| 불가능한 것 | **계정에 역할 부여는 불가능 (상속 X)** | — |
| 성격 | **표준 정의 영역** (권한의 표준 템플릿 정의) | **실제 권한 부여 영역** (실행 영역, IAM 매핑 수행) |
| 효과 | 중앙 표준 관리 | **직무 기반 표준화**와 **감사 일관성** 확보 |

- 조직에서 만든 역할 그룹(예: `DB-admin` = RDS for MySQL/MariaDB/MS-SQL ADMIN)은 **모든 프로젝트에서 조회 및 사용 가능**
- 그러나 조직에서 **IAM 계정에 직접 프로젝트 서비스 역할을 바인딩할 수는 없다.**
- **※ 프로젝트 공통 역할 그룹은 조직에서만 수정 가능하다.** ← 자주 나오는 함정
- 모든 권한은 프로젝트별로 직접 부여되며, **상속 구조가 아니라 프로젝트 단위의 명시적 바인딩 구조**

```
조직 = 표준 정의     |     프로젝트 = 실제 권한 부여
```

**Advanced 설계 관점**: 대규모 환경에서는 조직에서 직무 기반 역할 그룹을 정의해 표준화하고, 각 프로젝트에서 필요한 IAM 계정에 해당 역할 그룹을 바인딩 → 직무 기반 권한 일관성 + 감사/컴플라이언스 대응 + 프로젝트 간 권한 관리 구조 통제를 동시 달성

---

### 3-11. 멤버 직접 부여 vs 프로젝트 공통 역할 그룹 — Primary/DR 실전 설계

**조직(표준 정의 영역)**
- 프로젝트 공통 역할 그룹 `Security-Audit` 정의
  - Security Advisor ADMIN
  - Security Compliance ADMIN
- 모든 프로젝트에서 공통 참조 가능. 단, 조직에서 직접 프로젝트 IAM 계정에 바인딩은 불가

**Primary 프로젝트 (`Shop-prod`, Region A)**

| IAM 계정 | 역할 | 조건 |
|---|---|---|
| 보안관리자 | Security-Audit | — |
| DB관리자 | **RDS for MySQL ADMIN** | 조건 1: 평일 09:00~18:00<br>조건 2: 접근 IP 192.168.100.123 |

→ **ADMIN 권한이라도 항상 활성화되지 않는다.** 시간과 IP 조건을 만족할 때만 권한이 발효 = **역할 + 조건을 결합한 동적 최소 권한**

**DR 프로젝트 (`Shop-DR`, Region B)**

| IAM 계정 | 역할 | 조건 |
|---|---|---|
| 보안관리자 | Security-Audit | — |
| DB관리자 | **RDS for MySQL VIEWER** | 조건 1: 평일 09:00~18:00<br>조건 2: 접근 IP 192.168.100.123 |

→ DR은 기본적으로 **읽기 전용(READ-ONLY) 전략**을 유지하고, 장애 상황 등 특별한 경우에만 역할을 변경한다. DR 환경에서의 **불필요한 변경 작업을 사전에 차단**.

**Direct Role 반복 부여의 한계**: 프로젝트마다 동일 역할 반복 바인딩 / 인원 증가 시 권한 중복·누락 가능성 증가 / 감사 시 추적 복잡도 상승
**프로젝트 공통 역할 그룹의 장점**: 직무 기반 권한 표준화 / 프로젝트 간 일관성 확보 / 감사 및 컴플라이언스 대응 용이

**설계 포인트 3줄 요약**
- 프로젝트 공통 역할 그룹은 **조직에서 정의**하고, 프로젝트별 역할 및 조건은 **프로젝트에서 정의 후 멤버에 매핑**한다.
- 사전 정의된 역할 사용 시 불필요한 연관 역할/연관 권한은 **거부(Deny) 정책으로 정제**한다.
- **리전 전략(Primary/DR)과 IAM 모델은 함께 설계**해야 한다.

### 3-12. ★★ 허용 / 조건 / 거부 모델 (정책 평가 순서)

```
최종 권한 = (허용 ∩ 조건) − 거부
```

**평가 순서 (순서 배열형 문제 대비)**
1. **명시적 '거부(Deny)' 정책 우선 적용** — 거부 정책이 존재하면 해당 요청은 **즉시 차단**
2. **'허용(역할/권한)' 정책 확인** — 거부가 없으면 허용 정책 존재 여부 확인
3. **허용 정책의 '조건' 충족 여부 평가** — 허용 정책에 조건이 포함되어 있다면, 조건을 만족해야 권한이 실제로 적용

→ **조건을 만족하지 않으면 허용 정책이 있어도 권한은 적용되지 않으며, 명시적 거부가 존재하면 허용 정책보다 우선하여 접근이 차단된다.**

**조건의 역할 (사용 조건 제어)** — 조건은 **허용 정책을 무력화하는 것이 아니라, 허용된 권한의 사용 범위를 제한하는 역할**을 한다.
- 업무 시간 기반 접근 제한 (예: 관리자 권한은 평일 09:00~18:00 사이에만 사용 가능)
- 네트워크(IP/VPN) 기반 접근 통제 (사내망 또는 VPN 접속 시에만 권한 허용)
- 환경(Prod/Dev)별 권한 범위 제한 (운영은 제한적, 개발은 상대적으로 넓은 권한)

**거부 전략 (Guardrail 레이어)**
- 거부 정책은 IAM 설계에서 **가장 강력한 통제 수단**이며, 보통 **조직 전체에 적용되는 보안 가드레일**로 활용
- 대표적 **고위험 차단 대상**: **리소스 삭제(Delete) / 암호화 키 관리 / Public 설정 변경 / 외부 공개 설정**
- **멀티 테넌트 환경이나 MSP 환경에서 공통 보안 기준을 강제하는 수단**으로 사용
- 환경별 정책 강도 차등: **Prod 환경은 강한 Deny 정책**, **Dev/Stg 환경은 상대적으로 완화된 정책**

**설계 판단 기준**
- **허용 설계보다 '금지 기준(거부)'을 먼저 정의**한다.
- 멀티 테넌트/MSP 환경에서는 거부를 **표준 가드레일**로 활용한다.
- '조건'과 결합하여 '언제·어디서·무엇을' 통합 통제한다.

**★ 설계 순서 (암기)**

```
Guardrail(Deny) → Capability(Allow) → Usage Condition(Condition)
```

> "IAM 설계는 **가드레일(Deny) → 권한(Allow) → 조건(Condition)** 순서로 계층적으로 설계합니다."
> 즉, 먼저 조직 차원의 보안 기준을 정의하고(Deny), 그 위에 필요한 권한을 설계한 뒤(Allow), 마지막으로 권한의 사용 조건을 제한(Condition)하는 방식.

## 4. 성공적인 아키텍처를 위한 첫 번째 원칙: 배치와 통제

> **"어디에 배포하고(가용성), 어떻게 나누며(격리), 누구에게 권한을 줄 것인가(보안)가 아키텍처의 품질을 결정합니다."**

### 4-1. 물리적 배치 (Deployment) — 가용성 확보

핵심 질문: **"서비스가 중단되지 않으려면 어디에 두어야 하는가?"**

| 상황 | 권고 구성 |
|---|---|
| 운영(Prod) 환경 | **Multi-AZ(다중 가용성 영역) 구성을 기본 원칙**으로 — 단일 AZ 의존 시 해당 데이터 센터 장애가 서비스 전체 중단으로 이어짐 |
| 개발(Dev) 환경 | 비용 최적화를 위해 **Single AZ** 사용하되, **스냅숏이나 이미지를 활용한 복구 전략** 마련 |
| 확장성 / DR·Global | **Multi-Region + GSLB**로 지역적 장애까지 대비 |
| Hybrid | 레거시 연동 시 **전용회선 및 VPN 활용** |

### 4-2. 논리적 격리 (Hierarchy) — 운영 리스크 관리

핵심 질문: **"운영 중 실수를 방지하기 위해 어떻게 나눌 것인가?"**

- **프로젝트 중심의 환경 격리**: 개발(Dev), 스테이징(Stg), 운영(Prod)을 하나의 프로젝트에 섞지 말 것. 권한 실수로 운영 데이터를 삭제하는 사고를 막기 위해 **환경별로 서로 다른 프로젝트를 생성**하여 논리적으로 완전히 격리
- **공통 인프라 분리**: CI/CD 파이프라인, Bastion Host, 로깅 서버 등은 별도의 **'Management Project'** 또는 **'Shared Infra Project'** 로 분리해 중앙 관리
- **운영 표준화**: `[조직]-[환경]-[서비스]-[리소스]` 형태의 표준 명명 규칙 + 비용 추적을 위한 **필수 태그(Tagging, 예: Env, Owner)** 정책을 초기부터 적용

### 4-3. 접근 제어 (IAM & Security) — 최소 권한 보안

핵심 질문: **"누구에게, 어디까지 허용할 것인가?"**

- **역할 그룹(Role Group) 활용**: 사용자(Member)에게 개별적으로 권한을 주면 퇴사나 부서 이동 시 관리가 불가능 → 'DBA 그룹', '개발자 그룹'처럼 **역할 그룹을 만들어 권한을 할당**
- **계정 분리**: NHN Cloud에 가입한 이메일 계정(루트/결제 계정)은 **일상적인 운영에 사용해서는 안 된다.** 운영을 위해서는 별도의 **IAM 계정을 생성하여 사용**하고, 루트 계정은 **결제 및 최상위 정책 관리에만 제한적으로** 사용
- **조건(Condition) 기반 통제**: 단순히 ID/PW만 믿지 말고 **MFA(다중 인증)를 강제**하고 **사내망 IP나 업무 시간 등 특정 조건에서만** 중요 권한이 작동하도록 설정

> 이 3가지는 건물을 짓기 전 땅을 고르고(배포), 구획을 나누고(계층), 울타리를 치는(IAM) 기초 공사다.

## 5. 🎯 자주 나오는 함정 포인트

### A. 배포 패턴

1. **단일 리전(멀티 AZ) 배포도 리전 전체 장애에는 취약하다.** "멀티 AZ면 리전 장애도 대응 가능"은 오답.
2. **멀티 리전 배포의 보조 리전은 '축소 구성(reduced footprint)'으로 운영 가능**하다. "보조 리전은 반드시 주 리전과 동일 규모"는 오답.
3. **RDS 교차 리전 읽기 복제본은 보조 리전에서 '읽기 전용'** 이다. **쓰기는 리전 피어링을 통해 주 리전 마스터 DB에 수행**한다.
4. 복제 방식: **동기 = 높은 일관성 + 큰 지연**, **비동기 = 성능 우수 + 일관성 지연 가능**. 서로 바꿔 놓은 보기 주의.
5. **스토리지 복제는 데이터 양이 적을수록 유리**, **대용량은 스냅샷 기반 복구가 더 유리**(블록 단위 저장).
6. 이미지·복제·스냅샷 작업 시 정합성을 위해 **인스턴스 일시 중지 후 작업 권장**.
7. **백업은 복제·스냅샷과 별개**로 반드시 수립해야 하며, 단일 AZ에서는 **최후의 보호 장치**다.
8. 하이브리드/멀티 클라우드 연결 옵션은 **Direct Connect(Hosted Connection) / Network Firewall IPSec VPN / VPN Gateway(Site-to-Site)** 3종. 다른 서비스명이 섞이면 오답.
9. **Direct Connect(Hosted Connection)는 파트너 네트워크 플랫폼을 통해 온프레미스·타사 클라우드와 전용 회선을 동시에 연결 가능**하다.
10. 해당 국가에 **리전이 하나뿐인 경우** 다른 CSP 리전 또는 오프라인 스토리지 활용도 고려 대상이다.
11. 멀티 리전에서 **DR 테스트 계획 수립은 필수**다. "복제만 구성하면 충분"은 오답.

### B. 프라이빗 클라우드 3종

12. **Private Deck = VLAN / Private Station·Region = VxLAN(멀티 테넌트)**. 네트워크 방식 바꿔치기 주의.
13. **가용성(AZ): Deck 1개, Station 1개, Region 2개.** "Station도 멀티 AZ"는 오답.
14. **구축 기간: Deck 1개월 이내 → Station 2개월 → Region 5개월.**
15. **규모: Deck 240~960 VM(2 Rack Gold) / Station 600~3,000 VM(최대 3개 Rack) / Region 1,000~10,000 VM 이상.**
16. **관리 주체: Deck만 고객 직접 관리 가능**, Station·Region은 NHN Cloud 전담 엔지니어 운영.
17. **이용 방식: Deck만 '구매 / 구독' 선택 가능**, Station·Region은 구독만.
18. VM 산정 기준은 **4 core, 8 GB Memory**. Private Deck은 **1:1 ~ 4:1 오버커밋** 가변 적용 가능.
19. **Private Deck은 독립 구축형(상위 리전 연동 X)**, **Private Station은 연동 구축형(상위 리전과 연동 O)**.
20. Deck/Station은 Single AZ지만 **내부 컴포넌트 이중화로 안정성은 확보**한다. "Single AZ = 이중화 없음"은 오답.

### C. 리소스 계층 구조

21. **계층은 조직 → 프로젝트 → 리소스 3계층.** 리소스가 조직 바로 아래에 붙는 구조가 아니다.
22. **비용 청구의 단위는 조직**, **비용·사용량 추적(집계) 단위는 프로젝트**. 둘을 혼동하게 만드는 보기 주의.
23. **IAM 공통 보안 정책(MFA 의무화, 비밀번호 정책, 공통 태그 표준)은 조직 레벨**에서 설정한다.
24. dev/stg/prod를 하나의 프로젝트에 혼재시키는 것은 대표적 안티패턴 → **환경별 프로젝트 분리**.
25. 환경별 분리 시 공통 리소스(logging, Bastion, CI/CD) 중복 문제 → **"공통 인프라 프로젝트"** 별도 운영.
26. 팀별 분리 시 정책 편차 문제 → **"가드레일 정책"**(네이밍/보안 그룹/이미지·패치 기준) 필수.
27. 실무에서 **가장 많이 쓰이는 것은 혼합 구성**(서비스 단위 프로젝트 + 환경 접미사).
28. 권한·프로젝트 구성·태그 점검은 **분기 단위 정기 리뷰**.

### D. 명명 규칙

29. 표준 구조는 **[조직/부서]-[환경]-[서비스명]-[리소스유형]-[리전]-[고유식별자]** — 순서를 바꾼 보기 주의.
30. 리전 코드는 이름 안에 **포함**된다(kr1, jp1). "리전은 태그로만 관리"는 오답.

### E. 계정 / IAM

31. **NHN Cloud 계정 = 조직 OWNER 자동 보유, 삭제 불가(권한 위임만 가능)** / **IAM 계정 = 잠금·삭제·역할 변경 가능**.
32. **콘솔이 다르다**: NHN Cloud 계정 → **NHN Cloud 콘솔**, IAM 계정 → **IAM 콘솔**.
33. **2차 인증은 두 계정 모두 이메일·휴대폰·OTP를 지원**한다. "IAM 계정은 OTP 미지원" 류는 오답.
34. **결제 관리는 NHN Cloud 계정의 역할**. IAM 계정에 결제 관리를 맡기는 보기는 오답.
35. **CI/CD·자동화 스크립트에는 IAM 시스템 계정을 사용**한다. 루트(NHN Cloud) 계정 사용은 오답.
36. **IAM은 권한을 최종 사용자에게 직접 할당하지 않는다.** 구조는 **Permission → Role → User**.
37. **Role Binding #1(직접 부여)은 사전 정의된 역할 사용**, **#2(역할 그룹)는 사용자 정의 역할 사용 + 개별 권한 부여 및 거부 가능**.
38. 직접 부여는 **임시/단기 권한**(PoC, 긴급 장애, 단기 외주)에 적합하며 **기한(만료일) + 사유 기록** 필수.
39. **권한 명명 규칙 = [단위].[리소스].[권한]** — `Organization.Dashboard.Update`, `Project.Dashboard.Get`, `CloudMonitoring.Dashboard.Get`.
40. **역할의 '연관 역할'은 반드시 포함되는 요소가 아니다**(선택적 구성). "역할에는 항상 연관 역할이 포함된다"는 오답.
41. **ADMIN처럼 연관 역할이 많은 경우, 특정 역할이나 권한을 '거부(Deny)'할 수 있다.**
42. **사전 정의 역할(Predefined Role)** = NHN Cloud 제공(RDS for MySQL ADMIN 등) / **사용자 정의 역할 그룹(Custom Role Group)** = 사용자가 조합(DBA Grp).
43. **조건은 역할과 역할 그룹 모두에 부여 가능**하다. "역할에만 부여 가능"은 오답.
44. **조건이 여러 개면 최종 권한은 교집합(∩)** 이다. 합집합으로 계산하게 만드는 보기 주의.
45. **상위 역할에 조건이 설정되면 하위 역할이 그 조건을 상속받는다.** (화요일 ∩ 12~14시 → 매주 화요일 12~14시)
46. **조직에서는 계정에 역할을 부여할 수 없다(상속 X).** 프로젝트 역할은 **프로젝트별 직접 부여**만 가능.
47. **프로젝트 공통 역할 그룹은 조직에서만 수정 가능**하다. 프로젝트에서는 **참조·사용**만 한다.
48. **정책 평가 순서: 명시적 거부(Deny) → 허용(Allow) → 조건(Condition) 충족 평가.** 거부가 항상 우선.
49. **최종 권한 = (허용 ∩ 조건) − 거부.** 조건 미충족이면 허용 정책이 있어도 권한이 적용되지 않는다.
50. **IAM 설계 순서: Guardrail(Deny) → Capability(Allow) → Usage Condition(Condition).** 허용부터 설계하는 보기는 오답.
51. **거부 정책의 대표 차단 대상: 리소스 삭제, 암호화 키 관리, Public 설정 변경, 외부 공개 설정.**
52. **Prod는 강한 Deny, Dev/Stg는 완화된 정책** — 환경별 정책 강도 차등이 원칙.
53. **조건은 허용 정책을 무력화하는 것이 아니라 허용된 권한의 '사용 범위'를 제한**한다.
54. **DR 프로젝트는 기본적으로 읽기 전용(VIEWER) 전략**을 유지하고 장애 시에만 역할 변경. Primary와 동일하게 ADMIN을 부여하는 보기는 오답.
55. **ADMIN 권한이라도 조건(시간·IP)을 만족하지 않으면 활성화되지 않는다.**
56. 역할 그룹 난립 방지를 위한 **명명 규칙 필요** (예: `RDS:Admin:Prod`, `OBS:Operator:Stg`, `Compute:Viewer:Dev`).
