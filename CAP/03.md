## 1. DNS

### 1-1. NHN Cloud DNS 4종 비교

| 구분 | 내부 DNS | Private IP DNS | Private DNS | DNS Plus |
|---|---|---|---|---|
| **관리 주체** | NHN Cloud | NHN Cloud | **고객** | **고객** |
| **사용 범위** | 인스턴스 기본 DNS / 서비스 엔드포인트 도메인 관리 | VPC 내부 인스턴스 간 이름 해석 | 내부 전용 도메인 관리 | **외부 인터넷 사용자 대상** |
| **특징** | 기본 제공, 고객 수정 불가 | 사설 IP 기반 자동 이름 생성 및 내부 해석 | Zone 단위 관리, 멀티 VPC 가능, 내부 전용 | 전세계 분산 DNS(Anycast) / 대규모 질의 처리 / DDoS 완화 |
| **장점** | 설정 필요 없음 | 내부 통신 단순화, 설정 필요 없음 | 내부망 보안 강화, 일관된 네이밍 정책 유지 | 글로벌 서비스 대응, 안정성·성능 우수 |
| **제약** | 고객 직접 관리 불가 | **멀티 VPC·온프레미스 연동은 제한적** | **외부 접근 불가** | **외부 등록기관에서 도메인 구입 필요** |
| **대표 활용** | 인스턴스 기본 네임 서버, NHN Cloud 서비스 엔드포인트 관리 | VPC 내부 앱 간 통신 | 인트라넷·MSA·테스트 환경, 내부 도메인 운영 | 웹/앱 글로벌 서비스 운영 |

> **설계 판단 기준 한 줄**: "서비스 노출 범위(Internal vs External)" + "DNS 관리 범위(NHN Cloud vs 고객)"

### 1-2. 내부 DNS (3계층)
1. **인스턴스 기본 퍼블릭 DNS** — 인스턴스 생성 시 DNS Client에 자동 설정. `resolvectl`로 1차/2차 NHN Cloud DNS 확인 가능. 외부 도메인 조회용.
2. **Private IP DNS** — 고객이 DNS를 보유하지 않아도 VPC 내부에서 사설 IP 기반 조회 가능. 형식 `ip-10-1-1-33.kr1.nhncloud.internal`
3. **서비스 관리 DNS** — RDS, EasyCache, NKS, NCS 등 **서비스별 엔드포인트 도메인 전용 DNS를 별도 운영**
   - `xxxx.internal.kr1.mysql.rds.nhncloudservice.com`
   - `xxxxxxxx-nks-kr1.container.nhncloud.com`
   - `xxxxxxxx-kr1-ncs.container.nhncloud.com`

> ⚠️ **함정**: 서비스 엔드포인트 도메인은 **Google·KT 등 외부 Public DNS에서도 사설 IP가 조회된다.**
> 반면 **Private IP DNS로 부여된 도메인이나 Private DNS 관리 도메인은 퍼블릭 DNS에서 조회 불가**다.

### 1-3. Private IP DNS
- 네트워크 인터페이스 **생성 시 자동으로** 이름 생성
- VPC에서 Private IP DNS 기능을 **활성화하지 않아도** VPC 내 인스턴스·서비스에서 프라이빗 IP DNS 이름 **수신**은 가능 (활성화해야 DNS 포트가 생성되어 질의 가능)
- **제약사항**
  - 피어링된 VPC 간: DNS 서버를 직접 배포하거나 Private DNS 사용 필요
  - **두 개 이상의 서로 다른 VPC 포트를 가진 인스턴스는 Private DNS 동작을 보장하지 않음**
  - 온프레미스 연동: 자체 DNS 서버 배포 필요

### 1-4. Private DNS
- **프로젝트 내 동일 리전의 VPC**에서만 사용 가능
- 하나의 **Zone(도메인 영역)에 한 개 이상의 VPC를 바인딩**
- Zone에 연결된 **VPC별로 Private DNS Network Interface가 생성** → **VPC별 독립된 Private DNS Server IP**
- IP 주소와 함께 내부 도메인 생성: `ns.private-dns.nhncloud.internal`
- **Zone 외부에서 요청하면 응답 없음** (내부 전용)
- 단, **VPC 내부 인스턴스는 외부 등록기관에 등록된 도메인 요청에도 응답받을 수 있음**

**Private DNS 활용 장점**
- 보안: 외부 DNS 서버를 거치지 않아 DNS Spoofing 등 외부 공격 가능성 낮음
- 성능: 내부에서 직접 질의·응답 → 응답 속도 빠름
- 운영: Service Gateway 연계 시 **OS의 `/etc/hosts` 파일을 직접 수정할 필요 없음**

> 🔑 **자주 나오는 시나리오**: RDS 마스터 장애 → 마스터 인스턴스 IP가 재바인딩되지만 **도메인 이름은 변경되지 않는다.**
> 외부 DNS 사용 시 변경 전파에 시간이 걸려 재연결 지연 → **Private DNS를 쓰면 내부 DNS에 즉시 반영되어 신속한 IP 업데이트**가 가능.
> 단, **DNS 바인딩 변경을 감지하지 못하는 클라이언트는 기존 세션이 끊긴 후 재접속이 필요** → DNS 캐시 정책 및 재연결 로직을 사전 설계해야 함.

### 1-5. DNS Plus
- 별도 DNS 서버 설치 없이 **웹 콘솔에서 DNS 작업 수행**
- **글로벌 Anycast 네트워크** 기반 — 전 세계 네임서버 중복 배치, 높은 가용성·짧은 지연
- DNS 대상 **DDoS 공격 완화** 기능 제공
- ⚠️ **DNS Plus로 도메인을 구입할 수는 없다** (등록 기능 미제공 → 외부 등록기관 구매 후 연결)

## 2. Routing

### 2-1. 기본 라우팅 테이블
- VPC 생성 시 **자동 생성**
- **VPC CIDR → local** 규칙 자동 포함, **사용자가 임의로 삭제 불가**
- **local 게이트웨이** = VPC 내 암시적 라우터. **사용자가 임의로 생성·삭제 불가**
- **기본 라우팅 테이블은 VPC당 1개만 지정 가능**
- 인터넷 게이트웨이를 라우팅 테이블에 연결하면 **0.0.0.0/0 → 인터넷 게이트웨이 규칙이 자동 추가**

### 2-2. 암시적 연결 vs 명시적 연결

| 구분 | 암시적(Implicit) 연결 | 명시적(Explicit) 연결 |
|---|---|---|
| 정의 | 새 서브넷이 자동으로 기본 라우팅 테이블에 연결 | 서브넷을 특정 라우팅 테이블에 직접 연결 |
| 콘솔 표기 | **"기본 연결"** | 지정한 라우팅 테이블명 |
| 규칙 적용 | 기본 라우팅 규칙을 따름 | **더 이상 기본 라우팅 테이블 규칙을 따르지 않음** |
| 용도 | 기본 동작 | 퍼블릭/프라이빗 서브넷 분리 설계 |

**라우팅 테이블 규칙 (숫자 암기)**
- 하나의 **서브넷은 동시에 1개의 라우팅 테이블에만** 연결 가능
- 하나의 **라우팅 테이블에는 여러 서브넷을 동시에** 연결 가능

### 2-3. 게이트웨이 라우팅 테이블
- **라우팅 테이블을 지원하는 게이트웨이 유형: Peering Gateway, Transit Hub** — 이 둘뿐
- ⚠️ **VPC 로컬 게이트웨이는 VPC 라우팅 테이블이 아니므로 라우팅 규칙이 없다**
- Peering Gateway: 로컬 VPC 라우팅 테이블 + 피어 VPC 라우팅 테이블 존재. **명시적 연결(Explicit association) 방식은 미지원**
- 게이트웨이 타입으로 지정 가능한 것: **Transit Hub, Network Firewall 같은 중앙 게이트웨이 또는 Instance(Virtual Appliance)**

### 2-4. 서브넷 정적 라우트
- **DHCP 옵션(classless-static-routes)** 을 통해 인스턴스 **내부 라우팅 테이블**에 경로를 자동 등록
- **VPC 라우팅 테이블 = 네트워크 계층 전체 경로 제어 / 서브넷 정적 라우트 = 인스턴스 내부 라우팅 동작 제어**
- 등록된 라우팅 규칙은 인스턴스가 DHCP 요청을 보낼 때 응답 패킷에 포함되어 전달
- ⚠️ **일반적으로 최초 부팅 시 적용**되며, DHCP 임대 갱신 시에는 반영되지 않는 경우가 많음
  → 변경 적용하려면 **인스턴스를 재부팅하거나 DHCP 클라이언트를 재시작**
- 구성: **대상 CIDR + 게이트웨이 IP** (텍스트 형태 IP로만 지정, 게이트웨이 유형 지정 불가)
- CIDR을 `0.0.0.0/0`으로 지정하면 기본 게이트웨이를 다른 인스턴스 IP로 대체 가능
- 게이트웨이는 **서브넷 내 특정 인스턴스 IP** 지정이 일반적 (미사용 IP도 지정 가능하나 운영상 비권장)
- ⚠️ **멀티캐스트는 등록 불가**
- 실행중 인스턴스 반영: 일반 로드밸런서는 설정 변경, **NKS 로드밸런서는 재배포**

## 3. 다중 VPC 설계

- VPC는 기본적으로 **서로 통신이 불가능한 상태**로 생성됨
- ⚠️ **프로젝트마다 VPC는 기본 3개까지 생성 가능, 필요 시 쿼터 조정 신청 가능**
- 분리 기준: ① 환경별(개발/테스트/운영) ② 애플리케이션·워크로드별(APP1/APP2/공용서비스)

## 4. Peering Gateway

### 4-1. 핵심 제약 (단골 출제)
- **Private IP 주소 범위가 겹치면 피어링 불가**
- **1:1 연결만 지원** — 하나의 Peering은 두 VPC 간에만
- **전이적 피어링(Transitive Peering) 미지원** — A↔B, B↔C 연결 시 A↔C는 자동 연결되지 않음. A와 C도 별도 Peering 필요
- **Peering Gateway 자체는 무료**, 전송되는 **네트워크 트래픽 비용은 별도 과금**

### 4-2. 연결 복잡도 공식
> **VPC N개를 전부 상호 연결 → 연결 수 = N(N−1)/2**

| VPC 수 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 연결 수 | 0 | 1 | 3 | 6 | 10 |

→ 규모가 커지면 **Hub & Spoke(Transit Hub)** 도입이 정석 답안

### 4-3. Peering 3유형

| 유형 | 리전 | 프로젝트 | 추가 요건 |
|---|---|---|---|
| **VPC Peering** | 동일 리전 | 동일 프로젝트 | — |
| **Project Peering** | **동일 리전에서만 가능** | 다른 프로젝트(다른 조직 포함) | **허용 대상 테넌트 ID, VPC ID 등록 필요** |
| **Region Peering** | **다른 리전** | 동일/다른 프로젝트 모두 가능 | **허용 대상 테넌트 ID, VPC ID 등록 필요** + 지연·요금 증가 |

> 범위 확장 순서: **VPC Peering → Project Peering → Region Peering**

### 4-4. Packet Flow
- 피어링 게이트웨이 생성 시 **연결된 VPC에 네트워크 인터페이스가 생성**되고, 연결된 VPC의 서브넷 중 임의로 하나를 선택해 IP를 할당받음
- **피어링 게이트웨이는 라우터처럼 경로를 재계산하거나 중간 라우팅을 수행하지 않고, 출발지에서 목적지 VPC로 직접 전달**
- Subnet1 → Subnet2 전송 시 **VPC2 라우터를 통과하지 않고** 목적지 인스턴스로 직접 전달 → **추가 홉(Hop) 미발생**

### 4-5. 피어링 라우팅 테이블 (HUB-SPOC 구조)
- Peering Gateway 자체는 전이적 피어링 미지원이지만, **피어링 라우팅 테이블을 활용하면** 특정 트래픽을 Virtual Appliance나 Transit Hub로 경유시킬 수 있음
- **목적지 라우팅 테이블에서만 경로를 지정하면 됨**
- 설정 메뉴 위치
  - VPC 피어링: **'로컬 라우트', '피어 라우트' 메뉴**
  - 리전/프로젝트 피어링: 각각 **'라우트' > '라우트 변경' 메뉴**

## 5. Transit Hub

### 5-1. 3대 구성 요소

| 요소 | 내용 | 핵심 제약 |
|---|---|---|
| **Attachment(연결)** | Transit Hub와 VPC 리소스를 연결하는 단위 | **서브넷 지정 필수**. 동일 서브넷은 **1개의 Attachment만** 생성 가능. Attachment 생성 시 해당 서브넷에 **Network Interface 자동 생성** |
| **라우팅 연결(Association)** | Transit Hub 라우팅 테이블에 Attachment를 연결해 트래픽 경로 정의 | **하나의 Attachment는 1개 라우팅 테이블에만 연결 가능** |
| **라우팅 전파(Propagation)** | VPC CIDR 정보를 Transit Hub 라우팅 테이블에 자동 전파 | VPC CIDR 변경 시 자동 반영 |

> 동작 순서: **Attachment → 라우팅 연결(Association) → 라우팅 전파(Propagation)**

- Transit Hub 생성 시 **[기본 라우팅 테이블 연결]** 옵션 활성화 → Attachment 생성 시 기본 라우팅 테이블에 **암시적으로 자동 연결**
- **[기본 라우팅 테이블 전파]** 옵션 활성화 → Attachment의 CIDR 정보 자동 전파
- 두 옵션 모두 **생성 시 기본값(default)이 활성화**

### 5-2. VPC 기반 라우팅 vs Transit Hub 기반 라우팅

| 특징 | VPC 기반 라우팅 제어 | Transit Hub 기반 라우팅 제어 |
|---|---|---|
| 제어 위치 | VPC 서브넷 라우팅 테이블에서 **분산 제어** | Transit Hub 라우팅 테이블에서 **중앙 집중 제어** |
| Transit Hub R.T. 수 | **하나** (기본 R.T. 사용, 간소화) | **다수** (정책별 분리) |
| VPC R.T. 복잡도 | **복잡**(각 목적지 VPC에 대한 규칙 필요) | **간소화**(Transit Hub로만 보냄) |
| 주요 장점 | Transit Hub 설정 간소화, VPC별 독립 제어 | 중앙 집중식 관리 용이, 보안 정책 명확 |
| 주요 단점 | VPC R.T. 설정 복잡도 증가, 관리 분산 | Transit Hub R.T. 설정 복잡도 증가 |
| **선택 시점** | **VPC 수가 적고 운영 유연성이 중요할 때** | **강력한 중앙 통제 및 엄격한 보안 분리가 필요할 때** |

### 5-3. VPC 내 서브넷이 여러 개일 때 Attachment 설계

| 방식 | 구성 | 언제 쓰나 |
|---|---|---|
| **1개 서브넷에만 Attachment 생성** | VPC 내부 통신은 Transit Hub를 거치지 않고 VPC 내부에서 라우팅, VPC 외부 통신만 Transit Hub 경유 | **VPC 내부 통신은 Transit Hub를 사용하고 싶지 않을 때**. Attachment 수 감소 → **비용 절감** |
| **서브넷마다 Attachment 생성** | VPC 내부/외부 통신 모두 Transit Hub 경유 | **서브넷 간 통신도 Transit Hub를 통해 라우팅하고 싶을 때**. Network Firewall로 서브넷 중앙 통제 가능 |

### 5-4. 다중 프로젝트 연결 (공유)
- **조직 내 동일 리전**에 존재하는 프로젝트에만 공유 가능
- Transit Hub가 있는 프로젝트에서 **공유 대상 프로젝트의 테넌트 ID를 반드시 입력**
- 공유받은 프로젝트는 **Attachment만 생성**하여 공유 트랜짓 허브에 연결 (별도 라우팅 테이블 없음)
- ⚠️ **함정**: 공유받은 프로젝트에서 생성한 Attachment는 **기본 라우팅 테이블 연결과 전파가 자동으로 수행되지 않는다.**
  → **Transit Hub가 있는 프로젝트의 관리자가 공유 트랜짓 허브 라우팅 테이블에 명시적으로 연결**해야 함. 라우팅 전파도 필요 시 수동 설정.

### 5-5. 리전 간 전이적 통신
- **Transit Hub는 리전 간 직접 공유 불가**
- **VPC Peering도 기본적으로 전이적 관계(Transitive Routing) 미지원**
- **해결책**: 리전 A의 VPC와 리전 B의 VPC를 **리전 피어링**으로 연결.
  **도착지 네트워크에 Transit Hub 같은 라우팅 리소스가 존재하면 전이적 관계를 허용할 수 있음**
- 경로 예시: 리전A VPC1 → 리전A Transit Hub → 리전A VPC2 → (피어링 게이트웨이, **L2 수준으로 그대로 전달**) → 리전B VPC11 → 리전B Transit Hub → 리전B VPC12

### 5-6. Transit Hub Multicast

| 제약 구분 | 내용 |
|---|---|
| **시작 전 필수** | 생성 시 **'멀티캐스트 지원(Multicast Support)' 옵션 선택 필수**. ⚠️ **미선택 시 사후 사용 불가(수정 불가) → Transit Hub 삭제 후 재생성해야 함** |
| **연결 범위** | **VPC 타입 연결(Attachment)만** 멀티캐스트 도메인에 연결 가능 (2025년 12월 기준). **VPN Gateway·Direct Connect 연결은 미지원** |
| **프로젝트 공유** | **타 프로젝트에서 공유받은 Attachment는 멀티캐스트 구성에 사용 불가** → 단일 프로젝트 내 리소스로만 한정 |
| **서브넷 배타적 사용** | **1 Subnet = 1 Multicast Domain**. 하나의 서브넷은 NHN Cloud 전체에서 단 1개의 멀티캐스트 도메인에만 속할 수 있음 |
| **운영 방식** | **정적(Static) 모델. IGMP/PIM 미사용** — 서버의 Join/Leave 메시지 무시. **콘솔/API로 소스·멤버 직접 등록 필수** |
| **소스/멤버 규칙** | **1개의 소스와 N개의 멤버** 등록 가능 |
| **라우팅** | **OS 직접 라우팅 설정 필수** (예: `ip route add 239.0.0.0/16 dev eth0`). ⚠️ **콘솔의 '서브넷 정적 라우트' 기능은 멀티캐스트 경로 지정 불가** |
| **소스 IP** | 반드시 **멀티캐스트 도메인에 연결된 서브넷 대역 내** IP여야 함 |
| **보안** | ⚠️ **멀티캐스트 그룹 IP(예: 239.x.x.x) 대상으로는 SG/NACL 규칙이 적용되지 않음**. 보안은 **최종 수신 인스턴스(Member)의 유니캐스트 IP/포트 레벨**에서 관리 |

**멀티캐스트 구성 4단계 (순서 출제 가능)**
1. Transit Hub 및 Attachment 생성 (Multicast Enable)
2. 멀티캐스트 도메인 및 연결 생성 (Source·Member VPC 모두 연결)
3. 멀티캐스트 그룹에 소스와 멤버 등록 (Control Plane — 콘솔/API, IGMP 대신)
4. 서버 설정 및 통신 테스트 (Data Plane — OS `ip route add`, tcpdump 검증)

> 왜 SG/NACL이 안 먹나: Transit Hub 멀티캐스트는 일반 라우팅 경로가 아닌 **전용 멀티캐스트 복제 엔진**으로 전달되며, 이 엔진은 **유량 상태 저장(Stateful) 검사 과정을 건너뛰고 패킷을 복제**하기 때문.
> 또한 **대상 식별의 모호성**: 보안 그룹은 '출발지 IP/포트'와 '목적지 IP/포트'를 기준으로 막는데, 멀티캐스트 목적지 IP는 특정 장비 주소가 아닌 '그룹 주소'이기 때문.

## 6. 여러 VPC 연결 옵션 종합 비교

| 구분 | 장점 | 단점 |
|---|---|---|
| **Transit Hub**<br>→ 중앙 관리와 확장성 | 단일 게이트웨이를 통한 중앙 집중식 연결 / VPC의 라우팅 테이블 자동 전파 / 보안 로그 중앙화 용이 | **VPC 간 중첩된 IP 주소 범위 사용 불가** / **Attachment당 비용과 추가 트래픽 비용 발생** / **멀티 리전 간 연결은 미지원(리전 피어링 필요)** |
| **Peering Gateway**<br>→ 단순 연결, 저비용 | 설정 및 라우팅 간소화 / 교차 리전 VPC 연결 가능 / **무료(인스턴스 트래픽 비용만 발생)** | **VPC 간 중첩된 IP 주소 범위 사용 불가** / VPC가 많아질수록 연결이 복잡 / 보안 정책 일관성 어려움 |
| **Internet Gateway**<br>(Floating IP / NAT GW)<br>→ 완전 분리 및 외부 연동 | **VPC 간 중첩된 IP 주소 범위 사용 가능** / VPC 간 완전 격리 | 인터넷 게이트웨이 트래픽·Floating IP 트래픽 비용 발생 / **인스턴스의 Floating IP 외부 노출** |
| **다중 NIC 인스턴스**<br>→ 중첩 IP 환경, 특수 네트워크 | **VPC 간 중첩된 IP 주소 범위 사용 가능** / 다양한 가상 어플라이언스(방화벽·NAT·Proxy) 사용 가능 | **중계 서버 역할 인스턴스에서 NAT/Proxy 설정 필요** / VPC가 많을 때 라우팅·설정 복잡 |

> ⚠️ 각 인스턴스의 각 네트워크 인터페이스는 **다른 서브넷 IP 주소를 가져와야 한다**

## 7. 사용자 정의 엔드포인트 (Custom Endpoint)

- Service Gateway 연결 대상을 **NHN Cloud 관리형 서비스 → 사용자 Load Balancer까지 확장**한 기능
- **현재 게시 가능한 대상 리소스는 Load Balancer뿐**
- 역할 분리: **게시자(Provider)** ↔ **소비자(Consumer)**
- **Service Name 형식**: `{region}.sep-{12자리 16진수}` (예: `kr1.sep-xxxxxxxxxxxx`)
- 흐름: 게시자가 엔드포인트 생성 → Service Name 발급 → 소비자의 **Tenant ID**를 허용 프로젝트에 등록 → 소비자가 Service Name으로 자신의 VPC에 Service Gateway 생성 → Service Gateway의 **소비자 서브넷 Private IP**로 접근

### VPC 연결 vs 서비스 단위 사설 연결

| 구분 | Transit Hub / Peering Gateway | 사용자 정의 엔드포인트 |
|---|---|---|
| 연결 대상 | VPC / 네트워크 | 게시자의 Load Balancer (특정 서비스) |
| 연결 방식 | VPC 간 라우팅 | Service Gateway를 통한 연결 |
| 접근 주소 | 상대 VPC의 Private IP | **소비자 VPC의 Service Gateway Private IP** |
| **주소 영향** | **VPC 간 CIDR 중복 불가** | ⭐ **VPC 간 CIDR 중복 허용** |
| 주요 용도 | 시스템 간 광범위한 통신 | 공통 API / 내부 서비스 공유 |

**설계 시 제약**
- ⚠️ 대상 Load Balancer는 **생성 후 다른 리소스로 변경 불가** → 새 엔드포인트 생성해야 함
- ⚠️ 해당 엔드포인트를 사용하는 **Service Gateway가 존재하는 동안에는 엔드포인트 삭제 불가**
- Service Name은 애플리케이션이 접속하는 주소가 아니라 **게시된 엔드포인트를 식별하고 Service Gateway를 생성하기 위한 연결 식별자**

## 8. 하이브리드 연결

### 8-1. Direct Connect

- 온프레미스 ↔ NHN Cloud를 **전용 네트워크 회선**으로 직접 연결 (인터넷 구간 미경유)
- 연결 구조: 고객사 온프레미스 ↔ 통신사업자 회선 ↔ Direct Connect ↔ **NHN Cloud Zone** ↔ **Colocation Gateway** ↔ 고객 VPC 서브넷
- ⭐ **대역폭: 최소 10Mbps ~ 최대 10Gbps**
- 전용 회선 연결 접점의 **이중화 지원**
- **L2, L3 기반 VLAN, BGP** 등 다양한 통신 프로토콜 지원

| 구분 | 전용 연결 (Dedicated) | 호스팅 연결 (Hosted) |
|---|---|---|
| 방식 | **회선 사업자**를 통한 전용 회선 연결. NHN Cloud Direct Connect 네트워크 포트와 고객 네트워크 포트 간 **1:1 물리적 연결** | **파트너**를 통한 클라우드 플랫폼 연결. 파트너 네트워크 환경(VLAN, MPLS)을 통해 **논리적(Logical) 연결** |
| 제공 사업자 | **KT, LG U+, SK브로드밴드, 드림라인, 세종텔레콤** | **KINX 클라우드 허브, LG U+ 클라우드 멀티커넥트, 드림라인 클라우드 익스체인지 플랫폼** |
| 성격 | **보안성·안정성 중심** | **유연성·구축 속도 중심**, 멀티클라우드 연동에 적합 |
| 활용 | 금융·공공·제조 등 보안 규제가 엄격한 산업군 | AWS/Azure/GCP와 NHN Cloud를 함께 쓰는 멀티클라우드 |

> 두 방식 모두 인터넷 구간을 거치지 않는다는 점은 동일. 차이는 **물리적 전용선 vs 파트너망 기반 논리 연결**.

### 8-2. VPN Gateway (Site-to-Site VPN)

| 항목 | 값 |
|---|---|
| **대역폭(outbound 기준)** | ⭐ **20M, 50M, 100M, 1G 중 선택** |
| **암호화 알고리즘** | **AES, DES, 3DES** |
| **무결성 알고리즘** | **MD5, SHA1, SHA256** |
| **VPN Gateway 생성 단위** | **VPC 단위 — VPC당 1개만 생성 가능** |
| **VPN Gateway당 최대 연결 수** | ⭐ **10개** |
| 프로토콜 | IPsec (IKEv1/IKEv2) |
| 라우팅 | 정적 라우팅 또는 **BGP 기반 동적 라우팅** |
| 대응 장비 | FortiGate, Juniper SRX, PaloAlto PA, Cisco Firepower 등 |

**제한 사항 (단골 출제)**
- ⚠️ **IPv6 트래픽 미지원 — IPv4 전용**
- ⚠️ **VPC와 온프레미스 간 IP 주소 대역이 중복되지 않아야 함**
- ⚠️ Gateway를 만들 때 선택한 대역폭(예: 20Mbps)은 **동일 VPC 내 모든 연결에 공통 적용**
- ⚠️ **VPN이 연결된 VPC는 Peering Gateway, Transit Hub 등 다른 Gateway 서비스와의 동시 연결이 불가**
- VPN 터널 구간에 **Network ACL 적용 가능**

### 8-3. VPN Gateway 다중 프로젝트 연결 (Transit Hub 공유)

> 위 "동시 연결 불가" 제약을 우회하는 구조 — **이 부분이 함정으로 나오기 쉽다.**

기존에는 프로젝트마다 별도 VPN Gateway를 만들어야 했으나, **Transit Hub 프로젝트 공유**를 쓰면 **하나의 VPC에만 VPN 터널을 갖고 있어도 다른 프로젝트의 VPC가 동일 VPN 경로를 함께 사용**할 수 있다.

**연결 설정 6단계 (순서 배열형 출제 주의)**
1. Project A Transit Hub에서 **Project B, Project C에 공유**
2. Project B, C Transit Hub에서 **Attachment 생성**
3. Project A Transit Hub에서 **라우팅 규칙 추가**
4. **VPC A에 VPN Gateway 생성**
5. VPN Gateway 연결을 생성하여 **로컬 대역에 Transit Hub 선택 후 Project B, C Attachment 선택 후 VPN 연결 각각 생성**
6. **각 VPC에서 라우팅 설정**

**유의사항**
- Transit Hub에 연결된 **모든 VPC 대역이 CIDR 중복 없이 설계**되어야 함
- Hub 라우팅 테이블과 VPC 라우팅 테이블이 **일관된 경로 정책** 유지
- 온프레미스에 전달되는 경로 수가 증가하므로 **VPN 터널 정책(Phase2·Proxy-ID) 관리**가 중요

### 8-4. Network Firewall IPSec VPN
- Network Firewall을 쓰고 있다면 **별도 VPN Gateway를 만들지 않고도** Network Firewall 자체 IPSec VPN 기능 사용 가능
- Network Firewall이 **VPN 종단점 + 보안 정책 제어 + 트래픽 로깅 역할을 동시에 수행**
- Transit Hub와 결합하면 다중 VPC 하이브리드 구조 구성 가능
- **Direct Connect + IPSec VPN 혼합형** 네트워크 구성 가능

## 9. Network Firewall

- **Stateful** 방식으로 트래픽을 제어하여 **응답 패킷 자동 허용**
- **이중화(HA) 구성**을 통한 안정적 운영 지원
- VPC 간 내부 트래픽, 인바운드/아웃바운드 트래픽을 정책 기반으로 관리
- 로그 전송 대상: **Log & Crash Search, Object Storage, Syslog Server**
- VPN 터널을 통한 암호화 통신으로 사이트 간 연결 제공

### 9-1. Network Firewall 서브넷 구성

| 서브넷 | 역할 | 인터넷 게이트웨이 |
|---|---|---|
| **NAT 서브넷(NF-NAT-Subnet)** | 외부 인터넷과 직접 연결. Destination NAT(외부→내부), Source NAT(내부→외부), IPSec VPN(VPN Gateway 생성 시 NIC 생성, 라우팅 규칙 추가 필요) | ⭐ **필수** |
| **트래픽 서브넷(NF-TRAFFIC-Subnet)** | **실제 방화벽 정책이 적용되는 구간** | ⭐ **불필요** (모든 트래픽은 Network Firewall 통과 후 NAT 인터페이스로 전달) |
| **외부 전송 서브넷(NF-Log-Subnet)** | syslog, LNCS, OBS 등으로 **로그 전송**. ⚠️ **방화벽 정책 적용되지 않음** | ⭐ **필수** |

- Destination NAT와 Source NAT는 각각 **전용 인터페이스(NAT용 VIP, S-NAT용 VIP)** 를 사용하며, **NAT 추가 시 네트워크 인터페이스가 함께 생성**된다

### 9-2. Network Firewall + VPC Peering 구조
- Hub-VPC(Security): Internet Gateway, NAT Subnet, Network Firewall Subnet, Log-Transfer Subnet으로 구성. **AZ 분리로 이중화(HA) 가능**
- Peering Gateway 라우팅 테이블에서 `0.0.0.0/0` 목적지를 **Network Firewall TRAFFIC VIP**로 지정 → 모든 트래픽 방화벽 통과

> 🔑 **Longest Prefix Matching (아주 중요한 함정)**
> Spoke-VPC2에는 기본적으로 `10.2.0.0/16` **로컬 경로**가 존재한다.
> **/24 경로를 추가하지 않으면 서브넷 간 통신이 local로 처리되어 방화벽을 우회한다.**
> `/24` 경로를 Peering으로 지정하면 **보다 구체적인 경로(/24)가 /16(local)보다 우선 적용**되어 모든 내부 트래픽이 방화벽을 경유하게 된다.
> → **`/24` 경로 추가는 내부 트래픽까지 방화벽 경유를 보장하는 핵심 설계 요소**이며, **Transit Hub 없이도 VPC 간 보안 트래픽 제어가 가능**하다.

### 9-3. Network Firewall + Transit Hub 3가지 Case

| | Case 1 | Case 2 | Case 3 |
|---|---|---|---|
| 대상 | VPC 2 ↔ VPC 3 통신 | VPC 2 ↔ VPC 3 통신 | **VPC 2 내부 Subnet 간 통신** |
| Hub 서브넷 구조 | **단일 Forward Subnet** (VPC1_NF_FWD) | **IN/OUT 분리** (VPC1_NF_IN, VPC1_NF_OUT) | Case 2와 동일 (IN/OUT 분리) |
| Attachment | Hub-VPC에 1개 | Hub-VPC에 2개 | Spoke-VPC2의 **각 서브넷마다 개별 Attachment** (VPC2_SN1, VPC2_SN2) |
| 특징 | 구성 단순, 라우팅 테이블은 Spoke to Hub / Hub to Spoke 분리 | 트래픽 방향별 경로 분리 → 정책 적용 지점 명확, 정책 로깅·모니터링·포트별 제어 세밀화 | **동일 VPC 내 Subnet 간 트래픽도 반드시 방화벽 경유** → Zone 간 세분화된 보안 정책(Web↔App, App↔DB) 구현 |
| 비용/복잡도 | 낮음 | 운영 복잡도·Attachment 비용 증가 | 라우팅 테이블 항목·Attachment 수 최다 |

**공통 핵심 개념**
- **VPC1_NF_FWD(또는 NF_IN) Port**: Transit Hub로부터 유입된 트래픽을 수신하여 **NF_TRAFFIC_VIP로 전달**하는 인터페이스
- **NF_TRAFFIC_VIP Port**: Network Firewall이 **실제로 보안 정책을 적용하고 트래픽을 송신**하는 인터페이스. Inbound/Outbound 모두 이 지점을 통해 제어
- ⚠️ **라우팅 테이블 분리(Spoke to Hub / Hub to Spoke)**: 단일 라우팅 테이블을 사용할 경우 **Transit Hub 내부에서 루프(Loop) 발생 가능** → 방지를 위해 분리 필수
- ⚠️ **Network Firewall의 NF_TRAFFIC_VIP는 Transit Hub에 직접 연결할 수 없다** → **경유 서브넷(Network Firewall Forward Subnet)이 필요한 이유**
- Attachment는 **서브넷 단위 포트**로 생성 (Peering Gateway는 포트 1개/VPC 단위)

## 10. Virtual IP Address (VIP)

### 10-1. 두 가지 구현 방식

| 방식 | ① 로드밸런서에 할당 | ② 인스턴스가 가상 IP 직접 보유 |
|---|---|---|
| 동작 | VIP를 로드밸런서가 보유, Active/Standby 뒤에서 트래픽 분산·전환 | 인스턴스 NIC에 VIP를 추가 허용(**Allowed address pairs**), VRRP/keepalived로 소유·이동 |
| 리소스 VIP 소유 | ⭐ **리소스가 VIP를 소유하지 않음** | ⭐ **리소스가 VIP를 소유** |
| 장애 전환 | 헬스체크 기반 자동 Failover | keepalived/VRRP 등 헬스체크 스크립트로 구현 |
| 적합 | L4/L7 정책(SSL 종료, 세션 유지) 적용, 외부/내부 서비스 모두 | 애플리케이션이 정적 IP를 직접 바인딩해야 하는 **레거시/DB/HA 클러스터** |

### 10-2. 필수 조건 및 유의사항
- ⭐ **가상 IP를 사용하는 인스턴스들의 네트워크 인터페이스는 반드시 동일한 서브넷(L2 영역) 내에 위치**해야 함
- **Gratuitous ARP**로 소유권 전환
- ⭐ **OS 레벨 직접 구성 필수** — 콘솔 설정 변경 완료 후 인스턴스 내부 OS에서 가상 IP를 사용하도록 직접 설정해야 함 (Linux `ip addr add`, Windows 고급 TCP/IP 설정). **클라우드 시스템이 자동 구성해주지 않음**
- 외부 공개가 필요하면 **IGW + NAT/FIP 또는 LB 조합**을 고려 (내부 VIP는 직접 공인 노출 X)

### 10-3. 스푸핑 방지 우회 3가지 방법 (보안 설정 변경)

| 방법 | 내용 | 평가 |
|---|---|---|
| **스푸핑 방지 활성화 + 추가 허용 주소 등록** | 보안 그룹과 스푸핑 방지 등 모든 보안 기능을 유지하면서 가상 IP만 추가 허용 주소로 등록 | ⭐ **가장 안전, 권장** |
| **스푸핑 방지 기능만 해제** | 보안 그룹 등 다른 보안 기능은 유지, 스푸핑 방지만 해제 | NAT 인스턴스나 게이트웨이 역할 인스턴스에 사용. 보안과 유연성의 균형 |
| **보안 기능 해제** | 스푸핑 방지가 완전히 해제되지만 **보안 그룹도 함께 적용되지 않음** | ⚠️ 주의 요망. 자체 방화벽을 갖춘 환경이 아니면 사용 비권장 |

> 🔑 **자주 나오는 함정**: **가상 IP 자체에는 별도로 적용되는 보안 그룹 규칙이 없다.**
> 가상 IP를 출발지로 갖는 패킷을 수신해야 하는 **상대방 인스턴스는 보안 그룹 수신(Inbound) 규칙에 '보안 그룹'이 아닌 '가상 IP 주소(IP)'를 직접 원격지로 명시**해야 한다.
> 가상 IP는 어느 보안 그룹에도 속하지 않기 때문에, 원격지를 '보안 그룹'으로 지정하면 통신이 차단된다.

## 11. 네트워크 보안

### 11-1. Network ACL vs Security Groups

| 구분 | Network ACL | Security Groups |
|---|---|---|
| **적용 단위** | **VPC, 서브넷과 같은 네트워크 단위** | **인스턴스 네트워크 인터페이스 단위** |
| **상태** | ⭐ **Stateless** | ⭐ **Stateful** (인바운드 허용 시 대응 아웃바운드 자동 허용) |
| 기준 | IP 주소 기반 인바운드/아웃바운드 허용·차단 | 동일 보안 그룹 간 통신 허용 여부 지정 가능 → 세밀한 접근 제어 |
| 역할 | VPC 기본 방어선, 외부 연동 트래픽 제어 | 인스턴스 수준 세밀한 접근 제어 |

- **Security Groups 적용 가능 서비스**: **Instance, NKS, NCS, Storage Gateway**
- **자체 ACL 기능이 있는 대표 서비스**: **NHN Bastion, Load Balancer, RDS, EasyCache, NAS, API Gateway, Object Storage**
- 중앙 집중식 보안 강화가 필요하면 **Network Firewall** 사용 고려

> ⚠️ **함정**: "보안 그룹 규칙은 정상인데 통신이 안 된다 → 실제로 네트워크 인터페이스 수준에서 ACCEPT/REJECT 되었는지 확인" → 정답은 **Flow Log** (Cloud Monitoring·Service Monitoring·CloudTrail 아님)

### 11-2. 전송 구간 암호화 — VPN 3종 비교

| 구분 | Cloud Access | VPN Gateway | Network Firewall IPSec VPN |
|---|---|---|---|
| **용도** | 원격 사용자의 엔드포인트 보안, NHN Cloud 자원에 접속할 때 사용 | 온프레미스 네트워크와 NHN Cloud VPC 간 연결 | 온프레미스 네트워크와 NHN Cloud VPC 간 연결 |
| **사용 사례** | **재택근무, 원격 접속** | 업무 시스템 네트워크 확장, 하이브리드 연결 | 업무 시스템 네트워크 확장, 하이브리드 연결 |
| **연결 대상** | ⭐ **개별 사용자(PC, 노트북 등)** | 기업 네트워크(온프레미스 ↔ NHN Cloud, NHN Cloud ↔ 타CSP) | 기업 네트워크(온프레미스 ↔ NHN Cloud, NHN Cloud ↔ 타CSP) |
| **암호화 프로토콜** | ⭐ **WireGuard 기반 VPN** | IPSec (IKEv1/IKEv2) 기반 VPN | IPSec (IKEv1/IKEv2) 기반 VPN |
| **게이트웨이** | **인터넷 게이트웨이 필요** | **NHN Cloud VPN Gateway + 온프레미스 VPN 장비** | **인터넷 게이트웨이 필요** |
| 구분 | **Client-to-Site** | **Site-to-Site** | **Site-to-Site** |

- Cloud Access는 **Bastion 또는 관리 서브넷(Security Subnet)** 을 통해 내부 인스턴스 접근
- **"접근 전(Cloud Access) → 접속 후(Bastion)" 전 과정의 보안 통제**가 가능
- Bastion 강점: 리눅스 인스턴스 SSH 접근, 명령어 통제, 세션 감시/차단, 브라우저 SSH, 오토스케일 대상 자동 반영

### 11-3. HTTPS — SSL 처리 방식 3종

| 구분 | SSL Passthrough | SSL Offloading (Termination) | SSL Bridging |
|---|---|---|---|
| **개념** | SSL을 그대로 유지한 채 백엔드로 전달 | SSL 암호화 해제(복호화) 후 HTTP로 백엔드 전달 | 중간에서 SSL을 복호화 후 **다시 암호화** |
| **암/복호화 위치** | ⭐ **엔드 서버(백엔드)에서만 처리** | 로드밸런서(LB) 또는 프록시에서 SSL 해제 | 로드밸런서에서 복호화 후 다시 암호화 |
| **백엔드 트래픽** | HTTPS (암호화 유지) | HTTP (비암호화) 또는 HTTPS (다시 암호화) | HTTPS (다시 암호화) |
| **LB 역할** | 트래픽을 단순 포워딩, SSL 해제 없음 | 클라이언트와만 SSL 처리, 백엔드는 HTTP로 통신 | SSL을 복호화한 후 새로운 SSL 연결 생성 |
| **성능** | 성능 부담 증가(백엔드에서 암복호화) | ⭐ **서버 부담 감소 — 가장 효율적** | 중간 처리로 인한 약간의 성능 부담 |
| **보안성** | ⭐ **End-to-End 암호화 — 가장 안전** | 백엔드 서버는 HTTP 가능하므로 상대적으로 낮음 | 백엔드까지 HTTPS — 보안 유지 |
| **인증서/키 등록** | 불필요 | **LB에 등록 필요** | **LB 또는 Web Firewall에 등록 필요** |
| **사용 사례** | **금융, 내부 업무망** 등 높은 보안 요구 | 일반적인 웹 애플리케이션, CDN 등 공개형 | **L7 데이터 처리, WAF, SSL 검사, IDS/IPS, 내부 트래픽 보호** |

- ⭐ **로드밸런서는 SSL Passthrough, SSL Offloading(Termination) 두 가지만 지원**
- ⭐ **Web Firewall은 Passthrough, Offloading, Bridging 3가지 모두 지원**
- SSL Offloading 시 **복호화된 구간은 신뢰할 수 있는 내부 네트워크여야 함**
- SSL Passthrough의 단점: 로드밸런서가 트래픽 내용을 확인하지 못하므로 **별도 SSL 가시화 솔루션이 필요**할 수 있음

## 12. 네트워크 설계 모범 사례 (3원칙)

| 원칙 | 내용 |
|---|---|
| **계층화 (Layered Design)** | VPC/Subnet/Routing/Gateway 계층 구성, Public/Private Subnet 분리로 외부 접근 통제, Transit Hub·Peering Gateway로 리전·VPC 간 연동, Network ACL과 Security Groups로 **다중 방어선** 구성 |
| **암호화 (Secure Connectivity)** | VPN: Cloud Access(SSL) / VPN Gateway(IPSec), Load Balancer SSL 처리: Passthrough/Offloading/Bridging, **복호화 구간은 내부 신뢰망으로 설계**, 인증서 관리·키 보안 정책 수립(Certification Manager) |
| **가시화 (Observability)** | **Flow Log**, Cloud Monitoring을 통한 실시간 추적, Network Firewall·Web Firewall을 통한 통합 분석, 보안 이벤트 감사 로그 보관 정책 수립 |

**추가 설계 지침**
- 내부 서비스는 **Private DNS**, 외부 도메인은 **DNS Plus**로 관리
- 글로벌 트래픽 분산이나 DR 구성을 위해 **GSLB** 활용
- CDN 사용 시 원본(Origin) 접근 제어와 루트 경로 제한으로 오브젝트 스토리지 노출 방지

## 🚨 자주 나오는 함정 포인트 (총정리)

1. **서비스 엔드포인트 도메인은 외부 Public DNS에서도 사설 IP가 조회된다.** — "사설 IP니까 외부에서 못 본다"는 오답 유도.
2. **Private IP DNS 기능을 활성화하지 않아도 이름 수신은 가능**하다. 활성화는 DNS 질의(해석)를 위한 것.
3. **DNS Plus로는 도메인을 구입할 수 없다.** 외부 등록기관에서 사서 연결.
4. **local 게이트웨이 규칙은 삭제 불가**, 사용자가 생성·삭제할 수도 없다.
5. **서브넷은 동시에 1개 라우팅 테이블에만** 연결 가능. 반대(라우팅 테이블↔여러 서브넷)는 가능.
6. **서브넷 정적 라우트는 최초 부팅 시 적용.** 변경 후 즉시 반영을 기대하면 오답 — 재부팅/DHCP 클라이언트 재시작 필요.
7. **VPC 로컬 게이트웨이에는 라우팅 규칙이 없다.** 게이트웨이 라우팅 테이블은 **Peering Gateway, Transit Hub**만.
8. **전이적 피어링 미지원.** A↔B, B↔C가 있어도 A↔C는 별도 피어링 필요.
9. **Peering Gateway는 명시적 연결(Explicit association)을 지원하지 않는다.**
10. **Peering Gateway 자체는 무료**지만 **트래픽 비용은 과금**된다.
11. **Project Peering은 동일 리전에서만** 가능. 다른 리전은 Region Peering.
12. **Project/Region Peering은 테넌트 ID + VPC ID 등록이 필요**하다.
13. 피어링 패킷은 **상대 VPC 라우터를 통과하지 않는다** → 추가 홉 없음.
14. **공유받은 Transit Hub Attachment는 기본 라우팅 테이블 연결·전파가 자동으로 되지 않는다.** Transit Hub 소유 프로젝트에서 명시적 연결 필요.
15. **Transit Hub는 리전 간 직접 공유 불가.** 리전 간은 Peering으로 연결하되, 도착지에 라우팅 리소스가 있어야 전이적 통신이 성립.
16. **멀티캐스트 지원 옵션은 Transit Hub 생성 시에만 선택 가능** — 사후 수정 불가, 삭제 후 재생성.
17. **멀티캐스트 그룹 IP에는 SG/NACL이 적용되지 않는다.** 보안은 수신 인스턴스의 유니캐스트 IP/포트 레벨에서.
18. **멀티캐스트 경로는 콘솔의 서브넷 정적 라우트로 지정할 수 없다** — OS에서 `ip route add` 직접 설정.
19. **1 Subnet = 1 Multicast Domain.** 타 프로젝트 공유 Attachment는 멀티캐스트에 사용 불가.
20. **Transit Hub는 IP 중첩 불가.** 중첩 IP 환경에서 통신하려면 **Internet Gateway(FIP/NAT)** 또는 **다중 NIC 인스턴스**.
21. **Transit Hub는 멀티 리전 간 연결 미지원** — 리전 간은 Peering Gateway 필요.
22. **사용자 정의 엔드포인트는 CIDR 중복을 허용**한다 (VPC 연결 방식과의 결정적 차이). 단, 대상은 **Load Balancer만**.
23. **사용자 정의 엔드포인트의 대상 LB는 변경 불가**, **소비자 Service Gateway가 있으면 삭제 불가**.
24. **Direct Connect 대역폭: 10Mbps ~ 10Gbps.** VPN Gateway와 혼동 금지.
25. **VPN Gateway 대역폭: 20M / 50M / 100M / 1G.** VPC당 **1개**, Gateway당 최대 **10개 연결**.
26. **VPN Gateway는 IPv6 미지원.**
27. **VPN 연결된 VPC는 Peering Gateway·Transit Hub와 동시 연결 불가** — 단, **Transit Hub 프로젝트 공유 구조**로 하나의 VPN Gateway를 여러 프로젝트가 공유하는 설계는 가능.
28. **Network Firewall NAT 서브넷·로그 서브넷은 IGW 필수, 트래픽 서브넷은 IGW 불필요.**
29. **외부 전송(로그) 서브넷에는 방화벽 정책이 적용되지 않는다.**
30. **Longest Prefix Matching**: `/24` 경로를 추가하지 않으면 `/16` local이 우선되어 **내부 트래픽이 방화벽을 우회**한다.
31. **NF_TRAFFIC_VIP는 Transit Hub에 직접 연결할 수 없다** → 경유(Forward) 서브넷 필요.
32. **Spoke to Hub / Hub to Spoke 라우팅 테이블을 분리하지 않으면 Transit Hub 내부 루프 발생.**
33. **가상 IP를 쓰는 인스턴스들은 반드시 동일 서브넷에 있어야 한다.**
34. **가상 IP에는 보안 그룹이 없다** → 상대 인스턴스 인바운드 규칙에 **'가상 IP 주소'를 직접 명시**해야 함.
35. **VIP는 OS 레벨에서 직접 설정해야 한다** — 콘솔 설정만으로 자동 구성되지 않음.
36. **Network ACL = Stateless(서브넷), Security Groups = Stateful(인스턴스 NIC).**
37. **Security Groups 적용 서비스는 Instance, NKS, NCS, Storage Gateway** — RDS·NAS·LB 등은 **자체 ACL** 기능.
38. **패킷 수준 ACCEPT/REJECT 확인은 Flow Log.** Cloud Monitoring(성능 지표)·Service Monitoring(응답 코드)와 구분.
39. **로드밸런서는 SSL Bridging을 지원하지 않는다** (Passthrough + Offloading만). **Bridging은 Web Firewall.**
40. **SSL Offloading = 성능 최우선, Passthrough = 보안 최우선, Bridging = 절충형(보안+가시성).**
41. **Cloud Access는 WireGuard 기반 Client-to-Site**, VPN Gateway/Network Firewall IPSec VPN은 **IPSec 기반 Site-to-Site**.
42. **Cloud Access와 Network Firewall IPSec VPN은 인터넷 게이트웨이가 필요**하지만, VPN Gateway는 NHN Cloud VPN Gateway + 온프레미스 장비 구성.
43. **VPC는 프로젝트당 기본 3개** — 쿼터 조정 신청 필요.
