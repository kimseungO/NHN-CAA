## 1. 요구사항 기반 DB 유형 선택

핵심 질문은 "어떤 DB가 좋은가"가 아니라 **데이터 구조와 접근 방식에 맞는 모델이 무엇인가**이다. 최근에는 한 시스템이 여러 모델을 함께 지원하는 **멀티모델 DB**가 늘고 있지만, 모델별 특성을 먼저 이해해야 한다.

| 유형 | 구조 / 핵심 특징 | 적합한 요구사항 | 대표 서비스 |
|---|---|---|---|
| **관계형(RDBMS)** | 행·열 테이블, 스키마, **ACID**, SQL, 정규화, PK/FK 관계 | 금융·주문·결제·ERP·CRM 등 **데이터 정합성이 중요한 정형 데이터** | NHN Cloud RDS(MySQL, MariaDB, PostgreSQL, MS-SQL), Oracle, SQL Server |
| **키-값** | Key로 직접 접근, 스키마 없음, 인메모리 µs 응답, 샤딩/분산 해싱으로 수평 확장 | **세션 관리, 캐시**, 장바구니, 사용자 프로필 | 메모리: **EasyCache**, Redis, Memcache / 디스크: Cassandra, DynamoDB |
| **벡터** | 임베딩을 **수치형 벡터**로 저장, 코사인 유사도·L2 거리로 검색 | **RAG**, 의미 기반 검색, 추천, 이미지 유사도 검색 | **RDS for PostgreSQL + pgvector 확장** / 외부: Milvus, Pinecone |
| **문서형** | JSON 문서 단위, 컬렉션 내에서도 문서마다 스키마가 다를 수 있음, 중첩 구조 | **스키마 변경이 잦은** 모바일 백엔드, CMS, 로그, IoT | MongoDB, CouchDB, Firebase Firestore |
| **그래프** | 노드(Node)·간선(Edge)·속성(Property) | **관계 탐색·연결 분석**: 소셜 네트워크, 추천, **사기(Fraud) 탐지** | Neo4j, OrientDB, Amazon Neptune |
| **분석용(OLAP)** | **컬럼 기반 저장**(Parquet, ORC, Arrow), 스타 스키마(Fact/Dimension), 반정규화 | 대규모 집계·분석, BI, 데이터 웨어하우스 | DataLake / Hadoop 기반 DW, Apache Hive, Presto, Spark SQL |

**벡터 DB 저장 필드**: ID / Vector(임베딩) / Content(Text Chunk, LLM 컨텍스트로 전달되는 원본) / Source·Metadata(출처, 필터링용)

**분석용 DB 스키마**: Fact 테이블은 수치 이벤트(매출 등), Dimension 테이블은 고객·제품·날짜 등 설명 정보. OLTP(행 기반)와 달리 **열 기반**이라 필요한 컬럼만 읽어 집계가 빠르다.

## 2. DB Instance vs RDS — "누가, 어디까지 제어하는가"

| 구분 | DB Instance (직접 설치형) | RDS (완전관리형) | 아키텍트의 결정 질문 |
|---|---|---|---|
| 제어 권한 | **OS Root 보유** (에이전트 설치, 튜닝 자유) | **OS 접근 불가** (파라미터 그룹으로 관리) | OS 레벨의 보안/튜닝이 필수인가? |
| 지원 엔진 | 사용자가 직접 설치 (RDS 미지원 엔진 **Tibero, CUBRID** 등 포함) | 주요 4대 엔진 (MySQL, PostgreSQL, MS-SQL, MariaDB) | RDS 미지원 엔진·버전인가? |
| 고가용성 | 직접 구성·관리 (**MHA, Pacemaker** 등) | 관리형 HA (자동 Failover) | HA 운영 인력·기술이 있는가? |
| 확장성 | 복제본·스토리지 증설을 직접 구현 | 원클릭 확장 (Read Replica, 스토리지) | 트래픽 급증에 즉시 대응해야 하는가? |
| 백업/복구 | 스크립트 기반 수동 관리 | 자동 백업 + **PITR** | 데이터 복구(RPO) 자동화가 필요한가? |

- **DB Instance**: 콘솔에서 MySQL Instance, MS-SQL Instance 형태로 제공. DBMS가 포함된 이미지로 인스턴스를 만든 뒤 보안 설정·패치·백업을 **사용자가 직접** 수행. → 보안 솔루션 설치, 로그 분석 Agent 설치 등 커스터마이징 필요 시.
- **RDS**: HA, 자동 백업, 모니터링, Failover 내장. **OS 접근 불가**, DB 사용자 계정·스키마 관리만 가능. → 서비스 초기, 운영 자동화가 중요한 SaaS.

## 3. RDS 개요 (MySQL / MariaDB / PostgreSQL)

| 영역 | 내용 |
|---|---|
| 고가용성 | **서로 다른 AZ**에 마스터 + 예비 마스터(Candidate Master) 자동 배치, 장애 시 예비 마스터 **자동 승격** |
| 읽기 분산 | **읽기 복제본(Read Replica)** 추가, 필요 시 **읽기 복제본을 마스터로 승격** |
| 백업/복구 | 자동·수동 백업, **Object Storage로 백업 내보내기**, PITR(특정 시점 복원) |
| 백업 수행 위치 | **예비 마스터(Standby)에서 수행** → 운영 중인 마스터 부하 없음 |
| 관리 | DB 설정은 **파라미터 그룹**, OS·DB 엔진 업그레이드 가능 |
| 모니터링 | 시스템 성능, **Slow Query**, 장애·이벤트 시 **메일/SMS 통보**, "RDS 대시보드"에서 CPU·메모리·디스크 I/O |
| 보안 | VPC 내부 동작, **Security Groups / Subnet ACL**로 접근 통제, DB 사용자 권한으로 접근 제어, **OS 접근 차단** |

## 4. RDS for MS-SQL — 다른 엔진과 구조가 다르다 ⚠️

| 항목 | 내용 |
|---|---|
| HA 구조 | 서로 다른 AZ에 **Primary(주) / Secondary(보조) / Monitor(감시)** 서버 배포 |
| 복제 방식 | **Microsoft SQL Server 네이티브 미러링** (MySQL 계열은 복제 기반 HA) |
| Failover | Monitor 서버가 장애 감지·자동 Failover. **ping 간격 등 사용자가 조정 불가**. **Monitor 서버는 콘솔에서 직접 확인 불가** |
| 구조 성격 | 고가용성에 집중된 Active-Standby → **읽기 복제본 미제공** |
| 백업 | PITR 가능, Object Storage 자동 저장, **Secondary 서버에서 백업 수행** |
| 관리 | 파라미터 그룹, 메일·SMS 알림, 대시보드(CPU·메모리·세션) |
| **제약** | **읽기 복제본 없음** / **최소 8GB 메모리 인스턴스 이상에서만 HA 가능** / 버전별 **SQL Agent 등 일부 기능 제한** / 콘솔 사용자 관리 **미제공** |

## 5. RDS 고가용성 장애 복구 동작 — 엔진별 차이 (최빈출)

### 5-1. PostgreSQL / MS-SQL → **도메인 기반**
1. 정상: 마스터가 트래픽 처리, 예비 마스터는 다른 AZ에서 Health Check + 실시간 복제
2. 장애: 상태 점검 실패 → 예비 마스터 **자동 승격**. 클라이언트는 같은 도메인을 쓰지만 **도메인이 가리키는 IP가 새 마스터 IP로 바뀜**
3. 복구: 이전 마스터는 **Candidate Master로 재등록** → 복제 재개

- 클라이언트가 **DNS 서버에 접속할 수 없는 네트워크**면 도메인으로 접속 불가 → 장애 조치 후 정상 접속 불가
- 내부 가상 IP가 예비 마스터 → 마스터로 넘어가는 동안 **일시적 접속 중단** 가능
- **접속 중단 최소화 설정**: ① DNS 서버 캐시 **TTL** 조정 ② **JVM 수준 DNS 캐시 TTL** 조정 ③ **WAS 커넥션 풀 유효성 검사** 설정

### 5-2. MySQL / MariaDB → **VIP 기반**
- 엔드포인트 도메인에 **VIP(Virtual IP)가 바인딩**되어 있음 (예: VIP 10.10.10.100)
- 장애 시 예비 마스터가 승격돼도 **엔드포인트 IP가 변하지 않음** → 도메인-IP 바인딩이 그대로라 **클라이언트 재설정 불필요**
- DNS 레코드·IP 변경이 없으므로 DNS 전파 지연이나 연결 재구성으로 인한 장애 시간이 짧음

| | PostgreSQL / MS-SQL | MySQL / MariaDB |
|---|---|---|
| 장애 시 엔드포인트 IP | **바뀜** (도메인 IP 변경) | **안 바뀜** (VIP 고정) |
| 클라이언트 측 조치 | DNS·JVM TTL, 커넥션 풀 검증 필요 | 연결 재설정 없이 동일 엔드포인트로 접속 |
| 장애 시간 요인 | DNS 캐시·전파 지연 | 짧음 |

## 6. RDS 읽기 복제본 (MySQL, MariaDB, PostgreSQL)

- 마스터 데이터를 **비동기 복제** → **읽기 전용** 부하 분산
- **마스터 1대당 최대 5대**, 서로 다른 AZ에 분산 배치 가능
- **MS-SQL은 미지원**
- 비동기라 **복제 지연(latency)** 가능, 쓰기는 **반드시 마스터**로

**장애 조치 동작**
1. 복제본 **2대 이상** → 앞단 **로드 밸런서**로 분산 + 주기적 Health Check
2. 일부 복제본 장애 → LB가 **자동 제외**, 남은 복제본이 트래픽 처리
3. **모든 복제본 장애** → 애플리케이션이 **마스터로 직접 읽기 요청을 전환**해야 함
4. 복구 후 → 복제 재동기화 후 LB가 다시 분산

**운영 주의**
- 복제본이 **1대뿐이면 장애 시 읽기 서비스 중단** → ① **2대 이상 + LB** 로 분산·장애 대비, 또는 ② 1대라면 애플리케이션에 **마스터 자동 전환 로직** 구현
- 필요 시 복제본을 **승격(Promotion)** 해 독립 인스턴스로 운영

## 7. RDS 엔진별 기능 비교 (수치 암기)

| 항목 | MySQL | MariaDB | PostgreSQL | MS-SQL |
|---|---|---|---|---|
| 제공 리전 | **한국(판교), 한국(평촌), 일본(도쿄)** | **한국(판교)만** | 한국(판교), 한국(평촌) | **한국(판교)만** |
| 고가용성 | 제공 | 제공 | 제공 | 제공 (미러링) |
| 읽기 복제본 | 일본(도쿄) + **교차 리전: 판교↔평촌**, 마스터당 5대 | 판교, 마스터당 5대 (**교차 리전 X**) | 판교, 마스터당 5대 (**교차 리전 X**) | **미제공** |
| 스토리지 | HDD/SSD **20GB~2TB**, **자동·수동** 확장 | 20GB~2TB, **자동·수동** 확장 | 20GB~2TB, **수동만 (재시작)** | 20GB~2TB, **수동만 (재시작)** |
| 백업 | 자동·수동 + **교차 리전 백업본 복제(판교↔평촌)** | 자동·수동 | 자동·수동 | 자동·수동 |
| OBS 백업·복원 | 동일 리전 | 동일 리전 | 동일 리전 | 동일 리전 |
| 복원 | 스냅숏 복원 + 로그 기반 PITR | 동일 | 동일 | 동일 |
| 콘솔 사용자 관리 | 제공 | 제공 | 제공 | **미제공** (제한적) |

**설계 시 선택 기준**
- 글로벌 / 멀티 리전 → **MySQL** (교차 리전 복제 + 교차 리전 백업이 가능한 유일한 엔진)
- 단일 리전, 단순 구조 → MariaDB
- 분석형 워크로드, 확장성·쿼리 성능 → PostgreSQL
- 트랜잭션 중심, 안정성·일관성 → MS-SQL

> **요약**: 교차 리전 복제와 교차 리전 백업본 복제는 **MySQL만** 지원 → 리전 단위 DR 설계의 가장 큰 차별 요소.

## 8. RDS 운영체제 / DB 엔진 업그레이드

- **OS**: EOL이 가까워지면 콘솔에 **"운영체제 업그레이드" 버튼이 활성화**
- **DB 엔진**: 생성 후 콘솔의 **수정** 기능으로 업그레이드. **마이너 버전은 자동, 메이저 버전은 수동 승인**

**업그레이드 순서 (HA 구성, 무중단 단계적)**
> ① **예비 마스터 업그레이드** → ② **예비 마스터를 마스터로 승격** → ③ **이전 마스터를 예비 마스터로 변경** → ④ **(새) 예비 마스터 업그레이드**

**사전 확인 3단계**
1. **DB 엔진 업그레이드 사전 확인**: 메이저 업그레이드 전 호환성 검사 실행 (예: `mysqlcheck`로 데이터 손상, 인덱스 오류, ENUM/SET 이상 탐지)
2. **파라미터 그룹 비교**: 구·신 버전 파라미터 차이 확인 (예: `collation_server`, `innodb_adaptive_hash_index`)
3. **읽기 복제본으로 사전 검증**: 개발·테스트용 별도 DB가 없으면 **읽기 복제본에 먼저 적용**해 검증 (복제본을 먼저 올리고 승격하는 방식)

**제약 (2025.03 기준)**
- **RDS for MariaDB, RDS for MS-SQL: DB 엔진 업그레이드 미지원**
- **RDS for MS-SQL: OS 업그레이드 미지원**
- → 이 경우 **새 인스턴스 생성 후 백업·복구** 방식 권장
- **EasyCache**는 예비 마스터가 없으므로 순서가 다름: **읽기 복제본 노드 업그레이드 → 승격 → 이전 노드 업그레이드**

## 9. EasyCache (Valkey 기반 인메모리 DB)

| 항목 | 내용 |
|---|---|
| 관리 단위 | **캐시** = 인스턴스 + Valkey 엔진이 설치된 노드 |
| 구성 | 단일 또는 고가용성 캐시, **자동 Failover**, **읽기 전용 도메인** 제공 |
| 읽기 복제본 | **마스터와 동일 리전 최대 2대 + 교차 리전 1대** → 동일 리전 내 복제 2대 + 교차 리전 1대 = **최대 3중 구조** |
| 업그레이드 | DB 엔진, OS 업그레이드 지원 |
| 자동 백업 | **하루 최대 4회** 예약, **캐시 삭제 시 백업본도 삭제** |
| 수동 백업 | **캐시를 삭제해도 유지** |
| 백업 복제 | **동일 리전** Object Storage로 백업본 복제 |
| 백업 수행 위치 | **HA 여부와 관계없이 마스터에서 수행** ⚠️ (RDS는 예비 마스터에서) |
| 복원 | 특정 시점 백업본으로 캐시 데이터 복원 |
| 관리/모니터링 | 파라미터 그룹, 대시보드(CPU·메모리·네트워크·**캐시 Hit Ratio**), 메일·SMS 알림 |
| 보안 | Security Groups (DB 보안 그룹)로 접근 IP 대역 제어 |
| 사용 사례 | 분산 캐시, 세션 데이터, 메시지 큐·실시간 분석, 읽기 복제본으로 대규모 읽기 부하 분산 |

### 9-1. Redis → Valkey 전환

- 배경: Redis가 **2024년 이후 라이선스 정책 변경** → NHN Cloud는 **완전한 오픈 라이선스인 Valkey**로 전환 (Redis의 오픈 포크, Redis와 **완전 호환 API**, 기존 코드 수정 불필요)
- **Redis 기반 EasyCache는 신규 생성 불가**, 신규 생성·업그레이드는 **Valkey 엔진으로만** 지원
- 기존 Redis 인스턴스는 운영 유지 가능하지만 **버전 업그레이드, 읽기 복제본 추가, 백업 주기 변경 등은 제한**될 수 있음
- 마이그레이션: **AOF 또는 RDB 백업 파일을 이용한 복원** + 전환 시점에 캐시 무결성 검증(키 충돌, TTL 유지 등)

| 구분 | Redis용 EasyCache | Valkey용 EasyCache |
|---|---|---|
| 용어 | 복제 그룹 | **캐시** |
| 용어 | 프로필 설정 | **파라미터 그룹** |
| 용어 | 접근 제어 기능 | **DB 보안 그룹** |
| 용어 | 복제 노드 | **읽기 복제본 노드** |
| 읽기 복제본 | 마스터와 동일 리전 **2대** | 동일 리전 2대 **+ 다른 리전 1대** |
| 자동 백업 | **1회/일** | **4회/일** |
| HA 제어 노드 | 콘솔 **비노출** | 콘솔 **노출** |

### 9-2. EasyCache 고가용성 장애 조치 (Sentinel 기반)

- RDS와 달리 **"예비 마스터(Candidate Master)" 개념이 없음**
- 읽기 복제본을 **다른 AZ**에 추가하면 고가용성이 **자동 활성화**
- 각 노드에 **Sentinel(감시 서버)** 설치, 마스터가 있는 AZ에 **HA 제어 노드(HA Control)** 1대가 추가 생성됨

**장애 조치 흐름**
1. Sentinel이 마스터·복제본을 주기적으로 Health Check, 응답 실패 시 **의심(Suspect)** 표시
2. **과반수(3대 중 2대)** 이상이 장애로 판단 → **장애(Fail)** 판정 (Quorum → 단순 네트워크 단절에 의한 **오탐 방지**)
3. 복제본 중 하나를 **새 마스터로 자동 승격**, 기존 마스터는 **disable** 상태
4. 엔드포인트(도메인)가 **신규 마스터 IP로 바인딩** → 클라이언트는 재구성 없이 연결
5. **disable 마스터는 자동 복구되지 않음** → **삭제 후 읽기 복제본을 다시 추가**해 HA 재구성

**주의**
- Sentinel은 HA Control 포함 **최소 3대 이상**이어야 과반수 판단 가능
- 동적 합의 방식이라 유연하지만, 합의 시간(보통 **수 초**) 동안 응답 지연 가능
- Sentinel 간 네트워크 지연이 크면 오탐 가능 → AZ 간 통신 경로 안정화

| | RDS | EasyCache |
|---|---|---|
| 대기 노드 | **예비 마스터를 미리 구성** | 예비 마스터 없음, **복제본 중 하나를 즉시 승격** |
| 판단 주체 | 관리형 Health Check | **Sentinel 과반수(Quorum)** |
| 기존 마스터 | Candidate Master로 **재등록** | **disable** → 수동 삭제 후 재구성 |
| 리소스 효율 | 대기 노드 비용 | 높음 |

### 9-3. EasyCache 읽기 복제본 장애 조치

- 복제본은 추가 시 **다른 AZ에 자동 배치** (동일 리전 최대 2대, 교차 리전 1대)
- 동일 리전 복제본은 **단일 읽기 전용 도메인**에 등록, **DNS 라운드 로빈**으로 IP 바인딩·분산
- **모든 복제본 장애 시 읽기 전용 도메인이 자동으로 마스터 IP에 바인딩되지 않음** → **애플리케이션이 마스터 도메인/IP로 엔드포인트 전환** 필요
- **교차 리전 복제본**: 마스터 장애 감지 **안 함**, **읽기 전용 도메인 생성 안 됨** → **Failover 대상 아님**, 주로 **DR(백업/분산 읽기)** 용도
- 복제본 1대면 장애 시 읽기 중단 → **2대 이상 권장**, 클라이언트에 **도메인 바인딩 변경 감지 또는 재접속 로직** 구현
- 복제본 복구 후 읽기 전용 도메인에 다시 바인딩되어 분산 재개

## 10. 데이터베이스 성능 고려 사항 (작업 중 일시적 성능 저하)

| 구분 | RDS | EasyCache |
|---|---|---|
| 백업 및 복원 | 단일 DB 인스턴스 백업 / 특정 시점 복원 / 백업 후 OBS로 파일 내보내기 | 백업 수행 시 / 캐시 복원 / 백업 및 OBS 파일 내보내기 |
| 고가용성 | 단일 DB 인스턴스의 HA 구성 / 읽기 복제본 생성 | **읽기 복제본 노드 삭제 또는 재구성** |
| 장애 조치 | 읽기 복제본 재구축 / 예비 마스터 재구축 | (위와 동일) |

- **RDS**: 디스크 기반 → 백업·복원 시 **I/O 부하 증가**, PITR·OBS 내보내기 시 CPU·디스크 사용률 상승
- **EasyCache**: 인메모리 + 데이터 양이 적어 **성능 저하를 크게 못 느낄 수도** 있음. 단 노드 단위 백업·복원이나 복제본 삭제·추가 시 **순간적 응답 지연** 가능
- 장애 시: RDS는 예비 마스터·복제본으로 자동 전환, EasyCache는 Sentinel이 **복제본을 마스터로 승격**하는 과정에서 **일시적 연결 끊김** 가능

## 11. RDS for MySQL 레퍼런스 아키텍처 (판교 ↔ 평촌)

1. HA 구성 시 **서로 다른 AZ**에 마스터·예비 마스터 → 자동 Failover
2. 읽기 복제본으로 읽기 분산, **2대 이상이면 앞단에 로드 밸런서**로 엔드포인트 통합
3. **다른 리전에 읽기 복제본** 생성 → 주 리전 장애 시 **보조 리전 복제본을 마스터로 승격**해 DR
4. 리전 간 복제본을 만들려면 **Peering Gateway 또는 Transit Hub**로 **리전 간 사설 네트워크 통신**이 가능해야 함
5. 백업은 **예비 마스터에서 수행** → 마스터 부하 없음. 백업본을 **같은 리전 Object Storage**로 복제
6. **다른 리전의 읽기 복제본에서도 백업 가능**, 그 백업본은 **해당 리전 Object Storage**로 복제

## 13. 캐싱 전략 — 읽기 전략

| 전략 | 동작 | 예시 | 장점 | 리스크 |
|---|---|---|---|---|
| **Cache-Aside** (Lazy Loading) | 앱이 캐시 먼저 조회 → **미스 시 DB 조회 후 캐시 갱신**. DB가 원본(Source of Truth) | 상품 상세 스펙 조회 | 사용 중인 데이터만 캐싱 → 메모리 절감, 캐시 장애에도 DB로 서비스 가능 | **캐시 미스 시 DB 부하 집중**, TTL 설계 중요 |
| **Eager Loading** (Warming-up) | 요청 전에 **미리** EasyCache/CDN Edge에 적재 (배치·이벤트 트리거) | **열차 배차표, 수강 과목** 조회 | **트래픽 폭주 시 DB 부하 제로**, 응답 지연 없음 | 콘텐츠 업데이트 시 **캐시 정합성 관리 복잡** |
| **Edge Caching** | **GSLB**로 최적 리전 선정 → **CDN 엣지**가 Object Storage 콘텐츠 캐싱·전송 | 글로벌 정적 에셋(이미지/JS) | **국가 간 지연(Latency) 극복** | **Purge 지연 시 지역별 콘텐츠 불일치** |

대표 서비스: Cache-Aside = EasyCache + RDS / Eager Loading = EasyCache, CDN, Cloud Functions / Edge Caching = CDN, Object Storage, GSLB

## 14. 캐싱 전략 — 쓰기 전략

| 전략 | 동작 | 예시 | 장점 | 리스크 |
|---|---|---|---|---|
| **Write-through** | 앱이 **캐시와 DB를 동기적으로 동시** 업데이트, 둘 다 성공해야 완료 | **은행 잔액, 포인트** | 데이터 불일치 **기술적 차단** | 쓰기마다 **이중 네트워크 I/O 지연**, 캐시·DB 중 하나 실패 시 전체 쓰기 실패 가능 |
| **Write-around** | **캐시를 거치지 않고 DB에 직접 기록**, 캐시는 조회 시(Cache-Aside) 적재 | **메신저 과거 대화 내역** | 캐시 메모리를 핵심 서비스용으로 보존 | 로그 대량 조회 시 **스토리지 직접 접근 부하** |
| **Write-back** (Write-behind) | 쓰기를 **EasyQueue(Kafka 등)에 완충** → **Worker가 비동기로 RDS에 순차 반영** | **인게임 이벤트, 누적 통계**, 클릭 로그 | DB 사양 대비 **압도적 쓰기 성능**, 트래픽 평준화 | **비정상 종료 시 완충 중 데이터 유실**, **idempotency(중복 처리 방지)**·순서 보장, 최종 일관성 |

## 15. 읽기 × 쓰기 조합 매트릭스 (핵심 질문: "이 데이터에는 어떤 조합이 맞는가?")

| 읽기 ↓ / 쓰기 → | Write-through | Write-around | Write-back |
|---|---|---|---|
| **Cache-Aside** | **일반 서비스형 정합성 패턴** (상품 정보·사용자 프로필·주문 상태) | **메모리 효율 중심** (웹 서비스·사용자 프로필, 캐시 불일치 주의) | ❌ **권장하지 않음** |
| **Eager Loading** | **사전 적재 + 정합성 관리** (정책 데이터, 시스템 설정값) | **사전 적재 + 직접 쓰기** (공통 코드, 지역/통화 목록 — **주기적 재적재·무효화 필요**) | **이벤트 폭주 대응** (이벤트 신청, 대량 통계 — 재시도·중복 처리) |
| **Edge Caching** | **준정적 콘텐츠 갱신** (가격표·배너·정책 페이지, Origin 반영 후 **Edge Purge**) | **정적 콘텐츠 글로벌** (이미지·JS/CSS·공지) | ❌ **권장하지 않음** |

- **Cache-Aside × Write-back 비권장 이유**: Cache-Aside는 **DB를 원본**으로 두는데, Write-back은 **캐시·큐가 먼저 흡수** → 전제 충돌
- **Edge Caching × Write-back 비권장 이유**: 읽기 경로(Edge)와 쓰기 경로(비동기 적재)는 **별도로 설계**하는 것이 자연스러움
- Cache-Aside + Write-through도 분산 환경에서 캐시·DB가 **하나의 트랜잭션이 아니면 엄밀한 강한 정합성은 아님** → "불일치를 최대한 줄이는 설계"
- Edge Caching이 포함된 구조는 대부분 글로벌 서비스 → **정합성보다 지연 최소화 우선**
- **조합 선택 4대 기준**: ① **정합성 수준**(즉시 일치 vs 일시 불일치 허용) ② **트래픽 특성**(읽기 중심 vs 쓰기 폭주) ③ **데이터 유실 허용**(장애 시) ④ **Source of Truth**(최종 원본 위치)

## ⚡ 자주 나오는 함정 포인트

1. **MS-SQL은 읽기 복제본이 없다.** 읽기 분산이 필요하면 MS-SQL은 오답. HA는 **최소 8GB 메모리**부터.
2. **MS-SQL HA = 네이티브 미러링 + Primary/Secondary/Monitor 3대.** 예비 마스터(Candidate)라는 용어는 MySQL 계열. Monitor 서버는 **콘솔에서 안 보이고**, ping 간격도 **조정 불가**.
3. **교차 리전 읽기 복제본·교차 리전 백업 복제 = MySQL만.** PostgreSQL은 판교·평촌 둘 다 있지만 교차 리전 복제는 **불가**.
4. **MariaDB, MS-SQL은 판교 리전만.** MySQL만 도쿄까지 제공.
5. **Failover 후 IP**: PostgreSQL/MS-SQL은 **도메인 IP가 바뀐다** → DNS·**JVM TTL**, 커넥션 풀 검증. MySQL/MariaDB는 **VIP라 안 바뀐다**. 반대로 기억하기 쉬우니 주의.
6. **스토리지 자동 확장**: MySQL·MariaDB는 자동·수동, **PostgreSQL·MS-SQL은 수동만 + 재시작**. 범위는 모두 **20GB~2TB**.
7. **백업 수행 위치가 서비스마다 다르다**: RDS MySQL 계열 = **예비 마스터**, MS-SQL = **Secondary**, EasyCache = **HA와 무관하게 마스터**.
8. **OBS 백업 내보내기·복원은 모든 엔진 "동일 리전"만.** 다른 리전에 백업을 두려면 MySQL 교차 리전 백업 복제나 다른 리전 복제본 백업을 활용.
9. **RDS 읽기 복제본 최대 5대 / EasyCache 동일 리전 2대 + 교차 리전 1대.** 숫자를 섞어 내는 문제 주의.
10. **복제본이 1대면 장애 시 읽기 중단.** 2대 이상 + LB, 또는 앱의 마스터 전환 로직. **모든 복제본 장애 시 자동으로 마스터로 넘어가지 않는다** (RDS, EasyCache 공통).
11. **EasyCache 교차 리전 복제본**은 장애 감지 X, 읽기 전용 도메인 X, **Failover 대상 X** → DR 용도.
12. **EasyCache에는 예비 마스터가 없다.** Sentinel **과반수(3대 중 2대)** 합의로 복제본을 승격. 기존 마스터는 **disable**되어 **자동 복구 안 됨** → 삭제 후 복제본 재추가.
13. **EasyCache 자동 백업은 캐시 삭제 시 함께 삭제**, 수동 백업은 유지. 자동 백업은 Valkey **4회/일**, (구) Redis **1회/일**.
14. **Redis 기반 EasyCache는 신규 생성 불가.** 기존 인스턴스는 운영은 가능하지만 업그레이드·복제본 추가·백업 주기 변경이 제한 → 이전은 **AOF/RDB 백업 복원**.
15. **업그레이드 순서**: 예비 마스터 업그레이드 → 승격 → 이전 마스터를 예비로 → 예비 마스터 업그레이드. **마이너 자동 / 메이저 수동 승인**. MariaDB·MS-SQL은 **엔진 업그레이드 불가**, MS-SQL은 **OS 업그레이드도 불가** (2025.03) → 새 인스턴스 + 백업·복구.
16. **EasyCache 업그레이드 순서**는 "읽기 복제본 노드 → 승격 → 이전 노드".
17. **OS 레벨 에이전트 설치·Tibero/CUBRID·직접 HA(MHA/Pacemaker)** → RDS가 아니라 **DB Instance**.
18. **RAG·의미 검색 = 벡터 DB = RDS for PostgreSQL + pgvector.** 사기 탐지 = 그래프, 대규모 집계 = 컬럼 기반 분석 DB.
19. **Write-back의 필수 동반 설계는 idempotency(중복 처리 방지)** 와 유실 대비. 성능은 좋지만 운영 난이도가 높다.
20. **권장하지 않는 조합은 Cache-Aside × Write-back, Edge Caching × Write-back 두 개.** Eager Loading × Write-back은 "이벤트 폭주 대응"으로 **권장** 조합.
21. **리전 간 RDS 복제본**을 만들려면 **Peering Gateway 또는 Transit Hub**로 사설 통신이 먼저 되어야 한다.
22. **읽기 복제본 엔드포인트를 앱에 직접 등록**하면 클라이언트 IP 캐싱으로 특정 노드에 부하가 몰릴 수 있다 (예제 문제 5번 유형) → LB로 엔드포인트 통합.
23. **(예제 문제 8번 연계, 사용자 가이드 영역)** EasyCache에 백업 파일로 덮어쓰기 복원 시, 대상 캐시의 **Max Memory가 백업 데이터보다 작으면 실패**한다.
